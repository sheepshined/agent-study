## 题目正文

> **Q021. RAG（检索增强生成）的完整管线有哪些环节？**（难度：初 ｜ 频次：高）
> - 考察点：能否说全"离线索引 + 在线查询"双管线，并理解"知识库里有答案"与"智能体能答对"之间隔着哪些环节。
> - 参考回答：
>   - 先给定义与生态位：RAG 不改变模型，在推理前把"可能用得上的知识"检索出来塞进上下文。对比微调与长上下文直塞两条路线，RAG 的独特价值是六项全占：私有知识、时效性（增量索引）、逐句可溯源引用、检索层权限裁剪、知识更新改索引即生效、成本低（每次只带相关片段）。
>   - 离线索引管线六环节：① 连接器 Connector 拉文档 + 元数据 + 权限 ACL → ② 解析 Parsing（PDF/OCR/表格版面还原）→ ③ 切分 Chunking（结构感知 + 重叠）→ ④ 可选上下文增强（Contextual Retrieval）→ ⑤ 嵌入 Embedding（稠密向量 + 稀疏索引）→ ⑥ 索引存储（向量库 + 全文索引 + 元数据）。
>   - 在线查询管线六环节：⑦ 查询理解/改写（指代消解、HyDE）→ ⑧ 混合检索（BM25 + 向量各取 top-K）→ ⑨ RRF 融合 → ⑩ 重排 Rerank（交叉编码器取 top-N）→ ⑪ 权限过滤（按请求者身份裁剪）→ ⑫ 生成（带引用约束）。
>   - 关键认知："知识库里存了答案"和"智能体能答对"之间隔着解析、切分、嵌入、检索、重排、权限、生成约束七八个环节，任何一环出问题最终回答都会错；排障先定位环节再调参，而不是直接改 prompt 或换模型。
>   - 形态谱系四阶段：Naive（一次向量检索直通，幻觉与检索不到高发）→ Advanced（混合检索 + 重排 + 查询改写 + 父子检索）→ Modular（管线可编排）→ Agentic（agent 决定是否检索、检索几轮）；企业现状大多是 Advanced 为主干 + 局部 Agentic。
>   - 通行两阶段检索：每路召回 recall_k ≈ 50（便宜），RRF 融合后交叉编码器重排取 top-5（昂贵但准），这是 RAG 质量提升性价比最高的一步。
> - 追问与陷阱：
>   - 追问"长上下文会不会杀死 RAG？"——主流结论是互补而非替代：长上下文改变的是检索粒度（可以检更大的块甚至整篇文档），而最硬的理由是权限——先塞进 prompt 就没法做检索层裁剪了。常见错误：答"窗口够大就不需要 RAG"。
>   - 追问"微调和 RAG 怎么选？"——判据是知识更新频率与溯源/权限需求：微调把知识训进权重，更新要重训、无法逐句溯源、无检索层权限。常见错误：只答"RAG 便宜"，给不出选择判据。
>   - 追问"哪一环最容易出问题？"——切分与解析（机械等长切分是语义破坏的第一来源，裸 PDF 表格碎）。常见错误：把一切失败归因于"模型不行"。
> - 加分项：能报出 Anthropic Contextual Retrieval 的官方数字（top-20 检索失败率 5.7% → 上下文嵌入 3.7% → +上下文 BM25 2.9% → +重排 1.9%，合计 -67%）；能说出"双索引是标配"（稠密向量 + BM25 稀疏索引）与 RAGFlow/Qdrant/Weaviate 的落地形态。
> - 延伸阅读：[rag-handbook §1 RAG 是什么：架构与角色](../rag-handbook/RAG搭建文档.md) ｜ [rag-handbook §2 格式规范（搭建前必须吃透的部分）](../rag-handbook/RAG搭建文档.md) ｜ [ADP 课程 4.3 知识库质量与 RAG 调优](../fde-handbook/tencent-adp-fde-course/lessons/4.3_知识库质量与_RAG_调优.md)

> **Q022. 文档切分（chunking）怎么做？chunk 大小怎么定？**（难度：初 ｜ 频次：高）
> - 考察点：是否掌握切分策略谱系与参数依据，是否知道"参数要在自己语料上扫描，而不是套默认值"。
> - 参考回答：
>   - 先说目标：切分不是越细越好，而是每个块"既容易被问题命中、又能独立支撑回答"——只命中结论没有条件、只有表格数据没有表头、只有步骤没有前置条件，都说明切分要调。
>   - 策略谱系五档（按复杂度递增，低层不满足再上高层）：固定大小（按 token 硬切 + 重叠，快速原型）→ 递归字符（按段落→句子→词分隔符层级递归切，LangChain `RecursiveCharacterTextSplitter` 是事实标准，通用默认）→ 语义切分（按相邻句嵌入相似度找断点）→ 结构感知（按 Markdown 标题 / HTML 标签 / 代码 AST / 表格按行切，企业文档首选）→ 父子检索 / 句子窗口（小块检索、大块喂模型）。
>   - 参数基线：chunk 大小 256–512 token 起步（事实型问答可降到 128–256）；重叠 10–20%；Weaviate 建议起步 512 token + 50–100 token 重叠；LlamaIndex `SentenceSplitter` 默认 1024/200 偏大，别照抄。腾讯 ADP 产品化取值：切片最大 4800 字符、重叠建议 10% 最高 25%、表格按行切表头最多随 5 行。
>   - 方法论比数字重要：不要套默认值，要在自己的语料上做参数扫描（如 256/512/1024 × 0/10/20% overlap），用黄金测试集对比 Recall@k。
>   - 两个进阶技巧：Anthropic Contextual Retrieval——把整篇文档与每个 chunk 一起喂给便宜的小模型，为该块生成 50–100 token 的位置背景说明再嵌入与建 BM25 索引（成本约 $1.02/百万文档 token），top-20 检索失败率从 5.7% 降到 1.9%（合计 -67%）；Late Chunking（Jina AI）——先整篇编码得到 token 级向量，再对各块跨度池化，块向量天然携带全文上下文。
>   - 结构感知是第一优先：标题层级、表格行、代码函数是天然边界，机械等长切分是语义破坏的第一来源。
> - 追问与陷阱：
>   - 追问"chunk 到底该多大？"——先给基线（256–512 token）再给方法论（测试集扫描定参）。常见错误：背一个数字当标准答案，说不出参数要过测试集。
>   - 追问"重叠为什么需要？越大越好吗？"——重叠防语义在边界被截断；太小边界割裂、太大噪声占比上升（ADP：建议 10%、最高 25%）。常见错误：答"重叠越大越保险"。
>   - 追问"表格怎么切？"——按行切、表头随行走（ADP 表头范围最多 5 行），否则命中数据没有表头。常见错误：把表格当纯文本等长切。
> - 加分项：能说出"切分与嵌入是耦合变更"（切分变了嵌入输入就变，回归要组合测试而不是各改各的）；能解释 Contextual Retrieval 三级增益数字（-35% / -49% / -67%）与 Late Chunking 的"先嵌后切"反直觉之处。
> - 延伸阅读：[rag-handbook §2.2 切分（Chunking）规范](../rag-handbook/RAG搭建文档.md) ｜ [tuning-handbook §3.2 chunk 策略](../tuning-handbook/Agent调优手册.md) ｜ [rag-handbook §8 常见坑（FAQ 式速查）](../rag-handbook/RAG搭建文档.md)

> **Q023. 向量检索的相似度度量有哪些？top-k 怎么选？**（难度：初 ｜ 频次：中）
> - 考察点：对相似度度量数学含义与工程一致性的理解，以及 top-k 是否知道"召回与噪声的权衡"。
> - 参考回答：
>   - 三种常用度量：余弦相似度（cosine，看夹角不看向量长度，文本嵌入最常用）、内积/点积（inner product，向量归一化到单位长度后与余弦等价——python-handbook 的不变量："normalize=True 之后内积 == 余弦相似度"）、欧氏距离 L2（看绝对距离，faiss 提供 `IndexFlatL2`）。
>   - 工程一致性：rag-handbook 规范是向量统一归一化后用余弦相似度；归一化与否决定内积和余弦是否等价，全链路必须保持同一度量，否则分数不可比。
>   - top-k 的本质是召回与噪声的权衡：k 太小漏掉相关片段，k 太大把弱相关内容塞进上下文——噪声拉低精度、助长幻觉，还线性推高生成 token 成本。
>   - 生产通行两阶段：第一阶段每路召回 recall_k ≈ 50，第二阶段重排取最终 top-k；rag-handbook 检索接口规范的默认值是 top_k=5（重排之后）。
>   - 索引实现与规模匹配：faiss `IndexFlatIP` 是精确暴力检索，小语料（<10 万）首选、零参数；更大规模用近似最近邻（ANN）索引，chromadb 则把元数据过滤（where 条件）做进检索层。
>   - 分数阈值要配合排序用：检索分数要暴露给上层，低分告警、无结果显式说"没找到"，分数过低的片段宁可不给（kotaemon 低相关显式告警）。
>   - top-k 不是孤立参数：与召回数量、匹配度阈值、检索范围共同影响结果；调参要围绕固定测试样本看整体命中率，不围绕单条问题反复试（ADP 4.3 纪律）。
> - 追问与陷阱：
>   - 追问"为什么归一化后内积等于余弦？"——单位向量的内积就是夹角余弦。常见错误：实现中混用两种度量导致分数体系错乱。
>   - 追问"k 调大一定更好吗？"——不是，召回多噪声也多，且生成成本随上下文线性涨。常见错误：把"提高召回"简单等同于"调大 k"。
>   - 追问"相似度多少算相关？"——不同模型分数分布不同，没有全局阈值；应结合排序与重排，低分宁可不给。常见错误：死守一个魔法阈值。
> - 加分项：能解释 RRF（Reciprocal Rank Fusion，倒数排名融合）按 Σ1/(k+rank) 只看排名不看分数，免去余弦分数与 BM25 分数两套量纲的校准——这也是混合检索中不同度量可以共存的原因。
> - 延伸阅读：[python-handbook §5.1 嵌入：sentence-transformers](../python-handbook/Python大模型应用开发手册.md) ｜ [python-handbook §5.2 向量索引：faiss 与 chromadb](../python-handbook/Python大模型应用开发手册.md) ｜ [rag-handbook §2.4 嵌入与索引规范](../rag-handbook/RAG搭建文档.md)

> **Q024. 什么是混合检索（hybrid search）？为什么 BM25 还没被淘汰？**（难度：初 ｜ 频次：高）
> - 考察点：是否知道嵌入的盲区，以及"混合检索是默认而不是优化"这一生产共识。
> - 参考回答：
>   - 定义：混合检索 = 稠密向量检索（语义相似）+ 稀疏检索（BM25 等全文关键词匹配）两路并行，各取 top-K，用 RRF 融合合并排名。
>   - BM25 没被淘汰的原因：错误码、型号、人名这类精确词是嵌入的盲区——嵌入把词映射到语义空间，罕见专名/编号的向量区分度差；BM25 按词项精确匹配天然擅长。rag-handbook 设计八条第 2 条原话：混合检索是默认，不是优化；只做向量检索的 RAG 在错误码/型号/人名类查询上必然翻车。
>   - 企业实现形态：RAGFlow 用 Elasticsearch 存双索引；Qdrant/Weaviate 原生支持稀疏+稠密混合；Python 侧 rank-bm25 起步（注意中文必须先分词，如 jieba，不分词整句当一个词、召回为 0）。
>   - RRF 融合的价值：只看排名不看分数，免去两套分数量纲校准——余弦分数与 BM25 分数分布不同、不可直接相加。
>   - 生产化三步的顺序：先混合（解决精确词）、再重排（解决排序）、再父子检索（解决上下文完整性），三个叠加项各自独立有效、可逐个上线。
>   - 双索引是标配（rag-handbook §2.4）：稠密向量索引管语义，稀疏全文索引管精确词，索引期就都要建。
> - 追问与陷阱：
>   - 追问"BM25 中文有什么坑？"——必须先分词（jieba 等），否则整句当一个词项、召回为 0。常见错误：不知道中文 BM25 需要分词，直接 `BM25Okapi(整句列表)`。
>   - 追问"两路分数怎么合并？"——用 RRF 或先做分数校准再加权；直接把余弦分数与 BM25 分数相加是错的。常见错误：量纲混加。
>   - 追问"什么场景可以只用向量检索？"——语料小、查询全是自然语言、无精确词需求的原型可以；生产默认混合。常见错误：认为向量检索全面优于 BM25，"淘汰论"。
> - 加分项：能报出 Contextual Retrieval 里 BM25 的贡献（上下文嵌入 3.7% → +上下文 BM25 2.9%）；知道 QAnything 自研嵌入+重排配对模型来对抗大规模下的检索退化。
> - 延伸阅读：[rag-handbook §2.5 检索接口规范](../rag-handbook/RAG搭建文档.md) ｜ [python-handbook §5.3 稀疏检索：BM25 与中文分词](../python-handbook/Python大模型应用开发手册.md) ｜ [tuning-handbook §3.3 检索参数、embedding 与 reranker 选型、混合检索](../tuning-handbook/Agent调优手册.md)

> **Q025. 重排（rerank）是什么？和向量检索是什么关系？**（难度：初 ｜ 频次：中）
> - 考察点：能否讲清两阶段检索的分工与双塔/交叉编码器的算力差异。
> - 参考回答：
>   - 定义：重排在初步召回之后、生成之前——用第二个模型对候选片段与 query 逐对精算相关性、重新排序、取 top-N；rag-handbook 管线里它位于 RRF 融合之后、权限过滤之前。
>   - 与向量检索的关系是两阶段分工：召回靠便宜的第一阶段（top-50），精度靠昂贵的第二阶段（重排取 top-5）。嵌入是双塔（bi-encoder）架构，query 和文档各自编码只算向量相似度，快但粗；重排用交叉编码器（cross-encoder），query 和 doc 拼在一起进模型逐对精算，贵但准。
>   - 为什么值回成本：reranker 只重排前 K 条候选，计算量远低于全库逐对精算，也无法预计算——但正因为它贵，才只用在已缩小的候选集上。
>   - 常用模型：开源 BAAI/bge-reranker 系列（FlagEmbedding 库），商业 Cohere/Voyage rerank；rag-handbook 生产三步的示例就是 `bge-reranker-base` + top_n=5。
>   - 效果量级：Anthropic Contextual Retrieval 的最后一层增益就是"top-150 重排取 top-20"，把失败率从 2.9% 再压到 1.9%（合计 -67%）；rag-handbook 称两阶段检索 + RRF + 重排是 RAG 质量提升性价比最高的一步。
>   - 生产默认开启：rag-handbook 检索接口规范里 `rerank: bool = True`；调参判断树里"正确片段出现但排序靠后"的第一动作就是上重排。
> - 追问与陷阱：
>   - 追问"为什么不直接用交叉编码器检索全库？"——逐对精算无法预计算、代价随文档数线性爆炸。常见错误：不了解双塔与交叉编码器的算力差异。
>   - 追问"重排和混合检索的顺序？"——混合 → RRF → 重排：先解决"找没找到"，再解决"排得靠不靠前"。常见错误：顺序颠倒或以为二者二选一。
>   - 追问"正确片段出现了但排序靠后怎么办？"——上重排（或检查召回数与融合方式），而不是去换嵌入模型。常见错误：排序问题被当成召回问题治。
> - 加分项：知道 Rerank 训练数据飞轮方向（线上点踩/点击回流为重排模型微调数据，Onyx/FastGPT 的沉淀路线）；能说出 reranker 选型判据"排行榜决定候选，自己的测试集决定上线"。
> - 延伸阅读：[python-handbook §5.4 重排：交叉编码器为什么值回成本](../python-handbook/Python大模型应用开发手册.md) ｜ [rag-handbook §3.3 生产化三步：混合检索 + 重排 + 父子检索](../rag-handbook/RAG搭建文档.md) ｜ [tuning-handbook §3.3 检索参数、embedding 与 reranker 选型、混合检索](../tuning-handbook/Agent调优手册.md)

> **Q026. RAG 的元数据（metadata）应该存哪些字段？**（难度：初 ｜ 频次：低）
> - 考察点：是否理解元数据是"过滤检索 + 引用展示"的基础，以及三条硬规则。
> - 参考回答：
>   - 先说用途：元数据支撑过滤检索（时间、部门、权限）与引用展示（来源、页码）；索引时欠的债检索时都要还。
>   - 最小字段集（rag-handbook §2.3）：chunk_id（文档内稳定且可复现）、doc_id、source_uri（能定位到页/节，如 `hr://policies/travel-v3.pdf#page=4`）、title、doc_type（文档/问答/数据库条目）、version、effective_date、ingested_at（新鲜度监控用）、acl（权限标签）、tenant_id（多租户隔离），可选 keywords（给 BM25 侧补充锚点）与 acl_synced_at（权限变更近实时传播的依据）。
>   - 三条硬规则一：权限元数据必须与文档同批入库——连接器同步时一起拉，Onyx 的做法；不能等查询时再补。
>   - 硬规则二：版本/生效日期必须有——否则过期制度会继续被命中，这是企业场景第一大事故源。
>   - 硬规则三：chunk_id 必须可复现（同文档重导不换 id）——否则增量更新变成全量重灌。
>   - 落地形态：Chroma 里就是随行入库的 metadatas 参数，检索时 `where={"doc_type": "policy"}` 过滤发生在检索层而不是生成层——这正是权限铁律的位置。
> - 追问与陷阱：
>   - 追问"chunk_id 为什么要求可复现？"——同文档重导入 id 不变，增量更新才可行。常见错误：用随机 UUID，导致每次重灌全库。
>   - 追问"过期知识怎么处理？"——version/effective_date 进元数据、到期不再命中、下线旧版并重建索引。常见错误：靠人工定期删文档，忘了就会命中旧版。
>   - 追问"权限字段谁来写？"——连接器同步 ACL 时与文档一起入库，查询时按请求者身份过滤、不信客户端传参。常见错误：信任前端传来的用户角色。
> - 加分项：能说出元数据过滤与向量检索的执行关系（Qdrant 的 payload 分区、Chroma 的 where 过滤都在检索层生效）；能举例 source_uri 支撑前端"点开预览高亮"的引用 UI（kotaemon 参照实现）。
> - 延伸阅读：[rag-handbook §2.3 元数据规范：每条 chunk 必须带什么](../rag-handbook/RAG搭建文档.md) ｜ [rag-handbook §6.5 权限与多租户（企业场景的生死线）](../rag-handbook/RAG搭建文档.md) ｜ [python-handbook §5.2 向量索引：faiss（精确/近似）与 chromadb](../python-handbook/Python大模型应用开发手册.md)

> **Q027. 引用（citation）怎么做到"可验证"？**（难度：初 ｜ 频次：低）
> - 考察点：是否把引用当作可信度与验收标准的一部分，而不是前端装饰。
> - 参考回答：
>   - 为什么重要：企业制度/合规场景，答案不带引用等于不可验收；引用错误则说明检索、重排、文档版本或生成约束有问题（ADP 4.3）。
>   - 生成约束三件套：prompt 里明确"只基于给定上下文回答，不知道就说不知道"；答案逐条标注来源（如 `[doc-1234#p4]`）；检索分数过低的片段宁可不给。
>   - 引用粒度到文档+页码/章节：source_uri 支撑定位（如 `hr://policies/travel-v3.pdf#page=4`），前端可点开预览并高亮原文——kotaemon 的 citation UI 是参照实现，FastGPT/kotaemon 这条线被称为"引用可信"的样板。
>   - "可验证"的定义：答案中每条论断能对应到具体 chunk 的 source_uri，用户能回查原文；rag-handbook 设计八条第 5 条——无引用的答案在生产上视为不合格。
>   - 引用准确性要进回归：用标准问题集回归验证引用准确率（ADP 4.3 排障表：答案完整但引用缺失/错误，优先查生成约束与元数据映射——引用字段、文档元数据、节点变量映射）。
>   - 配套动作：低相关时显式告警、无结果显式说"没找到"，比硬编一个答案好——引用可信的前提是上下文本身可信。
> - 追问与陷阱：
>   - 追问"模型引用错了怎么排查？"——先查生成约束与元数据映射，不是先换模型。常见错误：一律归因为"模型幻觉"。
>   - 追问"怎么防模型编造来源？"——强制引用生成 + 只喂重排后的低噪上下文（top-5）+ 低分片段不给，三件一起上。常见错误：只在 prompt 里说"请引用"，无约束也无验收。
>   - 追问"引用粒度到什么级别？"——文档+页码/章节，只引到文档名用户无法快速核验。常见错误：引用粒度太粗，"可验证"名存实亡。
> - 加分项：把"引用准确率"写进评测指标并用固定集回归（ADP 4.3 原话"标准问题集回归验证引用准确率"）；能对照 kotaemon 的调试观测讲引用 UI 与检索分数暴露的联动。
> - 延伸阅读：[rag-handbook §2.6 引用与溯源规范](../rag-handbook/RAG搭建文档.md) ｜ [ADP 课程 4.3 知识库质量与 RAG 调优](../fde-handbook/tencent-adp-fde-course/lessons/4.3_知识库质量与_RAG_调优.md) ｜ [rag-handbook §3.4 检索质量设计八条](../rag-handbook/RAG搭建文档.md)

> **Q028. 知识库"明明有却答错"和"召回了但答案错"，分别怎么分诊？**（难度：中 ｜ 频次：高）
> - 考察点：能否把检索问题与生成问题分开，用三问分诊定位环节，而不是乱调参或换模型。
> - 参考回答：
>   - 入口是 ADP 4.3 的三问分诊：① 知识库里有没有？② 检索命中了吗？③ 有没有正确生成——先确认有没有知识，再确认有没有命中，最后再看有没有正确生成，这个顺序避免把知识缺失、切分错误或检索范围错误误判为 Prompt 问题。
>   - "明明有却答错"是检索侧问题（F1 系），细分为三种：F1a 知识缺失（其实没入库/解析失败/版本过期，动作是补文档、下线旧版）；F1b 召回失败（正确片段完全没出现，优先查检索范围/权限过滤/召回设置与切分，而不是先调 embedding）；F1c 排序失败（出现但排序靠后，动作是上重排）。
>   - "召回了但答案错"先做对照实验——把答案与召回片段逐条比对：答案扩展了片段外内容 → F2 忠实度问题（生成约束不足，治 prompt 约束）；片段本身旧/冲突 → F1d 知识治理问题（版本/下线/冲突合并）。
>   - 背后是两把尺子：召回率（recall）评"该找到的找到没有"（Recall@k、命中块断言），忠实度（faithfulness）评"答案是否忠于召回片段"（RAGAS faithfulness）。答案错先看是否忠于片段：忠于片段 → 检索问题（治 F1）；不忠于片段 → 生成约束问题（治 F2）。分错方向，调参就是在错层上使劲。
>   - 常见现象对照：答案完整但引用缺失/错误 → 生成约束或元数据映射；换了问法就答不出 → 召回脆弱（问答对沉淀 + multi-query）；命中了过期内容 → 版本治理缺失。
>   - 修完必须回归：Badcase 记录四要素（问题现象、优先归因、调整动作、调整后效果），每个修复直接转成回归用例，确认旧问题没反弹再扩大范围；同一 Badcase 多次复发说明是某类知识组织/切分/检索策略的系统性问题，升级专项。
>   - 宏观背景：MIT NANDA 报告指出 95% 企业 GenAI 项目无可入账价值，评测缺失是根因之一；没有分诊与回归纪律的项目就在这 95% 里。
> - 追问与陷阱：
>   - 追问"拿到 badcase 第一步做什么？"——先确认目标文档已上传、解析成功、可用，再看检索结果，最后才轮到改 prompt。常见错误：直接改 Prompt 或换模型（ADP 4.3 明说这是最容易走偏的做法）。
>   - 追问"召回率和忠实度是一回事吗？"——不是，一个是检索指标、一个是生成指标，指标都不一样。常见错误：混着治，用调检索参数去修忠实度问题。
>   - 追问"怎么算'命中'？"——期望命中的源文档/chunk 出现在检索结果里且排序可接受，要用固定测试集判定，不围绕单条问题。常见错误：拿一次测试的偶然答对当修复成功。
> - 加分项：能默画三问分诊决策树的五分支（F1a/F1b/F1c/F1d/F2）；能引用腾讯 ADP"五堵墙"（知识、工具、流程、权限安全、评测运营）说明分诊纪律在企业落地的位置。
> - 延伸阅读：[tuning-handbook §3.1 分诊先行：召回率与忠实度是两个指标](../tuning-handbook/Agent调优手册.md) ｜ [tuning-handbook §3.5 分诊表（速查）](../tuning-handbook/Agent调优手册.md) ｜ [ADP 课程 4.3 知识库质量与 RAG 调优](../fde-handbook/tencent-adp-fde-course/lessons/4.3_知识库质量与_RAG_调优.md)

> **Q029. 查询改写（query rewriting）有哪几招？各适用什么场景？**（难度：中 ｜ 频次：中）
> - 考察点：是否掌握四种改写手段的机制、适用场景与代价，并能说出各自的失败模式。
> - 参考回答：
>   - 第一招，改写进检索前（多轮结合上下文改写）：把"那个也按上周的方式"这类依赖对话史的问法改写成自含查询；适用多轮对话、指代消解；代价是一次小模型调用。
>   - 第二招，HyDE（Hypothetical Document Embeddings，假设文档嵌入）：让模型先写一个"假想答案"，用假想答案的向量去检索——解决问法与文档措辞差距大的问题（问句和文档在向量空间分布不同，假想答案更像文档）；代价是多一次生成调用，且假想内容可能引入偏置。
>   - 第三招，multi-query（多路查询）：一次生成 N 个改写查询，分别检索后融合（仍走 RRF）；适用口语化/多角度问法；代价是调用与 token 成本 ×N。
>   - 第四招，问答对沉淀：高频口语问法直接映射到固定答案——"命中率最稳的检索是不检索"；适用高频问题、风险口径、需要固定话术的问题；代价是人工校验与冲突合并（ADP 4.3：从文档生成的问答必须人工校验后采纳，未校验不应作为正式答案）。
>   - 问答对的来源纪律：不要只把制度标题改成问题，好问答来自真实用户问法——用户不问"市内交通费报销规则是什么"，问"打车票怎么报""网约车发票能不能报"，这些问法映射同一条标准答案；增补前先查重，避免同一问题不同答案。
>   - 定位边界：查询改写属于索引式 RAG 管线的前置优化；agent 式检索路线的调优杠杆换成"检索工具的返回密度与迭代次数上限"。
>   - 诊断联动：换了问法就答不出是召回脆弱的信号，优先问答对沉淀 + multi-query，然后在固定集上测"问法扰动鲁棒性"。
> - 追问与陷阱：
>   - 追问"什么时候不该用查询改写？"——高频风险口径问题直接走问答对、不检索；每次改写都有成本与偏置。常见错误：把改写当万能药，所有查询都过一遍 LLM，延迟与成本双升。
>   - 追问"HyDE 的风险是什么？"——假想答案里的事实可能污染检索方向（偏置）；假想内容与真实文档措辞仍可能不一致。常见错误：以为 HyDE 一定能提召回，不看场景上。
>   - 追问"批量生成的问答对能直接入库吗？"——不能，必须人工校验、查重、冲突合并（问答类知识的准备规范是"可校验、无冲突"）。常见错误：LLM 批量生成问答直接入库，口径冲突。
> - 加分项：知道 HyDE 出处（arXiv 2212.10496）与 LangChain MultiQueryRetriever；能引用 rag-handbook 设计八条第 6 条"问答对是文档的补充而不是替代"，说清沉淀问答后检索命中率立竿见影的机理。
> - 延伸阅读：[tuning-handbook §3.4 查询改写：HyDE、multi-query 与问答对](../tuning-handbook/Agent调优手册.md) ｜ [rag-handbook §2.1 数据摄入规范：什么能进库](../rag-handbook/RAG搭建文档.md) ｜ [ADP 课程 4.3 知识库质量与 RAG 调优](../fde-handbook/tencent-adp-fde-course/lessons/4.3_知识库质量与_RAG_调优.md)

> **Q030. RAG 的效果怎么评测？RAGAS 四指标是什么？golden dataset 怎么建？**（难度：中 ｜ 频次：高）
> - 考察点：是否掌握"指标—工具—数据集—回归"完整评测闭环，这是 demo 者与能上线者的分水岭。
> - 参考回答：
>   - RAGAS 四指标：faithfulness 忠实度（答案论断能否被上下文支持）、answer relevancy 答案相关性、context precision 上下文精确率（相关块是否排在前面）、context recall 上下文召回率（是否覆盖参考答案全部要点）——前两个评生成，后两个评检索。
>   - 工具分工四件套：RAGAS/TruLens 管离线打分（TruLens 的 RAG Triad：Context Relevance + Groundedness + Answer Relevance）、DeepEval 管 CI（评测不过 = 构建失败）、Langfuse/Phoenix 管线上 trace（query、检索单元、token、成本全记录）；三个都上才是完整闭环。
>   - golden dataset 起步：用 LLM 从真实文档 chunk 合成问答对（RAGAS TestsetGenerator），再尽快掺入生产真实查询——真实查询暴露合成数据没有的措辞、错拼、真实意图；反面纪律是不要用 LLM 凭空合成第一批题目。
>   - 规模与构成：50–150 条即可获得有统计意义的信号，严格回归基线 100+ 条；多样性比数量重要——易/中/难、边界，以及"知识库里没有、应当拒答"的题外类（拒答题）。
>   - 每条三要素：query + 期望命中的源文档/chunk + 参考答案（ground truth 由领域专家/业务方人写，评分可用 LLM-as-a-judge 放大）。
>   - 样本从哪来：生产日志四信号——无结果/空检索、检索分数偏低、短窗口内换措辞重问（最容易被忽略的强信号）、点踩会话；再加调试记录（每条修好的 bug 天然是带期望输出的评测样本，是最低成本的起步方式）。
>   - 回归纪律：任何管线变更（切分、embedding、reranker、过滤参数）前后各跑一遍，对比 Recall@k、MRR、nDCG 与 RAGAS 分数；评测接进 CI，退步直接卡发布；切分与嵌入是耦合变更，要组合测试。
>   - 数据集管理：当作代码管——进 git、走 review、有版本号；dev/held-out 两分（对 dev 过拟合等于自己污染自己的基准）；修题走 CHANGELOG；只增不删（deprecated 标记）。
>   - 为什么必须做：MIT NANDA 报告 95% 企业 GenAI 项目无可入账价值，评测缺失是根因之一；"无二值成功标准的任务 = 高风险未知项"是 FDE 社区共识。
> - 追问与陷阱：
>   - 追问"评测集多大合适？"——50–150 条起步、多样性优先、必须含拒答题与题外类。常见错误：追求上千条但全是 LLM 合成的易题，测不出真实差距。
>   - 追问"RAGAS 四个指标分别评谁？"——faithfulness/answer relevancy 评生成，context precision/recall 评检索。常见错误：把四个都当检索指标，归因错层。
>   - 追问"离线分数涨了就能上线吗？"——还要过 held-out 集与线上 trace 验证；围绕 dev 集反复调参会过拟合。常见错误：没有 dev/held-out 概念，拿调参集当考试集。
> - 加分项：能说出"golden dataset 是 agent 项目唯一不可替代的资产"（模型会换代、框架会重写，只有"你的业务上什么算对"的定义与样本长期有效）；知道 ragas 库现状（0.4.3，仓库已迁 vibrantlabsai/ragas，近月发布放缓）。

> **Q031. GraphRAG 和 Agentic RAG 分别解决什么问题？**（难度：中 ｜ 频次：中）
> - 考察点：能否区分两个"高级 RAG"各自针对的痛点，并给出选型判据而不是名词堆砌。
> - 参考回答：
>   - 先立靶子：向量检索擅长"找相似"，不擅长多跳关联——"A 公司的 CEO 毕业于哪所学校"需要两次关联，一次向量 top-k 给不出来。这是 GraphRAG 要解决的问题。
>   - GraphRAG 机制：索引期用 LLM 从文本抽取实体与关系构建知识图谱 → 聚类成社区 → 分层生成社区摘要；两种查询模式：local search 沿查询相关实体的邻域答具体事实题，global search 汇总社区摘要答全库归纳题（如"这批文档的主要主题是什么"）；代价是索引期 LLM 调用量大。
>   - LightRAG 是轻量替代：砍掉社区摘要与多跳推理，保留实体/关系抽取，检索分 local/global/hybrid/mix 四模式，LLM 调用量与成本大幅降低，且支持增量更新与删除（GraphRAG 的弱项）。
>   - GraphRAG 选型直觉：全库归纳类问题占比高才值得上图；普通事实问答用向量+混合足够。
>   - Agentic RAG 解决的是另一个问题：固定管线只会"一次检索"，接不住复杂多跳、多源、需验证的任务——在用户与检索之间插入 agent，由它决定是否检索（模型自答即可的跳过）、拆解复杂问题、跨多源多轮检索、判断结果是否足够再作答。
>   - 两者与传统管线都是演进关系而非取代：单跳低延迟场景仍走固定管线，复杂任务才升级；Agentic RAG 的代价是延迟与 token。企业现状是 Advanced 为主干 + 局部 Agentic，索引式 RAG 作为工具被 agent 调用——"agent 负责编排，RAG 负责检索"。
>   - 生态数字：Microsoft GraphRAG 约 3.6 万星（基本转入维护模式）、LightRAG 约 4.0 万星（EMNLP 2025）；kotaemon 已把两者做成即插即用后端，可低成本实验。
> - 追问与陷阱：
>   - 追问"GraphRAG 是不是 RAG 升级的必经之路？"——不是，看问题分布：全库归纳题多才上，且索引期 LLM 成本高。常见错误：把 GraphRAG 当高级货无脑上，成本爆炸。
>   - 追问"Agentic RAG 会取代传统 RAG 管线吗？"——不会，演进关系；多轮检索的延迟与 token 是真实代价。常见错误：答"取代"。
>   - 追问"global search 解决什么 local search 解决不了的？"——全库归纳题需要社区摘要的全局视图，向量 top-k 只能给出局部相似片段。常见错误：说不出两种查询模式的分工。
> - 加分项：能一句话点破两者不是竞争关系——GraphRAG 换的是索引结构（图），Agentic RAG 换的是检索决策权（交给模型）；知道 LightRAG 相对 GraphRAG 的核心优势是增量更新与删除。
> - 延伸阅读：[rag-handbook §7.1 图增强 RAG：GraphRAG 与 LightRAG](../rag-handbook/RAG搭建文档.md) ｜ [rag-handbook §7.2 Agentic RAG 与"还需要 RAG 吗"的终局](../rag-handbook/RAG搭建文档.md) ｜ [rag-handbook §1.3 形态谱系：从 Naive 到 Agentic](../rag-handbook/RAG搭建文档.md)

> **Q032. 多租户 RAG 怎么保证竞争对手看不到彼此的数据？**（难度：中 ｜ 频次：高）
> - 考察点：是否理解"权限必须在检索层强制"这条生死线，并掌握存储层隔离方案的取舍。
> - 参考回答：
>   - 总原则先行：隔离在存储层声明，在查询层强制，不信任客户端传参（Onyx / Azure AI Search 同款做法）。
>   - 为什么权限必须在检索层做、不能只在生成层做：未授权的 chunk 一旦进了上下文，模型可能复述其中内容——LLM 无法可靠地"看到再拒答"；且生成层过滤挡不住间接提示注入。唯一可靠的位置是在检索/重排前按请求者身份裁剪候选集（security trimming）。
>   - 通行做法：连接器同步时把源系统 ACL（Access Control List，访问控制列表）与文档一起入库；查询时用请求者身份过滤；权限变更要近实时传播（元数据里的 acl_synced_at 就是干这个的）。
>   - 多租户存储两种方案：Weaviate 原生租户——租户是一等对象、物理隔离、单 collection 支撑数百万租户；Qdrant 官方推荐 payload 分区——单 collection 内 tenant_id 字段 + 强制过滤，而非每租户一个 collection。
>   - 接口层强制：检索 API 的 acl 参数必传、由服务端强制（rag-handbook §2.5 接口规范原话："acl：请求者权限（必传！服务端强制，不信客户端）"），filters 里带 tenant_id。
>   - 上线前必测：用两个不同权限的账号对同一批问题做越权抽查（含"知道文档存在但无权读"的场景），并对 trace 做权限字段审计；ADP 运维纪律同款——每次大批量调整后回归，确认"部门权限没有串库"再扩大范围。
>   - 定性：权限串库不是调参项——tuning-handbook §3.3 判断树里"权限串库/部门内容泄漏"对应的是文档级 ACL 过滤，标注"这是生死线不是调参项"。
> - 追问与陷阱：
>   - 追问"能不能在 prompt 里写'不要透露其他租户的数据'？"——不能，生成层约束挡不住复述与注入。常见错误：以为指令就是权限，这是本题最常见的出局答案。
>   - 追问"每租户一个 collection 不是更彻底吗？"——collection 数量随租户线性爆炸、运维成本高；Weaviate 用原生租户解决，Qdrant 用 payload 分区。常见错误：只知道"物理隔离"一个词，说不出方案取舍。
>   - 追问"权限变更什么时候生效？"——近实时传播是硬要求，T+1 全量同步意味着离职员工当天还能查到敏感数据。常见错误：认为夜间批同步够用。
> - 加分项：能引用 EchoLeak（CVE-2025-32711，CVSS 9.3）说明"未授权内容进上下文后模型无法可靠拒答"已被生产系统零点击利用验证；知道"权限在检索层裁剪，生成层过滤只是兜底"是 rag-handbook 设计八条第 4 条。
> - 延伸阅读：[rag-handbook §6.5 权限与多租户（企业场景的生死线）](../rag-handbook/RAG搭建文档.md) ｜ [FDE 转行手册 §8.6 高频面试题清单](../fde-handbook/FDE转行手册.md) ｜ [rag-handbook §4.2 精读一：Onyx（企业知识层标杆）](../rag-handbook/RAG搭建文档.md)

> **Q033. 嵌入模型怎么选型？换 embedding 模型后旧向量怎么办？**（难度：中 ｜ 频次：中）
> - 考察点：选型方法论（榜单只是候选）与向量空间不兼容的处理流程（全量重建 + alias 切换）。
> - 参考回答：
>   - 选型维度：按语言匹配——中文看 C-MTEB 榜单、英文看 MTEB；权衡维度数与成本、精度；API 模型与本地模型（如 BAAI bge 系列）都可行。
>   - 方法论红线：排行榜分数只决定候选，自己的测试集决定上线——在自己的黄金集上对比才有发言权。
>   - 本地落地不变量：sentence-transformers 里 `normalize_embeddings=True` 把向量归一化到单位长度，之后内积 == 余弦相似度；全链路度量保持一致。
>   - 核心结论：换 embedding 模型 = 换向量空间，新旧向量互不兼容、混存即污染——必须全量重建索引，不存在"渐变迁移"。
>   - 通行迁移流程：建新 collection 全量重灌 → 灰度环境用黄金集对比新旧索引指标 → alias（别名）原子切换指针、随时回滚（Qdrant collections/aliases 模式）。
>   - 回归纪律：embedding 升级是回归测试的标准场景，变更前后各跑黄金集，对比 Recall@k、MRR、nDCG 与 RAGAS 分数；有统计意义的提升才切流。
>   - 耦合提醒：切分与嵌入是耦合变更——切分变了嵌入输入就变，换模型时切分参数可能要一起重新扫描，组合测试而不是各改各的。
>   - 反面教材：换 embedding 没重建索引 → 检索质量"神秘下降"（rag-handbook §8 FAQ 速查表条目）；进阶思路是 QAnything 自研嵌入+重排配对模型来对抗大规模下的检索退化。
> - 追问与陷阱：
>   - 追问"新旧向量能各存一半渐进切换吗？"——不能，两个空间的相似度不可比，混存直接污染检索结果。常见错误：以为可以按文档增量换。
>   - 追问"怎么决定要不要换模型？"——黄金集上对比新旧索引，提升显著才换。常见错误：看榜单刷分就冲动换库。
>   - 追问"切换怎么做到不停机？"——新 collection 重灌 + 灰度对比 + alias 原子切换，出事一键回滚。常见错误：原地覆盖索引，无法回滚。
> - 加分项：能报出常用组合（BAAI/bge-small-zh-v1.5 中文小模型 + sentence-transformers 6.1.0，注意仓库已迁 huggingface/sentence-transformers）；知道向量维度越小存储与计算越便宜但表达力越粗的权衡。
> - 延伸阅读：[rag-handbook §6.3 回归测试与 embedding 升级](../rag-handbook/RAG搭建文档.md) ｜ [python-handbook §5.1 嵌入：sentence-transformers](../python-handbook/Python大模型应用开发手册.md) ｜ [tuning-handbook §3.3 检索参数、embedding 与 reranker 选型、混合检索](../tuning-handbook/Agent调优手册.md)

> **Q034. Claude Code 为什么不用向量库也能检索代码？Agentic 检索与索引式 RAG 怎么选？**（难度：中 ｜ 频次：低）
> - 考察点：是否理解两条检索路线的分野与合流，而不是把一种范式当万能。
> - 参考回答：
>   - 机制：Claude Code（及其开源前身 anon-kode）不建向量索引——工具注册表（`src/tools.ts` 的 getAllTools）里是 GrepTool、GlobTool、FileReadTool 等检索类工具，由模型在主循环里决定搜什么、搜几轮、读哪些文件，这就是 agent 式检索（grep 迭代）。
>   - 上下文侧配合：环境上下文采集用 ripgrep 扫全仓库的 KODING.md（正式版 CLAUDE.md）注入系统提示词；检索是模型驱动的多轮工具调用，而不是一次向量查询。
>   - 两条路线对照：索引式 RAG 需要预建索引并增量维护，查询快且便宜，可扩展到 TB 级；agent 式检索无索引、永远最新，但每查询多轮工具调用 token 贵，不适合海量文档。
>   - 各自的强项：硬查询（语义关联）上迭代搜索往往更准；权限上索引式在检索层天然可过滤，agent 式依赖文件系统权限。
>   - 选型结论：代码仓库场景 agent 式检索已占优——仓库规模适中、有 git/文件系统权限、代码查询常是精确符号名（grep 天然擅长）、强依赖最新性；企业知识库仍是索引式 RAG 的地盘——文档量大、需文档级权限、成本敏感。
>   - 合流形态：Agentic RAG——索引式 RAG 作为工具被 agent 调用，"agent 负责编排，RAG 负责检索"；本工作区六家 agent（Claude Code / Codex / ZCode 等）全部采用 agent 式检索，但企业知识库产品仍是索引式的天下。
> - 追问与陷阱：
>   - 追问"agent 式检索能替代企业知识库 RAG 吗？"——不能：TB 级文档 grep 不可行、文档级权限没法靠文件系统表达、每次多轮调用的成本企业接不住。常见错误：把 coding agent 的做法照搬到企业知识库。
>   - 追问"agent 式检索为什么不担心索引过期？"——它根本不建索引，读的是文件系统当前状态，"无索引、永远最新"。常见错误：以为它也有索引只是不常用。
>   - 追问"两条路线能结合吗？"——能，Agentic RAG：agent 把索引式 RAG 当工具调用。常见错误：认为两条路线互斥、必须站队。
> - 加分项：能说出 agent 式检索路线的调优杠杆是"检索工具的返回密度与迭代次数上限"（tuning-handbook §3.4）；能对照 grep 类工具输出截断/持久 shell 等工程细节（anon-kode BashTool 的 formatOutput）。

> **Q035. 企业知识库调优的"三问分诊"是什么？**（难度：中 ｜ 频次：中）
> - 考察点：能否背出并会用 ADP 课程的企业级调优入口框架，说明每问对应的失败类型与动作。
> - 参考回答：
>   - 出处与定位：腾讯 ADP 课程 4.3 的企业调优入口（tuning-handbook §3 展开）——知识问答效果不稳定时，先判断问题出在知识、切分、检索，还是生成。
>   - 三问顺序：① 知识库里有没有知识？② 检索命中了吗？③ 有没有正确生成？先确认有没有知识，再确认有没有命中，最后再看有没有正确生成。
>   - 为什么是这个顺序：避免把知识缺失、切分错误或检索范围错误误判为 Prompt 问题——ADP 4.3 原话："很多问题的根因并不在生成，而在前面的知识准备和检索环节。"
>   - 第一问不过 → F1a 知识缺失：补文档/问答对，先整理再入库（文档要"可解析、可追溯"，问答要"可校验、无冲突"，数据库要"字段可理解"）。
>   - 第二问细分两支：正确片段完全没出现 → F1b 召回失败（查检索范围、权限过滤、召回设置、切分）；出现但排序靠后 → F1c 排序失败（上重排、调召回数）。
>   - 第三问细分两支：命中且回答错时对照答案与召回片段——扩展了片段外内容 → F2 忠实度问题（生成约束不足）；片段本身旧/冲突 → F1d 知识治理（版本/下线/冲突合并）。
>   - 配套纪律：检索参数围绕固定测试样本调，不围绕单条问题反复试；Badcase 记录四要素（问题现象、优先归因、调整动作、调整后效果）；同一 Badcase 多次复发升级为专项。
>   - 完整流程闭环：知识准备 → 导入配置 → 单次调试 → 批量评测 → 回归沉淀（ADP 4.3 流程总结），对应"五堵墙"里第一堵（知识）与第五堵（评测运营）的衔接。
> - 追问与陷阱：
>   - 追问"为什么先问知识有没有、再问检索？"——知识缺失时调检索参数永远无效，切分错误时调召回数量也无效。常见错误：上来就调召回数量或匹配度阈值。
>   - 追问"三问各自对应什么动作？"——补知识 / 调检索（范围→召回→重排）/ 治生成与版本。常见错误：三问答不全，最后只会"改 prompt"。
>   - 追问"怎么防止改好一个坏三个？"——每次调整后用关键问题集回归，确认旧问题没反弹、权限没串库，再逐步扩大范围。常见错误：单点验证通过就直接上线。
> - 加分项：能默画 F1a/F1b/F1c/F1d/F2 五分支决策树；能引用 ADP 4.3 的chunk 信号表（缺条件、缺表头、口语问法不命中、命中过期内容四种现象各对应什么动作）。
> - 延伸阅读：[ADP 课程 4.3 知识库质量与 RAG 调优](../fde-handbook/tencent-adp-fde-course/lessons/4.3_知识库质量与_RAG_调优.md) ｜ [tuning-handbook §3.1 分诊先行：召回率与忠实度是两个指标](../tuning-handbook/Agent调优手册.md) ｜ [rag-handbook §8 常见坑（FAQ 式速查）](../rag-handbook/RAG搭建文档.md)

> **Q036. 父子切分（parent-child chunking）是什么？解决什么问题？**（难度：中 ｜ 频次：低）
> - 考察点：是否理解"检索粒度与生成粒度解耦"这一核心思想及其适用条件。
> - 参考回答：
>   - 定义："小块检索、大块喂模型"（small-to-big）：索引用子块（小 chunk）精确命中，命中的子块不直接喂模型，而是返回它所属的父块（或周边句子窗口）给 LLM；同族变体还有句子窗口（sentence-window）——命中一个句子、返回周边窗口。
>   - 解决的问题：检索精度与上下文完整性兼得——小块语义聚焦、容易被问题命中；大块提供回答所需的完整上下文（条件、表头、前置步骤）。
>   - 针对的失败模式：片段只命中了结论没有条件、只有表格数据没有表头、只有步骤没有前置条件——这些正是机械切分的典型症状，父子切分是结构性解法。
>   - 参数参考（ADP 产品化取值）：父子级切分中子级切片最大长度不能超过父级，最大可设置 1500 字符；表格按行切分、表头范围最大 5 行。
>   - 在策略谱系中的位置：父子/句子窗口是切分策略谱系的最高一档（rag-handbook §2.2），定位是"低层策略不满足再上高层"的生产标配。
>   - 在生产三步中的顺序：先混合（解决精确词）、再重排（解决排序）、再父子（解决上下文完整性）——三个叠加项各自独立有效、可逐个上线。
>   - 工程代价：索引结构更复杂（要维护子块到父块的映射与去重——多个子块命中同一父块只返回一次）；父块变大后喂模型的 token 成本上升；父块同样要带完整元数据与权限标签。
> - 追问与陷阱：
>   - 追问"为什么不干脆用大块检索？"——大块语义稀释，嵌入向量代表不了细节，命中率反而下降。常见错误：以为块越大效果越好。
>   - 追问"父子切分和加重叠有什么区别？"——重叠只是缓解边界截断；父子是把"用来命中的粒度"和"用来回答的粒度"解耦，是结构性方案。常见错误：两者混为一谈。
>   - 追问"多个子块命中同一父块怎么办？"——按父块去重、以子块最高分排序。常见错误：同一父块重复占用 top-k 名额，上下文浪费。
> - 加分项：能引用验收标准——"命中块能否独立支撑回答"是判断切分是否要调的尺子（rag-handbook 设计八条第 1 条）；知道 ADP 表格按行切+表头随行（最多 5 行）是父子思想在表格上的落地。
> - 延伸阅读：[rag-handbook §2.2 切分（Chunking）规范](../rag-handbook/RAG搭建文档.md) ｜ [rag-handbook §3.3 生产化三步：混合检索 + 重排 + 父子检索](../rag-handbook/RAG搭建文档.md) ｜ [tuning-handbook §3.2 chunk 策略](../tuning-handbook/Agent调优手册.md)

> **Q037. RAG（检索）和 agent 记忆（memory）的边界怎么划？**（难度：高 ｜ 频次：中）
> - 考察点：能否从来源、真值、权限、失效语义、评测五个维度区分两套系统，并给出可操作的判别口诀。
> - 参考回答：
>   - 判别口诀（context-handbook §7.5）：预有的、权威的、可批量管权限的进 RAG；交互中长出来的、个人化的、需要冲突消解的进记忆。
>   - 内容来源：RAG 承载组织预先存在的知识（文档、wiki、工单库）；记忆承载交互中自动产生的内容（对话事实、偏好、轨迹、意图）。
>   - 写入方式：RAG 走离线摄入管线（切分/嵌入/索引，改版重建）；记忆在线写入，随会话流式产生，每次交互都可能产生新版本事实。
>   - 真值地位不同：文档是 ground truth、chunk 可溯源；记忆是模型的观察，可能错、会过时——supersession（事实被取代）/失效机制是记忆的必需品，对应 RAG 侧的版本化文档。
>   - 权限模型不同：RAG 是文档级 ACL，设计期一次做好；记忆随交互动态生长，权限要写进写入路径（provenance 溯源字段），不能事后补。
>   - 失效语义不同：RAG 靠版本化文档（effective_date/下线）；记忆靠 supersedes/invalidates 时间线——矛盾事实的数据库级答案是 bi-temporal（双时间线，Graphiti 的方案）。
>   - 评测不同：RAG 评检索命中率 + 答案忠实（RAGAS）；记忆分"回忆得起"与"遵守得住"两轴四维（回忆、遵守、触发、幻觉）——分开评，不能混。
>   - 合流与共存：记忆系统越来越"RAG 化"（mem0 混合检索、Graphiti 图检索借鉴 RAG 检索工程），RAG 越来越"记忆化"（Agentic RAG 把检索决策交给模型）；两者常同时存在——agent 用记忆记住"这个用户的报表要华东区口径"，用 RAG 检出"华东区口径的定义文档"。
> - 追问与陷阱：
>   - 追问"用户偏好存 RAG 还是记忆？"——个人化、交互中长出来、需冲突消解 → 记忆。常见错误：什么都塞企业知识库，把个人事实变成全公司可见。
>   - 追问"记忆错了怎么办？"——记忆不是事实源，要有取代/失效机制，且评测要单独测"遵守得住"。常见错误：把记忆当 ground truth，没有 supersedes 时间线。
>   - 追问"公司制度改版了，两边分别怎么办？"——RAG 侧走版本化更新/重建索引；记忆侧不需要动（它本来就不存制度）。常见错误：分不清两边的更新语义，两边都重建。
> - 加分项：能落到实现层——mem0 从两阶段流水线到单遍 ADD-only 的算法代际、Graphiti 的 bi-temporal 设计、OpenClaw 五层 tier 记忆模型（context-handbook §4/§7）；知道记忆污染是注入攻击的持久化形态（写入路径也要防注入）。
> - 延伸阅读：[context-handbook §7.5 对照小节：rag-handbook 的「检索 vs 记忆」边界](../context-handbook/Context与记忆系统手册.md) ｜ [context-handbook §4 长期记忆体系：类型学、写入、召回、遗忘](../context-handbook/Context与记忆系统手册.md) ｜ [rag-handbook §1.4 RAG vs Agent 检索：两条路线正在合流](../rag-handbook/RAG搭建文档.md)

> **Q038. 为什么说"检索结果是不可信内容"？对 RAG 的安全设计意味着什么？**（难度：高 ｜ 频次：低）
> - 考察点：能否把 Prompt Injection 的机理接到 RAG 场景，并给出分层防御设计而不是"加个检测器"。
> - 参考回答：
>   - 命题成立的前提：知识库里的内容只要是多方可写的（工单、邮件、用户上传、协作文档、评论区），检索片段就是把第三方可控文本送进上下文——security-handbook 的间接注入载体清单里明确包含"文档库检索片段（chunk）"。
>   - 机理：Prompt Injection 的本质是 LLM 对"系统指令"和"数据内容"没有语法级区分，两者同为 token 序列；间接注入（indirect injection）指攻击载荷放在第三方内容里，靠检索/RAG 触发。
>   - 生产实证：EchoLeak（CVE-2025-32711，CVSS 9.3）是第一个公开的生产系统零点击间接注入漏洞——攻击邮件被检索进上下文，隐藏指令（白底白字/markdown 注释）被当指令执行，进而驱动内部取数并用 markdown 图片外泄；其链路第②步的防御位就是"检索结果即不可信数据"。
>   - 设计含义一（权限前移）：未授权 chunk 一旦进上下文模型可能复述，LLM 无法可靠"看到再拒答"——权限必须在检索/重排前裁剪，这是多租户隔离（Q032）的安全根据。
>   - 设计含义二（防御分层四层）：① 指令隔离（围栏，挡不住自适应攻击）；② 数据来源标记（Spotlighting/provenance——必须是结构化字段而不是文本内自称）；③ 双 LLM 模式（特权 LLM 永不看不可信内容、隔离 LLM 永不持有工具；CaMeL 加污点能力标签与策略引擎，AgentDojo 上验证 85%+ 任务）；④ 最小权限 + 出口控制（egress filtering）——唯一不依赖模型行为的层。
>   - 设计含义三（检测器不是边界）：注入检测器在论文与评测中表现最差——攻击可对抗性改写（base64、隐喻、多语言），误杀率会杀死可用性；OpenClaw 立场原话"内容级扫描挡不住投毒，所以在写入处强制 provenance、用结构化门槛代替事后检测"；正确姿势是检测报警 → 降级运行（如暂收回网络权限）→ 人工复核。
>   - 设计含义四（按兑现路径布防）：输入有无数条路，兑现只有工具出口那几条；注入是概率问题不是布尔问题——正确要求是"证明注入不可兑现"，而不是"证明注入不可能"。配套判据是 lethal trifecta（致命三要素）：访问私有数据 + 接触不可信内容 + 对外通信能力，三者齐备攻击链即闭环，最该砍的是第三条（出口）。
> - 追问与陷阱：
>   - 追问"我司知识库都是内部文档，有风险吗？"——间接注入不看内外、只看"谁写的"：工单、同事邮件、评论区都是多方可写。常见错误：认为内网 = 安全。
>   - 追问"加个注入检测器就安全了吧？"——反模式。检测是遥测信号不是安全边界，"检测通过 = 放行"是错误设计。常见错误：把分类器当唯一防线。
>   - 追问"RAG 场景最该先做哪一层？"——检索层权限裁剪 + 出口控制（egress 白名单），它们不依赖模型行为。常见错误：只做 prompt 围栏就认为有了防御。
> - 加分项：能逐段复述 EchoLeak 四步链（投递 → 注入生效 → 内部取数 → 图片外泄）并指出"前四步任何一步拦住链路即断，生产系统只在第④步的域伪装上被绕过了部分防御"；知道"防的是兑现路径不是输入来源"这句总结。
> - 延伸阅读：[security-handbook §2 Prompt Injection 专题](../security-handbook/AI应用安全手册.md) ｜ [rag-handbook §6.5 权限与多租户（企业场景的生死线）](../rag-handbook/RAG搭建文档.md) ｜ [security-handbook §1.4 lethal trifecta：一条可以当场套用的公式](../security-handbook/AI应用安全手册.md)

> **Q039. PDF、表格、图片类文档的 RAG 有什么工程要点？**（难度：高 ｜ 频次：低）
> - 考察点：是否有"解析层先行、结构感知切分、不适合机器读的先人工提炼"的非结构化文档处理经验。
> - 参考回答：
>   - 总原则：适合人读 ≠ 适合机器检索；裸 PDF 直接入库是 rag-handbook §8 列名常见坑（解析乱、表格碎），必须先过专门解析层。
>   - 解析层的工具位置：PDF 的表格、多栏、扫描件需要专门解析——RAGFlow 的 DeepDoc、MinerU、Docling、PaddleOCR 都在这个位置；RAGFlow 被精读为"深度文档理解：解析与切分的工业级答案"。
>   - 不要直接入库的典型资料：只适合人看的活动海报/宣传页/截图合集、大量设计元素混杂的 PPT 页面、拍照模糊/倾斜/表格线不清的扫描件、无版本标识的多轮修改汇总文档——先人工提炼关键信息再进库（如海报提炼成"活动名称、适用时间、参与条件、优惠规则、限制条件、咨询入口"）。
>   - 表格切分：按行切、表头随行走（ADP 表头范围最大支持 5 行），否则出现"只有表格数据没有表头"的经典坏例；结构感知切分按 Markdown 标题/HTML 标签/表格行这些天然边界切。
>   - 图片与扫描件：走 OCR 进管线（PaddleOCR 路线）；更前沿的多模态 RAG 是图表/截图直接入索引（rag-handbook §7.3 列为方向，RAGFlow DeepDoc、kotaemon 的 Azure DI/Docling/PaddleOCR 路线）。
>   - 格式优先级：结构化文本（Markdown / 带版面信息的 HTML / 提取后的文本）质量远高于裸 PDF——能从源头要 Markdown 就别拿 PDF。
>   - 治理配套：制度类 PDF 必须带 version/effective_date 元数据（到期不再命中）；引用要能定位到页（source_uri 带 page），否则用户无法核验原文。
> - 追问与陷阱：
>   - 追问"扫描件直接 OCR 就行吗？"——模糊、倾斜、遮挡、表格线不清的扫描件 OCR 质量差，先重新整理或人工提炼。常见错误：高估 OCR，把垃圾进垃圾出。
>   - 追问"一张大表怎么进向量库？"——按行切带表头，或转成 Markdown/文本描述；整表一个 chunk 会语义稀释、行级查询命中不了。常见错误：整表直塞。
>   - 追问"PPT 怎么处理？"——设计元素混杂的 PPT 先提取关键信息再入库，不要把幻灯片当普通文档切。常见错误：每页 PPT 当一个 chunk，图文混杂无法检索。
> - 加分项：知道入库前先分知识形态（文档/问答对/数据库三类，各自准备规范不同——rag-handbook §2.1 与 ADP 4.3.2 同源）；能说出 RAGFlow DeepDoc 与 MinerU/Docling 各自的生态位置。
> - 延伸阅读：[rag-handbook §2.1 数据摄入规范：什么能进库](../rag-handbook/RAG搭建文档.md) ｜ [rag-handbook §4.3 精读二：RAGFlow（深度文档理解）](../rag-handbook/RAG搭建文档.md) ｜ [rag-handbook §7.3 再往后的方向（一句话索引）](../rag-handbook/RAG搭建文档.md)

> **Q040. 怎么估算一个 RAG 项目的月度成本？**（难度：高 ｜ 频次：低）
> - 考察点：能否用四档单价写出核算公式，并指出成本大头与降本杠杆的优先级。
> - 参考回答：
>   - 核算公式（tuning-handbook §7.1）：成本 = Σ_calls [ 普通输入 × 输入价 + 缓存输入 × 缓存价 + 输出 × 输出价 +（缓存写部分 × 写价）]，按四档单价 × 用量逐项算，不能只报一个混合价。
>   - RAG 链路的账单构成三块：检索侧（嵌入查询、重排服务、向量库基础设施）、生成侧（把 top-k 片段塞进 prompt 的输入 token + 答案输出 token）、索引侧（新文档嵌入与重建）。
>   - 关键量级判断：生成答案比嵌入查询贵两个数量级——RAG 成本大头在生成端。佐证：输出单价普遍是输入的 4–10×（Sonnet 5：$10/$2 = 5×；gpt-5.2：$14/$1.75 = 8×；Haiku 4.5：$5/$1 = 5×），而生成端上下文又比查询长得多。
>   - 单价口径（2026-09-28 实抓，$/M 输入/输出）：Anthropic Sonnet 5 $2/$10、Haiku 4.5 $1/$5、Fable 5.1 $10/$50；OpenAI gpt-5-mini $0.25/$2；Gemini 3.8-flash $0.75/$3.75；DeepSeek flash $0.30/$1.20（缓存命中 $0.006 ≈ 2%）。报价要注明基准日。
>   - 缓存是第一杠杆：缓存读价约为输入价 2–25%（DeepSeek 最激进，命中价约为未命中的 2–3.3%）；命中率要进 trace 与报表，命中率异常下跌 = 前缀漂移告警。RAG 场景的系统提示词 + 工具定义是稳定前缀，天然适合缓存。
>   - 批处理/错峰一律 -50%（Anthropic/OpenAI/Gemini 批处理 API；DeepSeek 错峰时段半价）——离线评测、夜间数据回流、批量打标没有理由不用。
>   - 结构性省钱：模型路由（简单查询走 Haiku 4.5 / gpt-5-mini 档、复杂查询升级大模型）与语义缓存（语义相近问题命中同一答案，公开报道最高省约 68.8%，叠加路由综合 60–85%，带正确性风险要评测兜底）。
>   - 估算框架示例：月查询量 ×（检索次数 × 输入 token × 输入价 + 输出 token × 输出价），再按缓存命中率折减、按路由比例加权；索引侧按日增文档量 × 平均文档 token 估嵌入成本；别忘了隐性项——回归评测的 judge 调用（全量 judge 账单可能超过 agent 本身）、重排服务、向量库运维。
> - 追问与陷阱：
>   - 追问"token 单价怎么报才专业？"——报四档（输入/缓存读/缓存写/输出）+ 批处理价，注明模型、基准日与币种。常见错误：只报一个"平均单价"，缓存与批处理的数量级差异全被抹掉。
>   - 追问"为什么缓存命中率是第一成本指标？"——命中价与未命中价差一个数量级（Anthropic 缓存读 0.1×、DeepSeek 0.02–0.033×），且输入 token 在多轮场景是复利结构。常见错误：只盯输出单价。
>   - 追问"预算超了先砍什么？"——先缓存/路由/批处理（不降质量），再考虑换小模型（要过评测）。常见错误：直接换最便宜模型，质量塌了再返工。
> - 加分项：能报出具体数字组合——DeepSeek flash $0.30/$1.20 + 命中 $0.006、gpt-5-mini $0.25/$2 作为路由底座、语义缓存 68.8%/60–85% 的出处与风险；知道 Gemini 3.8-flash 现价 $0.75/$3.75 只到 2026-12-31 的时效意识。
> - 延伸阅读：[tuning-handbook §7.1 token 成本核算：四档单价 × 用量](../tuning-handbook/Agent调优手册.md) ｜ [tuning-handbook §6.6 四家模型价格速查（2026-09-28 实抓）](../tuning-handbook/Agent调优手册.md) ｜ [rag-handbook §6.6 数据新鲜度与成本](../rag-handbook/RAG搭建文档.md)
