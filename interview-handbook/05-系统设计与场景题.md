## 题目正文

> **Q079. 设计一个企业知识库问答系统，你会怎么做？**（难度：初 ｜ 频次：高）
> - 考察点：能否按"离线管线 / 在线服务 / 评测上线"分层作答，并在切分、检索、模型分档这些关键环节给出选型理由与数字。
> - 参考回答：
>   - 面试时先澄清需求：文档规模与格式分布（PDF/Wiki/工单）、数据敏感级与权限模型、新文档多久必须可查（时效）、验收指标是什么——ADP 3.1 把需求翻译成背景现状/业务目标/使用对象/任务边界/资料知识/系统工具/限制与验收七个维度，一句话都不该漏。
>   - 架构按双管线答（rag-handbook §1.2）：离线索引管线 = 连接器（拉文档+元数据+权限 ACL）→ 解析（PDF/OCR/表格/版面还原）→ 切分 → 可选上下文增强 → 嵌入 → 索引存储；在线查询管线 = 查询改写 → 混合检索 → 重排 → 生成带引用。
>   - 切分（chunking）是第一关键决策：chunk（切分块）256–512 token 起步、重叠 10–20%；企业文档首选结构感知切分——表格按行切、表头随行走；不要套默认值，要在自己语料上做参数扫描（如 256/512/1024 × 0/10/20% overlap）用黄金集对比 Recall@k。
>   - 检索上生产化三件套（rag-handbook §3.3）：混合检索（BM25 与向量各取 top-50、RRF 融合）解决精确词命中，交叉编码器重排取 top-5 解决排序，父子检索（小块检索、大块喂模型）解决上下文完整性；三者独立有效、可逐个上线，预算紧先上混合检索。
>   - 生成侧给数字抓手：知识不足要拒答不编造（ADP 3.2 把拒答话术当必配项）；模型按任务分档省钱——查询改写用 Haiku 4.5（$1/$5），生成用 Sonnet 5（$2/$10），离线批量入库与回归评测走批处理一律 -50%。
>   - 评测先行：从真实用户问题挖黄金数据集，检索层看 Recall@k 与忠实度，端到端看答对率；eval-handbook §2.2 的口径是"离线是安全网、在线是体温计、回放是传送带"，离线评测是上线准入门槛。
>   - 上线与迭代：灰度发布 + 生产 trace 抽样人审 + 坏例回流评测集；知识新鲜度靠连接器定期同步与增量索引，别让答案停在半年前的语料上。
>   - 失败模式清单要主动背出来：解析丢表格、切分断语义、检索噪声带偏答案、模型复述未授权 chunk、引用不可溯源；其中权限问题要在检索层裁剪而不是生成层过滤（详见 Q082）。
> - 追问与陷阱：
>   - 追问：文档全是扫描件 PDF 怎么办？常见错误：直接切块嵌入——必须先 OCR 与版面还原、保留表格结构；解析质量是 RAG 的天花板，上游 garbage 下游无解。
>   - 追问：有了 1M 窗口的长上下文模型，还需要 RAG 吗？常见错误："窗口大就不用检索了"——长上下文是翻倍计价（Gemini 3.1-pro >200k 输入 $4/M），且权限裁剪与引用溯源这两个企业刚需 RAG 才有；两者是互补不是替代。
>   - 追问：怎么证明系统比直接问裸模型好？常见错误：凭感觉说"接了知识库当然准"——同一评测集对比"有检索 vs 无检索"的答对率与忠实度，用数字说话。
> - 加分项：能报出 Anthropic Contextual Retrieval 的增益曲线——top-20 检索失败率从基线 5.7% → 上下文嵌入 3.7%（-35%）→ +上下文 BM25 2.9%（-49%）→ +重排 1.9%（合计 -67%），成本约 $1.02/百万文档 token；或背出 ADP 3.2 标准模式的产品化清单：问答对兜高频、同义词解换说法、拒答兜知识不足、长期记忆做个性化。
> - 延伸阅读：[rag-handbook §1.2 双管线架构](../rag-handbook/RAG搭建文档.md)｜[rag-handbook §3.3 生产化三步：混合检索 + 重排 + 父子检索](../rag-handbook/RAG搭建文档.md)｜[ADP 3.2 标准模式实战：知识助手](../fde-handbook/tencent-adp-fde-course/lessons/3.2_标准模式实战：知识助手.md)

> **Q080. 设计一个合同/文档审核流水线，怎么编排？**（难度：初 ｜ 频次：中）
> - 考察点：能否把模糊的"审核"拆成节点可枚举的工作流，并用节点契约与并行化保证稳定与吞吐，而不是写一个巨型 prompt。
> - 参考回答：
>   - 先用六问判据定形态（workflow-handbook §1.2）：合同审核步骤可枚举、输入输出可契约化、结果可程序验收（条款齐不齐可判定）、确定性是硬要求、错误代价高——六问基本全"是"，这是典型工作流场景，不该用自由 agent。
>   - 流水线按 prompt chaining（提示词链，串行接力）拆：解析（PDF→结构化文本，表格单独处理）→ 要素提取（甲乙方、金额、期限、违约条款，结构化输出）→ 路由（routing 按合同类型分发：采购/销售/NDA/租赁）→ 并行审查 → 聚合汇总 → 生成审核报告。
>   - 并行审查用 parallelization（并行化）模式：缺失条款检查、风险条款识别、金额一致性核对三路同时跑再聚合（workflow §2.3）；聚合规则要预先写死（风险项取并集、引用优先），部分失败语义显式声明（全成功才过 or 容忍 N 路失败重跑）。
>   - 节点契约是可靠性的真正来源（workflow §3.3 六条）：显式声明字段名与类型、必填缺失要追问或走分支、枚举值收敛（风险等级只取高/中/低）、跨节点只走变量引用不走"默契"、契约变更=版本变更必须回归评测。
>   - 模型分档控成本：要素提取与分类用便宜档（gpt-5-mini $0.25/$2 或 Haiku 4.5 $1/$5），风险判断用 Sonnet 5（$2/$10）档；存量合同批量复审走批处理 -50%。
>   - HITL（human-in-the-loop，人在环）收口：低置信度出口与高风险结论（如"建议删除第 X 条"）转人工复核——审核效率的收益来自"人审范围收窄到机器标记的段落"，而不是全自动。
>   - 评测设计：抽取字段用可程序验收的判据（字段命中、枚举正确），端到端用人工标注的风险清单对齐；节点选型先于提示词调优——lesson 4.4 的典型 Badcase 就是用标签提取节点收集参数，字段缺失会影响后续执行时应改用参数提取节点并配缺失追问。
>   - 失败模式：解析层丢表格与盖章页、超长合同超上下文窗口要分段、输出格式漂移（用 schema 校验兜住）、附件与版本对比漏检。
> - 追问与陷阱：
>   - 追问：为什么不让一个强模型一次读完整个合同直接出报告？常见错误："节点多是过度设计"——单 prompt 无中间产物、错了无法定位、无法并行、改一处全重测；流水线每步可断言、可单点重跑。
>   - 追问：新增一种合同类型怎么办？常见错误：去改一个巨型提示词——正确做法是 routing 新增一路分支 + 为该类型补评测集，流程结构不动。
> - 加分项：能提出用 evaluator-optimizer（评估者-优化者）模式做"生成-评审回环"（初稿按检查清单自审再修订），以及"流程超过 15-20 个节点、画布拉面条时优先拆子工作流"（workflow §1.2）。
> - 延伸阅读：[workflow-handbook §2 工作流模式谱系：五种 pattern，一个变量](../workflow-handbook/Agent工作流编排手册.md)｜[workflow-handbook §3.3 输入输出契约设计规范（六条）](../workflow-handbook/Agent工作流编排手册.md)｜[ADP 4.4 Workflow 调优](../fde-handbook/tencent-adp-fde-course/lessons/4.4_Workflow_调优.md)

> **Q081. 给一个已有产品加"AI 助手"入口，第一步做什么？**（难度：初 ｜ 频次：中）
> - 考察点：有没有"先找场景再谈模型"的落地方法论，能不能抵御"上来就搭平台、上多 agent"的诱惑。
> - 参考回答：
>   - 第一步不是选模型，是把"加个 AI 助手"翻译成可测量目标：MIT NANDA 报告显示 95% 的企业 GenAI 项目没有可入账价值，根因多数是场景没选对——ADP 3.1 的做法是把客户一句话需求拆成七个维度（背景现状/业务目标/使用对象/任务边界/资料知识/系统工具/限制与验收）逐项确认。
>   - 场景选择三条标准：高频（每天发生）× 有稳定资料或固定流程 × 错误可容忍或可兜底（可拒答/可转人工）——制度问答、售后政策、工单预填是典型切口；ADP 3.1 的原则是"第一期先做能闭环、可验收的部分"，不追求一次覆盖所有愿望。
>   - 用五堵墙做可行性盘点（ADP 1.3）：知识（资料齐不齐、谁维护）、工具（有没有 API 与鉴权）、流程（固定还是开放）、权限安全（谁能看什么、数据出不出域）、评测运营（怎么验收、谁运营）——哪堵墙没准备好，哪堵就是排期风险，方案里要明说。
>   - 构建模式用现成选型谱系（ADP 四种模式，工具箱 §3.1 决策树）：只回答不"办事"→标准模式；输入明确流程固定→单工作流；多角色协作→Multi-Agent；开放探索读写文件→Claw；并画出分阶段模式演进图（ADP 3.1 酒店案例：一期标准模式答信息→二期工作流接工单→后期经营分析）。
>   - MVP 蓝本照 ADP 3.2 标准模式抄：系统提示词定边界→上传知识库→高频问答对→同义词→拒答话术→长期记忆→测试集验证→发布——三四周可见可演示，先赢信任再谈扩展。
>   - 评测先行：验收数据集在开发期就建好（ADP 3.2 专门有一步"用测试集检查应用是否真的可用"），发布后必须从用户侧再测一次——workflow §6.5 的纪律是"开发态调试正常，不代表用户侧已经拿到最新版本"。
>   - 成本先算一笔账（工具箱 §7.1 模板）：日均会话数 × 输入输出 token × 分档单价 × 缓存命中率，另加评测与冗余系数（示例：日均 2000 次会话、输入 3k/输出 0.8k、缓存命中率 60%，月消耗约 ¥2,150 × 冗余 1.3 ≈ ¥2,800）；开发调试阶段消耗约为上线稳态的 2-4 倍，预算要留。
>   - 失败模式：把"平台化"当一期目标、没有拒答导致幻觉进业务、无评测集上线即盲飞、助手没接产品账号体系成为越权后门。
> - 追问与陷阱：
>   - 追问：老板说"别人都有 copilot 我们也要一个"，怎么接？常见错误：直接开工——先翻译成 2-3 个候选场景与各自验收指标，用小 POC 对比后定一期范围，让预期落在纸面。
>   - 追问：产品已有账号与权限体系，AI 助手要不要另做一套？常见错误：另起炉灶——必须复用现有身份与 ACL（Access Control List，访问控制列表），权限在检索层裁剪，否则助手就是越权入口。
> - 加分项：能说出"模式可切但配置不继承"（ADP 2.3：标准/单工作流/Multi-Agent 之间可切换但提示词与模型配置不相互继承，Claw 不支持切回）——选型前想清楚切换成本，这是从课程里来的实战细节。
> - 延伸阅读：[ADP 3.1 方案设计方法](../fde-handbook/tencent-adp-fde-course/lessons/3.1_方案设计方法.md)｜[FDE 实战工具箱 §3.1 四模式选型决策树](../fde-handbook/FDE实战工具箱.md)｜[workflow-handbook §1.2 判据表：六个问题定形态](../workflow-handbook/Agent工作流编排手册.md)

> **Q082. 设计多租户 RAG，怎么保证竞争对手看不到彼此的数据？**（难度：高 ｜ 频次：高）
> - 考察点：能否把"数据隔离"落成存储/检索/应用三层的具体机制（选型、缓存、权限传播、越权验证），而不是一句"做了权限过滤"。
> - 参考回答：
>   - 先澄清隔离级别与合规约束：逻辑隔离（共享索引+元数据过滤）够不够还是要物理隔离、数据驻留（数据存哪国）、审计要求；租户数量与单租户数据量决定成本模型——这些决定选哪条技术路线。
>   - 核心原则一句话（rag-handbook §6.5）：隔离在存储层声明，在查询层强制，不信任客户端传参——租户身份永远来自鉴权态（token/session），绝不来自请求体里可篡改的 tenant_id 字段。
>   - 两条技术路线：Qdrant 官方推荐 payload 分区（单 collection 内 tenant_id 字段+强制过滤，成本低运维简单，适合海量小租户）；Weaviate 原生多租户（租户是一等对象、物理隔离、单 collection 支撑数百万租户）；极端合规要求再上每租户独立索引/独立库（成本最高，留给头部大客户）。
>   - 权限为什么必须在检索层做：未授权 chunk（切分块）一旦进了上下文，模型可能复述其中内容——LLM 无法可靠地"看到再拒答"，且生成层过滤挡不住间接提示注入；唯一可靠位置是检索/重排前按请求者身份做 security trimming（检索前裁剪），连接器同步时把源系统 ACL 与文档一起入库。
>   - 共享基础设施的串密风险清单要主动列：语义缓存与提示缓存必须带租户键、命中前校验租户一致；embedding（向量化）可被反推、高敏租户要独立模型或独立库；trace 与日志里的原文脱敏；权限变更要近实时传播（acl_synced_at 类元数据+增量同步），撤销权限不能等下次重建索引。
>   - 应用层兜底：输出引用只能来自该租户授权文档集合、配额按租户计量、管理操作全审计。
>   - 攻击面别漏注入外带：EchoLeak（CVE-2025-32711，CVSS 9.3）证明零点击注入链能让"合法能读 A 文档的会话"把 A 的内容外带出去——多租户系统要按 lethal trifecta（致命三要素：私有数据访问 × 不可信内容进上下文 × 对外出口）逐要素标注断点。
>   - 验收方法照 rag-handbook §6.5 原文动作答：用两个不同权限的账号对同一批问题做越权抽查（含"知道文档存在但无权读"的场景），并对 trace 做权限字段审计；越权用例进 CI 常驻回归，按 pass^k 思路（同一任务 k 次采样全过才算过，τ²-bench 口径）反复压。
>   - 失败模式：过滤器被客户端传参绕过、缓存串租户、权限同步延迟窗口、子代理/插件继承过宽权限把 A 租户数据带给 B。
> - 追问与陷阱：
>   - 追问：每租户一个 collection 和 payload 过滤怎么选？常见错误："物理隔离一定更安全所以默认它"——独立 collection 只留给少量大客户；海量小租户用强制过滤+默认 deny，漏配比过配更危险，要配配置审计。
>   - 追问：向量不是原文，会有泄漏风险吗？常见错误："向量泄漏无所谓"——embedding 可被反推攻击，共享嵌入模型与共享缓存都要按数据分级评估。
> - 加分项：能给出"权限变更近实时传播"的字段级设计（ACL 同步时间戳 + 增量同步任务 + 撤销后缓存失效），并把越权抽查做成发布流水线里的常驻门禁而非一次性测试。
> - 延伸阅读：[rag-handbook §6.5 权限与多租户（企业场景的生死线）](../rag-handbook/RAG搭建文档.md)｜[security-handbook §4.5 数据出境与多区域部署](../security-handbook/AI应用安全手册.md)｜[FDE 转行手册 §8.6 高频面试题清单（题 6 即本题）](../fde-handbook/FDE转行手册.md)

> **Q083. 设计一个客服 agent：工具调用、人工升级（HITL）怎么安排？**（难度：中 ｜ 频次：高）
> - 考察点：能否画出"参数提取→意图路由→分支处理→聚合回复"的完整链路，工具权限分级、HITL 插点有判据而不是"到处插"。
> - 参考回答：
>   - 先澄清：渠道与日均会话量、问题分布（问答为主还是办事为主）、SLA（响应时长）、错误代价（退款/赔付上限）——这决定做"问答型"还是"流程型"，以及工具能开放到哪一级。
>   - 参考架构直接用单工作流模式（ADP 3.3 全链路）：开始 → 参数提取（订单号/商品/诉求/情绪等级，情绪收敛为"平静、着急、愤怒、无法判断"四值枚举）→ 意图识别路由到物流/支付退款/退换货/其他四个分支 → 各分支挂知识库检索（售后政策+标准话术）→ 变量聚合 → 最终客服回复生成 → 回复节点；客服流程可枚举、错误代价高，正是 workflow 六问判据的典型命中——写死控制流保确定性。
>   - 工具调用"只读优先"：查订单、查物流、查余额类只读工具直接给模型；写操作（退款、改地址、补发）默认不给模型——走参数校验+规则引擎或人工审批；动作分级（只读/写/破坏性三级）是 OWASP LLM06"过度代理"的反面教材（security §3.1 最小权限四落点：工具面收窄、动作分级、资源边界、出口控制）。
>   - HITL 插点判据三条（tuning §4.6）：①置信度出口——判据输出 needs_human 或置信度低于阈值转人工，第一优先插点；②高风险动作前——退款审批、超额补偿、对外承诺；③不可逆操作前——幂等键救不回来的写入/删除/发送。反模式要主动点破：把"不确定就转人工"写成装饰性提示词（模型从不触发）、每一步都插（人工队列堆积、自动化归零）、高风险动作后置审核（审核通过时损失已发生）。
>   - 转人工的体验设计：交接包带完整上下文（提取的参数、已试方案、情绪等级），坐席工作台能看到 agent 的处理轨迹；转人工率与一次性解决率是核心运营指标。
>   - 可靠性工程：幂等键防重复退款（workflow §5.3 重试三要素）、每个写操作有审计日志与回滚路径、超时与重试预算按分支分别配置。
>   - 评测与发布：意图路由用枚举判据（四分支命中准确率）、端到端用测试集验证（ADP 3.3 Step 14-15：先单节点调试再全流程调试，发布填版本说明，发布后从用户侧再测一次）。
>   - 成本抓手：高频问题用问答对与同义词前置拦截（ADP 3.2 手法），生成模型按分支分档（物流查询走 Haiku 4.5 $1/$5，退款策略走 Sonnet 5 $2/$10），稳定知识库前缀吃提示缓存（Anthropic 缓存读 0.1×）。
>   - 失败模式：意图误路由（枚举收敛+兜底分支接住）、工具幻觉调用（工具面收窄+参数 schema 校验）、死循环（轮次与 token 预算上限）、情绪升级漏识别（情绪枚举要作为路由条件而非摆设）。
> - 追问与陷阱：
>   - 追问：为什么不用一个自由 agent 让模型自己决定调什么工具？常见错误："agent 更智能"——客服错误代价高、路径可枚举，写死工作流保确定性；自由度留给"其他"分支里的辅助问答。
>   - 追问：怎么衡量该不该扩大自动化覆盖？常见错误：只看转人工率下降——要同时看人工接管后的二次修改率与投诉率，否则只是"把不满从电话挪到工单"。
> - 加分项：能引 ADP 工作流"自动判断必填信息是否完整、缺了自动生成反问话术"的内置澄清机制（多轮澄清不破坏流程确定性），或比较五家引擎的 HITL 原语写法（workflow §3.4）。
> - 延伸阅读：[ADP 3.3 单工作流模式实战：客服助手](../fde-handbook/tencent-adp-fde-course/lessons/3.3_单工作流模式实战：客服助手.md)｜[tuning-handbook §4.6 HITL 插点位置：插在"低置信度出口"](../tuning-handbook/Agent调优手册.md)｜[workflow-handbook §5.3 幂等与重试：重试三要素 + 引擎默认值对照](../workflow-handbook/Agent工作流编排手册.md)

> **Q084. 设计一个数据分析 agent：让模型安全地查库出报表？**（难度：中 ｜ 频次：高）
> - 考察点：能否设计"生成≠执行"的安全链路，说清权限、校验、沙箱各落在哪一层，以及数字溯源纪律。
> - 参考回答：
>   - 先澄清：库的规模与 schema 复杂度（几百张还是几千张表）、账号能开什么权限、报表口径谁定义、并发与成本上限——schema 太大时"全塞进 prompt"不可行，这决定要不要做 schema 检索。
>   - 参考架构三段：NL→SQL 生成 → 静态校验 → 受控执行与结果解读。生成侧先做 schema 检索——按问题召回相关表/列的 DDL 与口径说明，用嵌入+BM25+重排的混合检索落成服务（python-handbook §5 的 RAG 工具链正是这条），只把相关表进上下文，配 few-shot 口径示例。
>   - 安全世界用最小权限四落点（security §3.1）对号入座：专用只读账号（数据库层 deny-by-default，根本不授予 UPDATE/DDL 权限）、资源边界（强制 LIMIT 行数、查询超时、并发上限、预算熔断）、出口控制（结果只回写白名单位置）、工具面收窄（只暴露"执行已校验 SQL"一个工具）。
>   - SQL 出模型后必须过静态校验再执行：解析器断言只读（拦 DML/DDL）、表名列名白名单匹配（防幻觉列）、schema 绑定校验列类型与聚合合法性——把"让模型写命令"改成"让模型填参数"（security §5.4 结构化约束：最被低估的护栏）。
>   - 执行沙箱化：连接池限流、慢查询 kill、行数截断后把"已截断"显式回传给模型，防止它拿部分结果编造总数；分析库与生产库物理分离（只读副本/数仓）。
>   - 结果解读纪律：数字只能来自查询结果（查询结果以结构化形式回填，禁止模型"补"数字），每个结论带可回查的 SQL 与结果集引用，图表与结论文本分开生成。
>   - 复杂分析可用 orchestrator-worker（编排者-工人）扇出：多表/多维问题拆成独立子查询并行执行、各自回传压缩结果，编排者汇总去重（multiagent §2.2）——但先过"真的需要多 agent 吗"的判据，单 agent 能跑就别上。
>   - 评测：建 text-to-SQL 评测集（问题+期望结果集），以执行准确率（结果集匹配）为主判据——可验证 reward 优先（eval §2.3）；口径陷阱（去重、时区、退款口径）靠 few-shot 与口径字典治理，用户纠正过的错 SQL 回流评测集。
>   - 上线策略：高敏感操作（导出、对外报表）HITL 确认，全量 SQL 审计留痕；灰度可先上"只出 SQL 不执行"的 copilot 模式积累信任。
>   - 失败模式：幻觉列名/表名、聚合口径错（去重与时区）、JOIN 放大行数、慢查询拖垮生产库、把 LLM 的"解释"当查询结果（数字必须来自数据）。
> - 追问与陷阱：
>   - 追问：为什么不直接给模型一个 execute_sql 工具让它自由查？常见错误："模型够聪明不会写坏 SQL"——权限与校验是架构属性不是模型属性，一次 DROP 或全表扫描的代价不可接受；只读账号是底线不是优化。
>   - 追问：几千张表的 schema 放不下上下文怎么办？常见错误：只放表名列表——用 schema RAG（检索增强生成）召回 + 列级注释 + 值域样例，召回错了评测集会暴露。
> - 加分项：能设计"口径字典+评测集覆盖口径陷阱"的组合拳，或指出分析场景的批处理红利（夜间批量报表走批处理 -50%）与并发节流（分析查询排队执行，别与在线业务抢连接）。
> - 延伸阅读：[security-handbook §3.1 最小权限在 agent 上的四个落点](../security-handbook/AI应用安全手册.md)｜[multiagent-handbook §2.2 orchestrator-worker（编排者-工人）](../multiagent-handbook/Multi-Agent协同手册.md)｜[python-handbook §5 RAG 工具链 Python 侧](../python-handbook/Python大模型应用开发手册.md)

> **Q085. 设计一个高并发 LLM 网关：限流、缓存、路由、降级怎么安排？**（难度：高 ｜ 频次：中）
> - 考察点：限流/缓存/路由/降级四大件各自的机制、判据与数字，有没有"每层都要监控、路由器也要过评测"的工程观。
> - 参考回答：
>   - 先澄清：峰值 QPS 与倍数、租户与计费模型、TTFT（time to first token，首字延迟）目标、成本红线——网关的目标是"稳、省、快"，优先级必须先问清。
>   - 限流做两级加保护：账号级配额（token/分钟与请求/分钟，令牌桶）+ 全局并发上限 + 上游保护；参照 OpenClaw 网关的六条独立限流设计（认证失败 10 次/60s 锁 5 分钟、控制面写 RPC 30 req/60s per method、ACP 会话创建 120/10s、Gateway 重启 30s 冷却等），要点是按"方法+身份+来源"多维分桶而不是一刀切；排队语义要可选（OpenClaw 四种队列模式：steer 注入当前运行/followup 排队/collect 合并/interrupt 打断），写操作默认串行防脏写。
>   - 缓存做三档：精确缓存（同请求 hash 直接回）、语义缓存（embedding 相似度命中，阈值保守+按租户分桶）、provider 前缀缓存（稳定前缀放最前：Anthropic 缓存读 0.1×/写 1.25×、OpenAI 缓存输入 10%、DeepSeek 缓存命中≈2%）——缓存是成本第一杠杆，命中率要当一级指标监控，且必须可失效（知识库更新/模型升级）。
>   - 路由按任务难度分档（tuning §6.5）：快问题走 Haiku 4.5（$1/$5）或 gpt-5-nano（$0.05/$0.40），重任务走旗舰档；推理模型与快思考价差 7-35×，别用推理模型答寒暄；级联降级"先小后大"要有明确升级判据（置信度不足或失败才升级，不是"感觉不行"）；路由器自己也要过评测集——路由错了等于把错误率做进架构，每档模型的 pass 率与成本并排监控。
>   - 降级预案：主模型超时/429 切备用 provider（协议兼容层如 litellm）、排队+背压（宁可慢不可错）、非核心功能可关（降级为短答案或缓存答案）；超时预算逐跳显式设置（参照 OpenClaw：模型 idle watchdog 云 120s/自托管 300s、agent.wait 30s、整体上限写进配置）。
>   - 可观测：每请求记录 token 用量并把成本归因到 trace（账单能对到每一次调用）、缓存命中率/各档模型通过率/上游错误率大盘、预算熔断（单租户单日美元上限触发自动降级，eval §8 有成本核算+熔断的最小实现）。
>   - 高并发工程细节：流式直通不缓冲（SSE 逐帧转发）、重试加抖动与熔断防上游 429 雪崩、幂等键防重复计费、长请求与短请求分队列防队头阻塞。
>   - 一致性围栏（多渠道 agent 网关必答）：同一会话并发请求参照 OpenClaw 写者围栏——事务内校验 expectedWriterRunId，被取代的请求提交不了脏状态；双层 lane 串行化（每会话 lane 套全局 lane）把"同会话被连续消息轰炸"当一等问题处理。
>   - 失败模式：重试风暴放大上游故障、语义缓存串答案（跨租户/跨权限）、路由把难题分给小模型且无人发现（通过率下滑没告警）、成本失控（无归因无熔断）。
> - 追问与陷阱：
>   - 追问：限流限 QPS 还是限 token？常见错误：只限 QPS——LLM 的成本与负载都在 token，一个长请求等于百个短请求的负载，两级都要限。
>   - 追问：语义缓存返回旧答案谁负责？常见错误：只管快——缓存要带 TTL 与失效键（知识库更新、模型升级可失效），并按租户/权限分桶，否则缓存本身就是越权泄漏面。
> - 加分项：能给出 TTFT 分解方法论（tuning §7.5：TTFT/生成速率/工具往返三笔账，OpenAI 缓存命中实测 TTFT 最高 -80%，Anthropic Opus 5.5 Fast 档 2× 价格换至多 2.5× 速度），强调"先测各分量再选杠杆，平均错方是最常见的浪费"；或引 OpenCode 把模型目录外置到 models.dev 的做法——模型信息当配置管不当代码管。
> - 延伸阅读：[tuning-handbook §7 成本与延迟工程](../tuning-handbook/Agent调优手册.md)｜[tuning-handbook §6.5 模型路由与级联降级](../tuning-handbook/Agent调优手册.md)｜[05-openclaw 架构拆解 §7.5 secrets、限流与审计](../05-openclaw/架构拆解.md)

> **Q086. 设计一个长文档处理系统：1000 页 PDF 提取结构化数据？**（难度：高 ｜ 频次：中）
> - 考察点：解析-切分-分段抽取-合并-校验的 map-reduce（分治并行）主线，以及长窗口与成本预算的现实取舍。
> - 参考回答：
>   - 先澄清：版式复杂度（纯文本/表格/扫描件比例）、目标 schema（抽哪些字段、嵌套多深）、准确率要求与验收方式（字段级 F1 还是抽样人审）、一次性任务还是持续管线——投入量级由这四个答案决定。
>   - 解析层决定上限：版面分析（标题层级/双栏/页眉页脚剔除）+ 表格还原（跨页表格拼接、表头随行走——rag-handbook §2.2 表格按行切）+ 扫描件 OCR；解析产出必须带页码元数据，后续字段可定位、可回查原文。
>   - 切分按结构不按字数：结构感知切分（按章节/条款边界），父子结构（小块检索、大块喂模型）在本场景同样适用——"段落级抽取+章节级上下文"。
>   - 主线用 map-reduce 并行（workflow §2.3 parallelization 的 sectioning 变体）：每段独立抽取（同一 schema、结构化输出、并行执行）→ reduce 合并（跨段实体对齐、去重、冲突标注）；部分失败语义显式声明（容忍 N 段失败、只重跑失败段，不全量重来）。
>   - 长窗口 vs 分段的选择题要有数字：Gemini 3.8-flash 有 1M 窗口（$0.75/$3.75）可大块处理省编排，但注意 Gemini 3.1-pro 分层计价 >200k 输入 $4/M（输出 $12→$18）——长上下文不是免费的，是翻倍的；且整本塞入损失"逐段置信度"与并发重跑能力。中档模型（Sonnet 5 $2/$10）分段 map-reduce 通常更稳更省。
>   - 若用 agent 式长会话跑全书，上下文按三层预算管（context §2.1，ZCode 样本）：microcompact（阈值 0.9，旧工具结果换占位符、保留最近 5 条）→ auto compact（200k 窗口、输出预留 21k + buffer 13k，摘要替换历史）→ reactive compact（超窗后补救，最贵）——梯度共识：剪枝先于摘要，宁可新开窗口也不无限摘要。
>   - 截断三抓手（tuning §6.4）：token 估算中文必须用 tokenizer 实算（字符/4 对中文显著低估）、压缩触发点留缓冲（触发线贴窗口上限=一次超窗错误就补救）、截断从后往前剪保住缓存前缀（Anthropic 缓存读 0.1× 的前提是前缀稳定）。
>   - 校验层：schema 校验（字段类型/枚举/必填）、跨字段一致性（金额合计 vs 明细）、跨段冲突报告、低置信字段抽样人工复核；所有字段带页码引用可回查。
>   - 成本抓手：全量跑批处理 API 一律 -50%、小模型预筛（gpt-5-nano $0.05/$0.40 级）分拣"含表格的页"再升级重模型、公共指令前缀吃提示缓存。
>   - 失败模式：跨页表格断行断列、页眉页脚与水印噪声混进字段、合并阶段实体对齐错（同名不同实体）、长输出截断导致 JSON 残缺（分块输出+校验重试）。
> - 追问与陷阱：
>   - 追问：为什么不全用 1M 窗口一次抽取？常见错误："窗口大=能力强"——计价翻倍、长输出截断风险、逐段校验与并发重跑全没了；大窗口适合理解性问题，结构化抽取更适合确定性分段管线。
>   - 追问：扫描件准确率上不去怎么办？常见错误：先换更强的抽取模型——先治解析（OCR 引擎与版面模型换型、按页质量分诊），上游 garbage 下游无解。
> - 加分项：能设计"页级质量分诊"（OCR 置信度低的页走重模型或人工）与"版本增量重抽"（文档更新只重抽变化段并 diff 回归），或引用 voting（投票）变体对关键字段多次采样取多数降漏检。
> - 延伸阅读：[rag-handbook §2.2 切分（Chunking）规范](../rag-handbook/RAG搭建文档.md)｜[workflow-handbook §2.3 parallelization（并行化）：扇出聚合](../workflow-handbook/Agent工作流编排手册.md)｜[tuning-handbook §6.4 上下文窗口与截断策略](../tuning-handbook/Agent调优手册.md)

> **Q087. 设计跨会话的 agent 记忆系统，怎么做个性化？**（难度：中 ｜ 频次：中）
> - 考察点：记忆的类型学分层、写入与召回策略、遗忘与污染防护——有没有"记忆是高价值个人信息库"的安全意识。
> - 参考回答：
>   - 先澄清：个性化的对象（用户画像/稳定事实/偏好/待办）、记忆跨什么边界（同产品多会话还是跨渠道）、合规要求（用户能否查看与删除——GDPR 被遗忘权）。
>   - 类型学用四分法（context §4.1）：语义记忆（稳定事实："用户的部署目标是 X"）、情景记忆（事件轨迹："上周三那次部署失败因为…"）、程序记忆（指令与偏好：AGENTS.md/CLAUDE.md 类）、前瞻记忆（"周五提醒我"）——第四类最容易漏，且证据很硬：LongMemEval 证明"写了什么比怎么索引更重要"，PrefEval（ICLR 2025）证明偏好只靠"在上下文里放着"几轮后就失效。
>   - 前瞻记忆的关键设计（context §4.1）："记得做"是触发器问题不是检索问题——时间型编译成 cron、事件型进 SQLite intent 表（关键词/嵌入触发字段+过期+冷却+开火预算）；OpenClaw 明确说"把意图存成记忆文件里的一句话是最不可靠的设计"（TriggerBench 显示前瞻记忆随上下文变长急剧退化且模型会不可信地自发取消）。
>   - 分层信任模型参照 OpenClaw 五层 tier（context §4.2）：Instructions（仅人类写、会话开始总是注入）/ Curated core（整理后的 MEMORY.md/USER.md，受预算注入）/ Episodic（日记与转录，从不自动注入、只能显式搜索）/ Prospective（触发器命中才进）/ Review（供人审）——最重要边界：未 vet 的内容无论检索分多高都结构性禁止自动进 prompt，"这是安全性质，不是调优选择"。
>   - 写入策略三问（context §4.3）：何时存（会话结束批量抽取 or 实时抽取）、存什么（原子事实条目，带来源与时间戳）、冲突怎么办（新事实覆盖旧事实要留版本；Graphiti 用 bi-temporal 双时间线在数据库层面回答"矛盾事实该信哪个"）。
>   - 召回策略：按相关性+新近度+重要性打分、注入条目有预算上限；两条 lane 成本分离——高频小记忆走稳定前缀吃缓存（Anthropic 缓存读 0.1×），长尾记忆显式搜索。
>   - 框架选型有当日谱系（context §5，2026-09-27 实抓）：mem0（66.1k star，抽取-检索流水线）、Graphiti（31.2k，时序知识图谱）、MemOS（11.6k）、Letta 已转型 letta-code——归档/转型扫描是选型纪律；自研起步也成立：MEMORY.md + 向量库 + 触发表就能覆盖第一版。
>   - 安全与卫生三条（context §4.2）：session-kind gating（cron/心跳/子代理会话的产物永远不具晋升资格）、recall-loop prevention（从记忆注入的内容被结构性标记、永不再次被提取为新记忆——"一个事实被召回一百次仍是一个事实"）、taint 传播（工具声明为网络来源后本轮消息被污染标记）；记忆必须按用户/租户硬隔离并进越权测试——记忆串用户是最严重事故。
>   - 评测分开评两条（context §6.1）：回忆得起（LongMemEval 类）与遵守得住（PrefEval 类）；记忆污染是注入攻击的持久化形态（context §6.2），红队用例要包含"诱导写坏记忆"。
>   - 失败模式：过时记忆误导（无 TTL 无覆盖）、错误记忆固化（无审计与编辑入口）、隐私泄漏（记忆是高价值个人信息库，删除要覆盖全部副本）、个性化过头（过时偏好被反复执行）。
> - 追问与陷阱：
>   - 追问：记忆放 RAG 向量库里行不行？常见错误："都是检索所以一样"——RAG 管共享知识（可重获取、无个人属性），记忆管"这个用户的事实与偏好"（私有、有时序、有冲突合并），生命周期与信任层级都不同；OpenClaw 的 curated/episodic 边界就是为此设的。
>   - 追问：个性化做过头是什么体验？常见错误：记忆越多越好——历史塞满开头拖慢 TTFT 且过时偏好干扰当下；要配遗忘与衰减机制（context §4.5）。
> - 加分项：能讲 Graphiti 的 bi-temporal（事实发生时间 vs 系统记录时间）如何回答"用户上个月说 A、这周改口 B，现在信哪个"；或背出 OpenClaw 三条卫生规则术语，并指出"把意图从模型手里编译出去"这一设计哲学。
> - 延伸阅读：[context-handbook §4.1 记忆类型学：四分法与实现映射](../context-handbook/Context与记忆系统手册.md)｜[context-handbook §4.2 OpenClaw 的五层 tier 模型](../context-handbook/Context与记忆系统手册.md)｜[context-handbook §5 主流记忆框架横评](../context-handbook/Context与记忆系统手册.md)

> **Q088. 设计一个内容安全 guardrails 层，怎么分层？**（难度：中 ｜ 频次：中）
> - 考察点：分层防御的位置感（输入/模型/输出/工具侧）与"安全是双轴指标"的评测观，避免"有检测器=有防线"的错觉。
> - 参考回答：
>   - 先立威胁模型再谈护栏：agent 场景的第一公理失效——指令与数据没有边界（security §1）；lethal trifecta（致命三要素）三条腿齐了才有真风险，护栏设计的目标就是给"私有数据 × 不可信内容 × 出口"插断点。
>   - 分层架构四段：输入侧（prompt injection 检测、PII（Personally Identifiable Information，个人身份信息）识别脱敏、越权请求分类）→ 模型侧（选安全对齐模型、系统提示词边界声明）→ 输出侧（内容分类器、schema 校验、引用核验）→ 工具侧（动作闸门：参数 schema 校验、危险操作 deny-by-default+审批）。
>   - 结构化约束是最被低估的护栏（security §5.4）：让输出过 schema 校验同时是质量工程和安全工程——防输出被直接拼进 shell/SQL/HTML（OWASP LLM05）、防工具参数注入（入参在 harness 侧二次校验，ZCode 双轨 schema 的做法）、把"让模型写命令"改成"让模型填参数"。
>   - 注入检测器的三条工程纪律（security §5.3 原文）：①检测器输出当信号不当裁决——报警走降级（收网络权、切保守模型、人工复核），"未检出"不等于放行；②检测器自己也要过评测集（对正常业务流量测误杀率，误杀样本回流回归集）；③结构性防御优先——花在 provenance/权限/出口上的工程回报远高于堆检测模型（公开评测结论：对已知模板有效、对自适应攻击衰减快、误杀率随攻击面扩大上升）。
>   - 框架选型报当日横评（security §5.2）：NeMo Guardrails（7.2k star，对话流程化护栏）适合对话产品、Guardrails AI（7.5k）适合 schema 校验、presidio（11.1k）PII 识别不论其他都可上、llm-guard 已归档不进新依赖；分类器（Llama Guard/Prompt Guard）自托管做粗筛与遥测。
>   - 评测必须双轴（security §6.4）：ASR（Attack Success Rate，攻击成功率）↓ 与 overrefusal（过度拒答）↓ 同看——只压 ASR 会把产品压成"什么都拒"；再加护栏误杀率与 MTTD（从注入到达上下文到被降级的时延）；判攻击成功用状态断言（文件被读/请求出站），不信模型自述。
>   - 红队进 CI：攻击用例集（多语言、编码变体、间接注入）常驻回归，每次护栏或模型变更重跑；自动化红队工具定期扫新攻击面。
>   - 延迟与成本预算：护栏全串行会叠加 TTFT——重分类器并行跑或异步抽检，分级响应（高置信放行、可疑降级、高危拦停）；护栏模型用小档（Haiku 4.5 $1/$5 级）控成本。
>   - 失败模式：护栏形同虚设（只在 prompt 里写"不要作恶"）、误杀率失控伤业务、只测英文单轮攻击、护栏升级无回归（新护栏挡住正常流量没人知道）。
> - 追问与陷阱：
>   - 追问：加了护栏是不是就安全了？常见错误："有检测器=有防线"——自适应攻击衰减快，必须配权限与出口的结构性防御；EchoLeak（CVE-2025-32711，CVSS 9.3）是零点击链路，单点检测拦不住。
>   - 追问：overrefusal 怎么量？常见错误：没有正常流量基准——用 XSTest 类样本测错误拒绝率，并把业务里"看起来像攻击的正常请求"也放进回归集。
> - 加分项：能给出动作闸门的最小实现思路（security §6.5 的 ActionGate：动作级白名单+结构化参数+审批绑定执行要素，红队用例进 CI），或对照 OWASP LLM Top 10（2025 版）逐条讲防线位置。
> - 延伸阅读：[security-handbook §5.2 护栏与安全工具横评](../security-handbook/AI应用安全手册.md)｜[security-handbook §5.3 注入检测器的真实水位](../security-handbook/AI应用安全手册.md)｜[security-handbook §6.4 安全指标：双轴 + 归因](../security-handbook/AI应用安全手册.md)

> **Q089. 客户要求私有化部署/数据不出域，架构怎么调整？**（难度：中 ｜ 频次：低）
> - 考察点：知道私有化改的是哪几层（模型/数据/安全/运维）、成本怎么换算法，以及能力落差如何诚实管理。
> - 参考回答：
>   - 先澄清"数据不出域"的准确范围：数据不出域（检索与日志本地、模型仍用云）vs 模型也私有（推理本地）vs 完全离线（连更新都不进）——三档方案成本差一个量级；再问 GPU 预算、并发与延迟要求，这决定模型档位。
>   - 模型层调整：外部 API 换本地推理栈（python-handbook §6 谱系：vLLM 0.30.0、92.8k star 做生产吞吐——PagedAttention 高并发；Ollama v0.34.4、181.8k 做开发机；llama-cpp-python 0.3.35 做 CPU/进程内 GGUF 分发；transformers 是模型定义层）；按显存与并发倒推量化档位，推理服务参数（并发/上下文长度/KV cache）要压测。
>   - 数据层调整：向量库、embedding 模型、OCR 全部本地化；最容易漏的迁移项——embedding 换本地后维度与语义空间都变了，历史索引必须全量重建，不能增量混用。
>   - 安全层调整：审计日志留域内、PII 脱敏在本地完成、密钥本地化（SecretRef 思想：agent 不看到值地取凭据）；若保留部分云 API，按 security §4.5 做数据出境字段清单化（哪些字段允许进 prompt=哪些字段出境）与出域审批。
>   - 能力落差逐项找替代：云端才有的联网搜索、多模态大模型、托管 reranker——本地替代（如 bge-reranker 级交叉编码器）或功能降级；"私有化版 vs API 版"的效果差距要提前用评测集量化，写进方案给客户预期，不要上线后才暴露。
>   - 成本账换算法（工具箱 §7 思路）：从"按 token 付费"换成"GPU 折旧+并发利用率"——云上便宜档（gpt-5-nano $0.05/$0.40、DeepSeek flash $0.30/$1.20）意味着低用量客户私有化未必更省，按客户量级算盈亏平衡点；开发调试消耗约为稳态 2-4 倍在私有化同样成立。
>   - 运维面新增：模型版本升级流程（评测回归后灰度）、显存与吞吐监控、模型权重供应链安全（来源校验、哈希核对）。
>   - 失败模式：并发一上来吞吐崩（vLLM 参数没调、显存 OOM）、长上下文场景被窗口卡死、私有化后评测缺位效果悄悄劣化、以为私有化=不用做权限隔离（企业内部同样有部门级租户隔离）。
> - 追问与陷阱：
>   - 追问：客户只有 CPU 服务器怎么办？常见错误：硬上大模型——降档到小模型+量化（GGUF/llama.cpp 路线）或"本地小模型粗筛+疑难人工"，并诚实告知能力边界。
>   - 追问：私有化之后还要做评测吗？常见错误："模型定了就稳定了"——语料、切分、提示词、模型升级都会漂移，回归评测照常执行。
> - 加分项：能给出中间形态设计（脱敏后出域/私有化网关+云推理混合）与各自审计口径，或给出 GPU 并发估算方法（并发数 × 上下文长度 × KV cache 显存占用）来回答"这台机器能撑多少用户"。
> - 延伸阅读：[python-handbook §6 本地推理与模型服务](../python-handbook/Python大模型应用开发手册.md)｜[security-handbook §4.5 数据出境与多区域部署](../security-handbook/AI应用安全手册.md)｜[FDE 实战工具箱 §7 成本与报价思路](../fde-handbook/FDE实战工具箱.md)

> **Q090. 给银行设计 <100ms 实时风控，LLM 用在哪一层？**（难度：中 ｜ 频次：中）
> - 考察点：能否守住"<100ms 是硬约束所以 LLM 不进主路径"的架构判断，并为 LLM 找到正确的旁路价值——考的是克制。
> - 参考回答：
>   - 先算延迟账定调：LLM 的 TTFT 即使缓存命中也在百毫秒级、完整生成秒级、吞吐与延迟分布不可控——<100ms 的主路径放不下 LLM，这是物理与成本约束，不是模型能力问题（tuning §7.5 延迟三笔账：TTFT/生成速率/工具往返）。
>   - 主路径构成（毫秒级、延迟确定）：规则引擎（黑名单/阈值/频次）+ 轻量 ML 模型（GBDT/嵌入相似度）+ 特征服务（预计算特征毫秒级取回）——可解释、可回滚、可回测，满足监管对决策依据的要求。
>   - LLM 位置一：案件调查旁路——对规则/模型命中的告警（每天千级而非每笔交易），LLM 汇总交易序列、设备与历史行为生成调查报告，把调查员人时压缩一个量级；异步执行，延迟无关紧要，可用批处理 -50% 控成本。
>   - LLM 位置二：规则与策略生产——离线用 LLM 从案例文本归纳新型欺诈模式的候选规则，人工审核+影子流量验证后才进规则库；LLM 的产出物是"候选"，不是"决策"。
>   - LLM 位置三：解释与文书——被拦截交易的"为什么"解释文本、申诉处理辅助、反洗钱合规报告草稿，全部异步生成、人工签发。
>   - 为什么不硬塞主路径用 workflow 六问判据回答（§1.2）：错误代价高（误杀与漏放都有资损与监管责任）、确定性是硬要求、结果要可程序验收——六问全指向写死的控制流；LLM 概率性输出与长尾延迟两条都不合格。
>   - 若业务坚持要语义理解进主路径：把语义任务离线预计算——如"交易摘要文本"嵌入后进向量特征库，主路径查向量（毫秒级）而不是现场调 LLM；或把 LLM 的判断蒸馏成小模型做实时打分。
>   - 评测与合规：主路径模型有完整离线回测（历史欺诈集上的误杀率/漏报率）与审批留痕；LLM 旁路产出也要评测（调查报告的事实准确率）并审计；SLA 用 P99 口径验证而不是平均值。
>   - 失败模式：把 LLM 放主路径导致 P99 超标、模型输出不可解释过不了监管、旁路报告被直接当结论（无人工核）、每笔交易都调 LLM 的成本灾难。
> - 追问与陷阱：
>   - 追问：风控规则库能不能让 LLM 自动更新上线？常见错误："挖掘+上线全自动"——规则变更必须人工审批+影子模式（shadow mode）验证后生效，LLM 只到"候选"为止。
>   - 追问：一次误杀怎么向监管解释？常见错误：拿 LLM 生成的文本当解释——主路径必须输出规则+评分的可解释依据，LLM 只辅助人类撰写文书。
> - 加分项：能给出延迟预算分配示例（特征取回 10ms + 规则 5ms + 模型推理 30ms + 网络/排队余量），并指出 100ms 是端到端 SLA、要留排队与抖动余量——这类"数字抓手"是本题的分水岭。

> **Q091. prompt 的版本管理与发布流程怎么设计？**（难度：中 ｜ 频次：低）
> - 考察点：能否把 prompt（提示词）当生产代码管——版本化、回归门禁、灰度、配置化热更新、回滚五件事齐不齐。
> - 参考回答：
>   - 心智模型先立住：prompt 是生产代码——它直接决定输出行为，改动必须有版本、有评审、有回归，"就改了一句话"也要走流程。
>   - 版本化：prompt 模板进版本库或配置中心（带版本号），与代码版本绑定；模板参数（变量槽）与正文分离；每次变更记录"改了什么、为什么、预期影响哪类 case"。
>   - 每版必过回归评测，方法论即 tuning §1.1 闭环五步：定位瓶颈 → 假设 → 单变量变更 → 回归评测 → 固化——一次只改一个变量，否则归因不了；固定评测集上新旧版本对比，通过率不降才可发布。
>   - 灰度发布套三时机框架（eval §2.2）：离线是安全网（发布前评测集准入）、在线是体温计（5%→25%→100% 流量切分，看通过率/人工纠正率/用户反馈）、回放是传送带（生产 trace 回流成数据集，新版本先在昨日真实流量上回放再放量）。
>   - "发布 ≠ 生效"三条纪律（workflow §6.5，源自 ADP 3.3 Step 15）：①发布要确认变更项（模板、变量、模型配置逐项列出）；②发布要写版本说明（V1.0 范式："完成 XX 搭建。新增 A/B/C，并完成测试集验证"）；③发布后必须从用户侧再测一次——客户端缓存、多入口都可能让用户拿到旧版。
>   - 配置化与热更新：prompt 放配置中心而非编译进代码，改 prompt 不发版；但热更新要配"当前生效版本可查询+生效审计"，多实例滚动生效时间要可观测。
>   - 回滚预案：配置中心一键切回上一版本且回滚也走审计；每个版本的评测报告留档，作为"该版本何时可用"的证据。
>   - 多 prompt 治理：系统提示词/分支提示词/护栏提示词分开版本化；组合矩阵用覆盖矩阵抽样回归，不全量组合爆炸；输出契约变更=行为变更，评测集与版本指纹要跟着动（workflow §3.3 规范六）。
>   - 失败模式：线上手改无记录（配置漂移）、评测集过拟合（prompt 背题）、回滚后发现评测集也改过（版本不配套）、"谁都能改线上 prompt"（生效入口没收敛）。
> - 追问与陷阱：
>   - 追问：prompt A/B 测试和普通回归有什么区别？常见错误：看均值就下结论——LLM 输出方差大，要固定采样参数（temperature/seed）并关注分布与最差 case，不只看均值。
>   - 追问：谁能改线上 prompt？常见错误：谁都能改——配置中心要有权限与评审流，能生效的入口数量要收敛，否则版本管理形同虚设。
> - 加分项：能引 promptfoo 类 diff 工具做"版本对比门禁"（tuning §8.2 把门禁做成产品的思路），或指出评测集本身也要版本管理（eval §4.4：把评测集当代码管）——评测集漂移是 prompt 回归失效的头号原因。
> - 延伸阅读：[tuning-handbook §1.1 闭环五步：定位瓶颈 → 假设 → 单变量变更 → 回归评测 → 固化](../tuning-handbook/Agent调优手册.md)｜[workflow-handbook §6.5 版本管理与灰度发布：发布 ≠ 生效](../workflow-handbook/Agent工作流编排手册.md)｜[eval-handbook §2.2 三时机：离线 / 在线 / 灰度回放](../eval-handbook/Agent评测与质量工程手册.md)

> **Q092. 流式输出的前后端链路怎么设计？**（难度：中 ｜ 频次：低）
> - 考察点：SSE 机制细节、TTFT 优化与"流式之外"的工程点（取消、断线、结构化输出），避免只会说"用流式接口"。
> - 参考回答：
>   - 协议选型：LLM 流式的工业标准是 SSE（Server-Sent Events，服务器推送事件）——单向 HTTP 长连接，帧格式是硬约定：每帧以 `data: ` 开头、以空行结尾（python-handbook §7.2）；前端用 EventSource 或 fetch 读流；WebSocket 只在需要双向（实时语音、协作）时才上。
>   - 全链路逐跳配置：模型 API 流式 → 服务端 async 客户端逐 token 转发（FastAPI StreamingResponse / sse-starlette）→ 网关与反向代理禁缓冲（Nginx `proxy_buffering off`、`X-Accel-Buffering: no`）、空闲心跳（注释帧防 LB 切断）、超时按长生成配置。
>   - TTFT 是体验核心指标（tuning §7.5 三笔账）：TTFT——缓存命中（OpenAI 实测最高 -80%）、稳定前缀缩短、就近路由；生成速率——输出长度约束、小模型、Fast 档（Anthropic Opus 5.5：2× 价格换至多 2.5× 速度）；工具往返——无依赖工具并行、预取；先测各分量再选杠杆。
>   - 前端渲染：增量 markdown 渲染（未闭合语法容错）、打字机节流（按 rAF 合帧）、代码块高亮延迟到闭合后再做，避免每帧重排。
>   - 取消与省钱：用户点停要级联 abort（前端 abort → 网关 → 上游 provider 中止生成），中断部分的计费与算力都省下来；abort 前已生成内容要落盘供续接展示。
>   - 断线重连：SSE 原生 Last-Event-ID 只覆盖短断线；长生成续传用"生成任务 ID + 结果落盘 + 重放/轮询"兜底——服务端可重放已产出 token，不必从头生成。
>   - 结构化输出的流式难题：JSON 流式无法边收边完整校验——改为"分段字段流式"（先流标题再流正文各字段），或前端用增量 JSON 解析器容错渲染；服务端最终仍要做完整 schema 校验，流式只是展示层优化。
>   - 可观测：TTFT/每秒 token 数/工具往返分别埋点；流式也别丢 usage——最后一帧带 token 统计供计费与成本归因。
>   - 失败模式：某一层缓冲导致"转圈 10 秒一次性吐完"（最常见是 Nginx 缓存/压缩模块没关）、长连接被 LB 空闲超时切断（无心跳）、错误发生在流中间（先发错误帧再关流，前端能提示而不是静默截断）。
> - 追问与陷阱：
>   - 追问：为什么不用 WebSocket？常见错误："双向一定更好"——LLM 场景以请求-响应单向为主，SSE 更简单、过代理更友好、自带重连；有双向实时需求再上 WS。
>   - 追问：已经流式了，为什么用户还觉得慢？常见错误：只压总时长——用户感知由 TTFT 主导，先推"正在检索…"等进度事件帧比压模型延迟更有效。
> - 加分项：能指出"流被截断时的收尾判据不能只信 stop_reason"（anon-kode 以内容块里有没有 tool_use 为准的源码教训），或给出 POC 形态：Gradio/Streamlit 一函数起界面的流式 demo（python §7.3/§7.4）适合演示，生产再换 FastAPI+SSE。
> - 延伸阅读：[python-handbook §7.2 FastAPI + SSE 流式：LLM 服务的工业标准](../python-handbook/Python大模型应用开发手册.md)｜[tuning-handbook §7.5 延迟预算分解：TTFT / 生成速率 / 工具往返](../tuning-handbook/Agent调优手册.md)

> **Q093. 上线后的"评测-监控-告警"运营体系怎么搭？**（难度：中 ｜ 频次：中）
> - 考察点：三时机框架、trace→dataset 闭环、成本熔断——"上线之后"有没有完整骨架，而不是只答"看日志"。
> - 参考回答：
>   - 总框架用三时机（eval §2.2）：离线评测（发布前，固定评测集×候选版本，回答"能不能上"）、在线评测（生产中，真实流量抽样打分+业务指标，回答"实际表现如何"）、灰度回放（新版本在昨日真实流量上回放，回答"换了会怎样"）——离线是安全网、在线是体温计、回放是传送带，三者不是三选一。
>   - 在线质量监控三层：规则与业务指标（转化率、人工纠正率、投诉率）、LLM-as-judge 抽样打分（judge 必须先与人工标注校准再上岗，eval §5）、用户显式反馈（点赞点踩）——全量人审不可持续，按比例采样、高价值 case 优先（eval §7.3 纪律：采样而非全量）。
>   - 成本监控：token 用量与成本归因到 trace（每次调用可查账）、单会话成本分布、预算熔断（单租户/单日美元上限触发自动降级或熔断——eval §8 有成本核算+整轮预算熔断的最小实现）；模型路由后各档 pass 率与成本并排监控。
>   - 延迟监控：TTFT 与端到端的 P50/P95/P99 分位数、按错误码分桶；SLA 一律用 P99 口径。
>   - 告警三类：阈值告警（错误率、超时率）、环比突变告警（通过率环比跌 X%——provider 静默更新最常见）、预算告警（成本日环比激增）；每条告警带 trace 链接直达现场，能归因的告警才是好告警。
>   - trace 体系：接 OpenTelemetry GenAI 语义约定（正在收敛的追踪协议），记录输入输出、工具轨迹、token 用量；PII 落盘前过滤、保留期分级、trace 访问本身有审计（security §7.2 数据项）。
>   - 闭环五步（eval §7.3）：生产 trace → 筛坏例（四信号+轨迹异常）→ 入 dataset（必须带溯源字段：trace_id/时间/反馈类型，修正时能回到原始现场）→ experiment 跑分（新版本 vs 基线）→ 回归门禁（退步卡发布）→ 新版本上线产生新 trace，循环不息。
>   - 环境漂移感知：provider 静默更新与限流策略变化靠"金丝雀评测集"每日跑分发现——固定评测集的分数突变=环境漂移信号，别等用户投诉。
>   - 运营组织：每周坏例评审会（产品+工程+业务）、评测集版本管理（当代码管，eval §4.4）、看板分层（高管看业务指标、工程看质量/成本/延迟）。
>   - 失败模式：只监控报错不看质量漂移（服务不挂但答错）、评测集从不更新（与现实脱节）、judge 无校准就上岗（分数不可比）、告警阈值拍脑袋导致狼来了。
> - 追问与陷阱：
>   - 追问：LLM-as-judge 分数能直接当 KPI 吗？常见错误：未校准直接用——judge 有位置偏差与长度偏差，先做与人工标注的一致率对齐（eval §5.4），关键场景用多 judge 仲裁。
>   - 追问：告警阈值怎么定？常见错误：拍一个固定值——用历史分布（基线±Nσ）与业务容忍度联合确定，且每次事故后回检阈值有效性。
> - 加分项：能当场画出 trace→dataset→experiment→回归门禁的闭环图并点出两条工程纪律（溯源字段必带、采样而非全量），或给出预算熔断的判定逻辑（单请求成本 × 当日调用数预估 > 预算即降档）。
> - 延伸阅读：[eval-handbook §2.2 三时机：离线 / 在线 / 灰度回放](../eval-handbook/Agent评测与质量工程手册.md)｜[eval-handbook §7.3 trace → dataset → 评测的闭环](../eval-handbook/Agent评测与质量工程手册.md)｜[eval-handbook §8 成本与延迟工程（预算熔断）](../eval-handbook/Agent评测与质量工程手册.md)

> **Q094. 设计一个 multi-agent 深度研究报告系统，怎么分工与交接？**（难度：高 ｜ 频次：高）
> - 考察点：orchestrator-worker（编排者-工人）的分工依据、上下文隔离的收益论证、交接协议的工程细节——"为什么这样拆"要能自洽。
> - 参考回答：
>   - 先过真需求判据：报告类任务的子问题天然独立（不同视角/不同子题），是多 agent 少数收益明确的形态（multiagent §1.3）；如果只是一篇短报告，单 agent + 检索更省——先把这句话说在前面，再谈架构。
>   - 参考架构 orchestrator-worker（multiagent §2.2）：orchestrator 把研究问题分解为 N 个独立子任务 → N 个 worker 并行执行（各自独立上下文、各自 3+ 工具并行检索）→ 各自回传压缩结论 → orchestrator 汇总去重成稿。Anthropic 研究系统的形态：Lead Agent 拆 3-5 个并行子代理，收益可达 90% 时间节省；成败手筋在分解质量——模糊委派是重复劳动的第一根因。
>   - 视角驱动的分解抄 STORM（multiagent §8.3）：写手+持不同视角的专家多轮对话产出大纲与问题（perspective-guided question asking），再并行检索回答、最后汇编成文——视角天然独立、产物可验收（问题-答案对+引用）、拓扑简单（中心分解+独立并行+汇总），天然避开接缝失败。
>   - 上下文隔离是收益来源（context §3.1）：每个 worker 独立上下文，检索到的原始网页不进主编排上下文——隔离同时解决"上下文爆炸"与"信息串扰"；检索型 worker 可用低档模型跑（成本分档，子代理默认独立 token 消耗）。
>   - 交接协议四条直接抄（multiagent §3.3）：①回传"简明报告"而不是全量过程——结论+关键证据的路径引用（URL、命令与退出码）+未决问题，父代理复核的是可定位的证据不是子代理自述；②回传通道即身份边界——子代理结果以不继承用户身份的消息注入，信息可以从子代理流回、权限不能；③默认拿走高危工具——检索型 worker 不给写/发送类工具，防横向扩张；④首步不打扰——后台结果从第二个 model step 起 drain，主代理第一个调用永远聚焦用户原请求。
>   - 汇总与成稿阶段：去重（多 worker 撞同一信源）、冲突标注（两个 worker 结论矛盾时不静默取其一，标记双方出处与置信）、引用核验（每个论断可回查原始 URL，核验必须程序化）。
>   - 治理与预算（multiagent §6.4 治理清单思路）：任务级 token/调用预算熔断；worker 失败容忍（个别子任务失败降级为"该视角缺失"标注而非整体失败）；全程审计与可复现（固定参数、快照检索结果）。
>   - 评测评两条线（multiagent §7.1）：任务质量（报告覆盖度、事实准确率、引用有效率）+ 协作质量（分解合理性、子任务重复率、交接信息保真）；稳定性用 pass^k 口径（τ²-bench：同一任务 k 次采样全过才算过）——多 agent 方差大，单次通过不代表可靠。
>   - 失败模式：模糊委派导致重复劳动、worker 上下文爆炸（worker 也要做预算治理）、结论冲突被静默平均、worker 编造引用（引用核验程序化兜底）、orchestrator 被回传内容撑爆（回传必须是压缩报告而不是过程）。
> - 追问与陷阱：
>   - 追问：为什么不用一个长上下文模型自己跑完全程？常见错误："窗口够大就不用拆"——单上下文会串视角、检索中间件占满窗口且无法并行；隔离的 worker 各自窄上下文，快且可并行。
>   - 追问：worker 之间要不要互相通信？常见错误："多 agent 就要多聊"——平权自由对话是接缝失败高发区；中心分解+独立并行+汇总的简单拓扑更稳（STORM 经验）。
> - 加分项：能引 open_deep_research 于 2026-08 被归档的教训（star 高不等于长期依赖安全，归档/维护状态扫描要进选型流程），或说出 MAST 失败分类学中"接缝失败"这一类，以及权限不随消息流动的底线（同伴消息不能当用户批准）。
> - 延伸阅读：[multiagent-handbook §2.2 orchestrator-worker（编排者-工人）](../multiagent-handbook/Multi-Agent协同手册.md)｜[multiagent-handbook §3.3 交接协议四条（可以直接抄）](../multiagent-handbook/Multi-Agent协同手册.md)｜[context-handbook §3.3 handoff 摘要协议：什么该带回父代理](../context-handbook/Context与记忆系统手册.md)

> **Q095. 从 0 到 1 搭一个企业 agent 平台，会怎么设计？（结合六家 agent 架构）**（难度：高 ｜ 频次：中）
> - 考察点：分层架构的完整性（网关/工具/编排/知识/安全/评测六层）与"从六家 agent 架构抄作业"的自觉——高级岗的平台设计压轴题。
> - 参考回答：
>   - 先立选型原则：平台为场景服务——先有 2-3 个已验证场景再抽象平台（MIT NANDA：95% 企业 GenAI 项目无可入账价值，多数死于无场景空转）；平台要支持的能力形态直接参考 ADP 四种构建模式（标准/单工作流/Multi-Agent/Claw）。
>   - 模型网关层（自建第一步）：统一多 provider 协议、模型目录外置成配置（换模型从发版变改配置）、路由与级联降级、提示缓存、token 计量与成本归因、限流与预算熔断——tuning §6.5/§7 与 OpenClaw 网关（§7：Identity first → Scope next → Model last）是现成参照。
>   - 工具/插件层：协议统一用 MCP（Model Context Protocol，模型上下文协议）；"一切皆插件"（deepseek-harness §3 的 Cordis 装配体系）让能力扩展不进内核；插件独立进程/沙箱隔离（04-zcode 的做法）；权限按最小权限四落点（工具面收窄、动作分级、资源边界、出口控制），插件与 MCP server 按不可信输入管理（供应链面）。
>   - 编排与运行时层：两种形态并存——确定性流程走工作流引擎（六问判据），开放任务走 agent 运行时（主循环+工具+委派，01-claude-code 的骨架）；状态持久化是平台护城河：参照 ZCode 用 SQLite 31 表做唯一真源+事件溯源（事件即事实：ModelRequest/ModelComplete/CheckpointCreated…），才有 fork/rewind/checkpoint 这些企业刚需（调试、审计、断点续跑）。
>   - 并发与队列层：多渠道入口必然出现"同会话被连续消息轰炸"——参照 OpenClaw：双层 lane 串行化（每会话 lane 套全局 lane）、四种队列语义（steer/followup/collect/interrupt）、写者围栏（SQLite 事务内校验 expectedWriterRunId 防脏写）、并发上限显式配置（lane 未配置为 1、main = max(8, CPU 并行度×4)、subagent = 8）。
>   - 知识层：RAG 服务化（离线管线+在线检索+检索前权限裁剪），知识治理流程（谁维护、更新频率、评测准入）当平台功能而不是线下约定。
>   - 安全与身份层：复用企业 IAM 统一身份、审批流（危险操作 deny-by-default+审批绑定执行要素）、结构化审计日志（谁在何时批准了什么、批准绑定的是什么）、注入防护与出口控制——五堵墙的"权限安全"在平台层收口。
>   - 评测与运营层（最后一堵墙）：评测集管理、回归门禁、trace 平台、成本看板、坏例回流流程——评测运营是平台内建能力，不是"以后再说"。
>   - 演进路径：一期=网关+工具层+标准模式场景（数周可交付）；二期=工作流引擎+评测门禁；三期=multi-agent/Claw+自助化——与 ADP 3.1 的模式演进图同构，客户预期就顺了。
>   - 失败模式：平台先行无场景、权限模型后补（先放权后收权极难）、插件供应链失控（未审查的 MCP server 进生产）、状态不持久导致无法审计与续跑。
> - 追问与陷阱：
>   - 追问：编排引擎自研还是用开源（n8n/Dify/LangGraph/Temporal）？常见错误：按 star 排名选——按场景判据选（2026-09-28 横评：n8n 206k / Dify 157k / LangFlow 155k star；LangGraph 核心包 1.2.12、42k；Temporal 23k 把确定性变成工程纪律；Flowise 已整库归档），且归档/维护状态扫描是必做动作。
>   - 追问：平台第一版要不要内置记忆系统？常见错误：一上来做复杂记忆——先做会话持久化与用户级配置；长期记忆（mem0/Graphiti 类）按场景二阶段上，且必须带 provenance 与删除闭环。
> - 加分项：能横向说出至少三家可抄的设计（01-claude-code 的主循环+委派骨架、03-deepseek-harness 的插件装配、04-zcode 的状态持久化与 fork/rewind、05-openclaw 的网关限流），并点破它们都不做画布工作流的原因——coding 场景步骤不可枚举，写死路径做不了。

> **Q096. 存量业务系统怎么渐进式引入 agent（灰度、回滚、审计）？**（难度：高 ｜ 频次：高）
> - 考察点：旁路优先的克制、灰度/回滚/审计三件套的工程细节——企业落地的最后一公里，高级岗压轴题。
> - 参考回答：
>   - 总原则一句话：旁路优先——第一个 agent 只做"读"与"建议"，不碰主流程的写路径；这是技术风险与组织信任的双重策略，价值证明后逐级放大权限。
>   - 场景选择：从"人力耗时但错误可审"的环节切入（工单预填、知识检索、报告草稿、代码评审建议），避开"直接自动化对外决策"；错误代价高的环节永远保留人工确认——workflow §1.2 六问的第 6 问（错误代价高→工作流+人审）。
>   - 架构解耦：agent 作为旁路服务独立部署，通过 API 以只读账号读业务系统，不进核心链路的事务边界——agent 挂了不影响主业务；写回走显式 API+审计+审批，绝不直连数据库。
>   - 灰度路线：白名单（内部员工）→ 小流量（5%→25%）→ 全量；每步看在线指标（采纳率、人工修改率、投诉率）并用灰度回放（eval §2.2：新版本先在昨日真实流量上回放再放量）。
>   - 回滚设计：feature flag 一键关闭 agent 入口；prompt/模型/插件版本都可独立回滚（配置中心版本化）；"发布 ≠ 生效"三条纪律照抄（workflow §6.5：确认变更项、写版本说明、发布后从用户侧再测一次）。
>   - 审计与合规：全量操作留痕（agent 做了什么、依据什么、谁批准），权限决策结构化审计（security §7.2：谁在何时批准了什么、批准绑定的是什么）；导出、对外发送类敏感操作单独成审批轴。
>   - 上线前过安全检查单（security §7.2）：lethal trifecta 三要素逐项标注断点、deny-by-default、子代理权限收窄（只继承 deny/拿走高危工具）、PII 进出口双侧脱敏、凭据不进上下文、数据出境字段清单化——逐条勾完才放行。
>   - 评测先行：上线前从历史工单/日志挖黄金评测集；上线后 trace→dataset→experiment 闭环持续回流（eval §7.3），每次扩权（新增写工具/新数据源）都要回归。
>   - 权限放大阶梯：只读 → 建议（人确认后执行）→ 受限写（白名单操作+审批）→ 自主写（仅低风险、可回滚）——每一级都要评测与审计达标才晋级，且随时可降级；用阶梯和数据换业务方的"直接放开"诉求。
>   - 失败模式：一上来接管写操作（退款/发货）出事故即全盘皆输、没有 feature flag（出事只能发版回滚）、审计缺失过不了合规、agent 与主系统未解耦（agent 拖垮主业务）。
> - 追问与陷阱：
>   - 追问：业务方急着要 agent 直接改工单，怎么谈？常见错误：用"技术风险大"这种抽象理由——给出阶梯方案与数据门槛（建议模式跑 N 周，采纳率/修改率达标再开受限写），用证据换权限。
>   - 追问：灰度指标看什么？常见错误：只看任务完成率——必须同时看人工修改率（输出被改了多少）、越权审计零事件、下游投诉率；完成率高但修改率高说明质量虚。
> - 加分项：能把"权限不随消息流动"（multiagent §3.4：同伴消息不能视作用户批准、"被拒后转托=权限洗白"要拒绝并上报）迁移到存量系统多 agent 协作；或用 ZCode 的 fork/rewind/checkpoint 类比"agent 操作可回卷"的审计设计，讲出状态持久化对审计的价值。
