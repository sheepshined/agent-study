## 0. TL;DR

- **FDE 的一句话职责**：在客户环境里把"模型能力"翻译成"可验收的业务能力"，并把现场学到的模式反哺回产品。交付之外的隐藏 KPI 是**这次部署让下一次部署变快了**（§1.4，来源见 §9.1）。
- **交付七阶段**：售前支持 → 需求诊断 → 方案设计 → POC → 交付实施 → 验收 → 运维交接。每阶段一张"输入/产出/风险/翻车点"卡（§1.2）；阶段间的交接物就是 §5 的六份模板——**模板先于工作，先有验收标准再动手**。
- **需求诊断第一原则**：客户说的话 ≠ 需求。用五组问题清单（业务目标/数据现状/集成约束/合规红线/成功标准）把业务语言翻译成方案语言，再用 in/out of scope 把第一期钉死（§2）。识别不了伪需求，后面每个阶段都在替它还债。
- **选型只看一个变量：控制流在哪**（[workflow-handbook §1](../workflow-handbook/Agent工作流编排手册.md) 的第一性判据）。落到 ADP 四模式：问答为主选标准、流程固定选单工作流、多角色协作选 Multi-Agent、开放探索选 Claw——先选模式再画图，别反过来（§3.1）。
- **POC 的本质是"最小可信"而不是"最完整"**：一个能闭环、可验收的切口 > 十个半成品能力；Demo 必须带降级预案和录屏备份（§4）。
- **交付物模板六件套**：需求规格 → 方案设计 → 验收标准（DoD，Definition of Done，完成定义）→ 测试用例 → Handover 交接 → 运维手册，全部可直接复制（§5）。
- **沟通纪律**：周报固定节奏、行动项带 owner 和日期、变更必须走 CR（Change Request，变更请求）、坏消息早说 + 带选项（§6）。虎嗅报道的"为前端过度承诺填坑"（[转行手册 §2.1](FDE转行手册.md)），就是预期管理失守的结局。
- **成本先算后烧**：token 按"输入/输出/缓存命中"三个口径估，调试和评测消耗也计入（裁判模型打分本身就是 token 开销，ADP 4.1 原话）；四家厂商当日实抓价格速查与缓存杠杆见 [tuning-handbook §6.6](../tuning-handbook/Agent调优手册.md)；人天按"有模板 ÷1、首次 ÷2"打折（§7）。
- **排障先分六类再动手**：模型超时 / 检索不准 / 集成失败 / 权限问题 / 性能瓶颈 / 成本突增——每类一张故障树；生产高风险错误的第一响应是**限流降级保现场，不是继续调 Prompt**（§8，ADP 4.1 原话）。
- **公开实践的三条硬经验**（§9 当日实抓）：① 观察 > 访谈——盯人干活 30 分钟胜过一场需求会；② "who merges the code in the customer's repo"（谁在客户仓库里合代码）是 FDE 与售前的分水岭；③ 每个现场 hack（临时补丁）都会变成你要养一年的资产——留哪些、扔哪些要显式决定。
- **第一周上手清单**在 §10.2：建目录、立模板、跑通一条端到端链路、写第一份周报。

**阅读路线**：刚接手第一个客户 → §1→§2 顺序读；明天要出方案 → §3 + §5.2；后天 Demo → §4；要报价 → §7；线上出事了 → §8 直接查表。

## 1. 交付全景与角色边界

### 1.1 职责接口：FDE 与四方的边界

FDE 是"半个软件工程师 + 半个解决方案架构师 + 半个顾问"（[转行手册 §1.1](FDE转行手册.md)）——但"半个"不是"随便补位"。接口不清楚是现场摩擦的第一来源。下表把常见灰色地带钉死（R=Responsible 主责，C=Consulted 被咨询，I=Informed 知会）：

| 事项 | 销售/售前 | 产品 | 研发/平台 | 客户 | FDE |
|---|---|---|---|---|---|
| 商务承诺（价格/工期/范围） | **R** | C | I | C | **必须知情（I）**——历史上最贵的坑：销售承诺了 FDE 兜不了的功能（见 §6.4） |
| 需求诊断与范围界定 | C | C | I | R（客户确认） | **R** |
| 方案设计与选型 | I | C | C | C | **R** |
| POC 搭建与演示 | I | I | I | C | **R** |
| 生产代码/应用搭建 | I | I | C（平台缺陷时） | I | **R** |
| 平台级功能缺陷修复 | I | R | **R** | I | C（提 issue + 临时绕行，见 §8.3） |
| 验收签字 | I | I | I | **R** | C（组织证据、跑测试集） |
| 上线后运维 | I | I | C | R（业务侧） | C→R（handover 前） |
| 现场经验反哺产品 | I | **R**（接收） | R | I | **R**（供给）——这是 FDE 区别于外包的立身之本 |

> 反哺为什么是职责不是美德：Latent.Space 精读（ex-Palantir 的 Vinoo Ganesh）明确 "FDEs are an extension of the product team, not sales or services"——汇报线挂在产品，每次部署都要回答"这次留下了什么下次部署能直接用"；ICONIQ 2026 年调研中 24% 的 FDE 把自己的职责描述为"把客户定制反哺回核心产品"（来源见 §参考资料）。这正是 [FDE转行手册 §1.2](FDE转行手册.md) 的"土路 → 高速公路"循环的执行机制。

### 1.2 七阶段交付流水线

每阶段记四件事：**输入**（从上一阶段接什么）、**产出**（交出去什么，对应 §5 哪份模板）、**典型风险**、**常见翻车点**。

| 阶段 | 输入 | 产出 | 典型风险 | 常见翻车点 |
|---|---|---|---|---|
| ① 售前支持 | 商机背景、客户初步诉求 | PoC 承诺边界、可行性预判 | 被要求"先承诺再验证" | 售前为赢单过度承诺（虎嗅：国内 FDE 常在"为前端销售的过度承诺填坑"，[转行手册 §2.1](FDE转行手册.md)）——**对策：售前阶段就写一页 scope 备注，随合同归档** |
| ② 需求诊断 | 客户访谈、现有文档与系统 | 需求规格说明（§5.1）+ 干系人地图（§2.5） | 需求飘、伪需求混入 | 只访谈不观察——客户自己也不知道自己怎么干活（§2.2） |
| ③ 方案设计 | 需求规格 | 方案设计文档（§5.2）+ 可行性风险清单（§3.5） | 过度设计 / 模式选错 | 拿着模型能力找场景，而不是从业务问题出发 |
| ④ POC | 方案文档、脱敏样例数据 | 可演示的最小闭环 + 演示脚本（§4） | 演示环境与真实环境脱节 | 用假数据做出来的"完美效果"，一上真数据就崩 |
| ⑤ 交付实施 | 验收标准（§5.3） | 可用系统 + 测试用例表（§5.4） | 范围蔓延（scope creep） | 没有书面 DoD 就开工——验收时各说各话 |
| ⑥ 验收 | 测试集、验收标准 | 签字验收报告 | 指标口径歧义 | "准确率 90%"没定义分母和判卷方式（§5.3 填写要点） |
| ⑦ 运维交接 | 全部文档、监控数据 | Handover 文档（§5.5）+ 运维手册（§5.6） | 知识只在我脑子里 | 人一撤场，系统变成黑盒；客户不会换知识库 |

> 来源：ADP 课程 [2.3](tencent-adp-fde-course/lessons/2.3_从开发到上线：ADP_应用的完整使用流程.md) 七步流程 + Hashnode 2026 FDE 指南的四段交付环（scoping → prototyping → production → feedback），两者合并重述，来源见 §参考资料。

### 1.3 ADP 2.3 七步流程的 FDE 视角重述

ADP 课程 2.3 讲的是"平台上怎么走完七步"；FDE 视角多两件事——**平台外的事**（商务/文档/沟通）和**每步的客户确认点**。对照表（平台动作 → FDE 补充）：

| ADP 2.3 平台七步 | FDE 在这一步额外要做的 | 客户确认点 |
|---|---|---|
| 开通产品并创建工作空间 | 确认部署形态（SaaS / 专有化）与账号权限归属；工作空间对应 §2.5 干系人地图里的组织边界 | 安全合规部门签字 |
| 创建应用并选择模式 | 走 §3.1 选型决策树并写选型理由书，而不是"默认标准模式" | 方案评审会（§6.2） |
| 配置知识库、连接器和工具 | 知识治理前置：资料谁维护、更新频率、权限分级（ADP 3.2 素材：过期资料及时下线，避免引用旧口径）；工具接入用 MCP（Model Context Protocol，模型上下文协议，见 [mcp-handbook](../mcp-handbook/MCP搭建文档.md)） | 数据授权与脱敏清单 |
| 搭建智能体逻辑 | 按 ADP 3.2/3.3/3.4 的实战路径搭建；每步留调试记录（§8.2） | 中期演示（防跑偏） |
| 对话调试与效果评测 | 单次调试 → 评测集批量验证（ADP 4.1 闭环）；评测集来源必须是真实业务问题 | 验收标准评审（§5.3） |
| 发布应用与渠道接入 | 凭证管理（AppKey 不进前端/日志明文）、灰度发布计划、回滚预案 | 上线通知与培训排期 |
| 监控运营与持续优化 | 建周报节奏（§6.1）、成本看板（§7.1）、badcase 回流评测集（[eval-handbook §4](../eval-handbook/Agent评测与质量工程手册.md)） | 运营例会 + 迭代路线图 |

### 1.4 一条贯穿全程的主线：反哺回路

每次部署在 §1.2 的七个阶段之外，持续回答三个问题（Exponent/OpenAI FDE 流程与 Latent.Space 精读的交集，来源见 §参考资料）：

1. **这次遇到了什么平台装不下的东西？**——不是收集客户的功能点子（三家客户要同一个功能是低信号），而是三个 FDE 在绕同一个平台限制（高信号）；
2. **哪些现场补丁值得晋升为产品能力，哪些必须显式扔掉？**——"每个临时脚本都会变成你要长期维护的资产"（§9.1 的 vinoo.groovy 案例：一个下午写的留存脚本在十万人客户那里跑了一年）；
3. **下一家同行业客户，方案里哪一段可以直接复用？**——把答案写进你自己的行业 skill 库（国内自由职业 FDE 实践：沉淀 10+ 个行业技能包复用，[转行手册 §2.3](FDE转行手册.md)）。

> 来源：ADP [2.3](tencent-adp-fde-course/lessons/2.3_从开发到上线：ADP_应用的完整使用流程.md)（平台七步）；Hashnode 2026 指南（四段环与 20%/80% 论述）；Latent.Space（反哺与补丁）；均当日实抓，链接见 §参考资料。

## 2. 需求诊断工具箱

ADP 3.1 的原话："客户往往不会直接说'我要一个标准模式应用'……他们通常会用业务语言描述问题"——一句话里可能同时混着重复咨询、知识检索、问题统计、管理看板四件事。需求诊断就是把这团东西拆开。

### 2.1 客户访谈问题清单（五组）

ADP 3.1 给了七维度需求框架（背景现状/业务目标/使用对象/任务边界/资料知识/系统工具/限制验收）。现场更好用的是五组、每组不超过四问——问太多客户会开始编答案：

**第一组：业务目标（为什么是现在？）**
- 这个问题今天是怎么解决的？人工流程走一遍给我看。
- 如果只改善一个数字，你希望是哪个？（要具体指标，不要"提升效率"）
- 为什么是现在做？之前试过什么、为什么没用？
- 立项后谁向谁汇报这个项目的成败？

**第二组：数据与知识现状（智能体知道什么？）**
- 回答依赖哪些文档/系统？给我最新的三份样本（**拿实物，不要描述**）。
- 资料谁维护、多久更新、有没有版本号和生效日期？
- 同一个问题在两份资料里答案不一致时，以谁为准？
- 有没有绝对不能进模型的数据（见第五组）？

**第三组：集成约束（智能体能连什么、动什么？）**
- 要读/写哪些系统？接口和鉴权方式现成吗？谁有权限开？
- 哪些动作允许自动执行、哪些必须人工确认？（ADP 3.1 操作分级：只读可自动、可逆动作校验留痕、删除/付款/改价必须审批）
- 出错了怎么回滚？谁负责？
- 网络/部署形态有约束吗（内网隔离、数据出境、信创要求）？

**第四组：合规红线（哪里绝对不能碰？）**
- 数据分类分级现状？（员工薪资、客户身份、医疗金融信息不能因"用于问答"就全量入库——ADP 3.1 原话）
- 高风险输出（法律/医疗/金融/绩效处分）谁审核？免责声明不能替代人工确认。
- 日志怎么留、留多久、谁能看？（日志也是受保护数据——ADP 4.1：最小采集 + 脱敏 + 保留周期）
- 采购流程里有没有等保/审计/供应商准入要求？

**第五组：成功标准（怎么算成了？）**
- 验收指标是什么、怎么测、谁判卷？（要求到可执行：数据集、样本量、通过线）
- 上线后多久复核一次效果？
- 什么情况下你会关掉这个系统？（反向问题，最能暴露真实底线）
- 验收数据集和负责人现在能定吗？（定不了 = 项目风险信号）

> 来源：ADP [3.1_方案设计方法](tencent-adp-fde-course/lessons/3.1_方案设计方法.md) 七维度清单压缩重述；操作分级/日志纪律出自 3.1 与 4.1 原文。

### 2.2 真需求 vs 伪需求识别

判据表（命中越多，越可能是伪需求）：

| 信号 | 真需求的样子 | 伪需求的样子 |
|---|---|---|
| 现状描述 | 能拿出具体单据/表格/截图，能说清耗时 | "我们流程很复杂很落后"但拿不出样本 |
| 指标意识 | 有今天的人工基线数字 | 全是"提升 50% 效率"这类无分母的话 |
| 发起人 | 有预算权的业务负责人 | 中层"先做个样子给上面看" |
| 数据现实 | 承认数据脏并愿意配合清洗 | "数据你们自己想办法" |
| 边界感 | 能说清什么不归它管 | "最好什么都能做" |
| 复用意愿 | 接受"第一期只做一个闭环" | 坚持一次上齐问答+工单+看板+驾驶舱 |

三个高发伪需求模式（来源：多仓库共识 + 现场经验，与 [multiagent-handbook §1](../multiagent-handbook/Multi-Agent协同手册.md) 的"何时真的需要多 Agent"同构）：
- **"AI 大屏需求"**：真实诉求是领导汇报素材 → 解法可能是一个统计报表，不是智能体。先问：这个数字明天有人基于它做什么决策？
- **"把 ChatGPT 装进公司"**：没有知识边界和权限模型的企业问答，上线即事故（越权召回、旧口径）→ 解法是先做知识治理，再谈应用。
- **"全自动办事"**：客户嘴上要全自动，签字意愿为零 → 用 §2.1 第三组的操作分级问题当场拆穿，改造成"AI 起草 + 人工确认"。

**验证方法**（比访谈更硬）：挑一个最痛的环节，**观察而不访谈**——跟着业务员干半天活。Latent.Space 精读的案例：某数据质量工程师总卡住一次数据迁移，访谈问不出原因；看她操作才发现她唯一的质量校验工具是肉眼盯 CSV——给她做了一个 Parquet 查看器，迁移解锁、管线执行从约 17 小时降到 2 小时。**客户说不出来的隐性知识（tacit knowledge），是访谈问不出来的。**

### 2.3 范围界定模板（in / out of scope）

可直接复制，填完贴进需求规格说明（§5.1）：

```markdown
## 范围界定（v1.0 · 2026-09-28 · 客户确认人：____）

### In Scope（第一期承诺交付）
- [场景1] 例如：门店员工通过企业微信咨询商品知识与促销政策，基于授权知识库回答并附引用来源
- [场景2] 例如：投诉类问题生成工单并流转给售后团队
- [场景3] …（每个场景必须能一句话说清"谁、在哪、做什么、产出什么"）

### Out of Scope（本期明确不做，写到合同/方案里）
- [不做1] 例如：数据分析看板（列入二期候选）
- [不做2] 例如：自动退款等资金操作（只读查询，操作类转人工）
- [不做3] …

### 边界规则
- 知识范围：仅基于 [授权知识库清单]；知识不足时明确拒答（拒答话术见 §5.6 附录）

- 免责边界：[法律/医疗/金融] 类问题输出仅作参考，以 [正式系统/负责人] 为准

### 变更规则
- 本范围外的新增诉求一律走 CR 流程（§6.3），评估影响后排期
```

填写要点：**Out of Scope 比 In Scope 更重要**——它是在为三个月后的自己省一场验收吵架。ADP 3.1 的"第一期先做能闭环、可验收的部分"（优先知识类 → 流程固定类 → 多角色协同 → 文件/代码处理）就是往 In Scope 里挑切口的标准顺序。

## 3. 方案设计工具箱

### 3.1 四模式选型决策树

第一性判据来自 [workflow-handbook §1](../workflow-handbook/Agent工作流编排手册.md)：**控制流在谁手里**——步骤能预先枚举、每步输入输出写得清、错一步代价高 → 开发者写死（工作流）；步骤写不死、需要模型临场判断 → 交给模型（agent/自主模式）。

```
需求进来
├─ 用户提问，系统基于授权资料回答，不"办事"
│   → 标准模式（知识库 + 问答对 + 同义词 + 拒答 + 长期记忆，ADP 3.2 路径）
├─ 输入明确、流程固定、步骤可拆（工单/表单/分流/报告）
│   → 单工作流模式（参数提取 → 意图识别 → 分支处理 → 变量聚合 → 回复，ADP 3.3 路径）
├─ 一个目标需要多个专家角色协作（调研/设计/评审/复核）
│   → Multi-Agent 模式（先 3-4 个角色，路由不稳时用工作流编排替代自由转交，ADP 3.4 路径）
└─ 开放探索、要读写文件/跑代码/长耗时自主任务
    → Claw 模式（给目标 + 文件 + 工具范围，让它自主规划）
```

四个辅助信号（ADP 3.1"模式选择看四个信号"的重述，与判据树交叉验证）：**①流程稳定吗**（越固定越适合工作流）；**②输入输出谁消费**（人看 → 自然语言，系统消费 → 结构化字段，决定了节点设计）；**③知识质量**（资料乱 → 先治理再上模式，模式救不了烂数据）；**④系统依赖**（只回答问题依赖少，要"办事"就要确认接口/权限/审计/回滚）。

三条提醒：
- **模式可切但配置不继承**：ADP 2.3 明确——标准/单工作流/Multi-Agent 之间支持切换，但提示词、模型配置等**不相互继承**；Claw 不支持切回其他模式。选型前想清楚，切换有成本。
- **同一个项目往往分阶段组合**（ADP 3.1 酒店案例：一期标准模式答酒店信息 → 流程固定后工作流接工单 → 后期 Multi-Agent/Claw 做经营分析）——**方案文档里画出模式演进图**，客户预期就顺了。
- **多 Agent 不是默认答案**："何时真的需要多 Agent"的伪需求判据见 [multiagent-handbook §1](../multiagent-handbook/Multi-Agent协同手册.md)；需要协议化接外部系统时，工具层用 MCP 统一（[mcp-handbook](../mcp-handbook/MCP搭建文档.md)）。

## 4. POC 与 Demo 工具箱

### 4.1 最小可信场景设计

POC 不是"功能全做一遍的缩水版"，而是**一条能让客户亲眼确认价值的最小闭环**。切口怎么选（ADP 3.1 的优先级序）：
1. 能找到稳定资料的 → 知识问答切口（最容易闭环、最容易验收）；
2. 流程已经固定的 → 流程自动化切口（信息收集 → 判断 → 出结果）；
3. 都不行 → 选"半自动切口"：AI 出草稿，人工点确认——价值照样能演示。

四条设计规则：
- **数据用客户的真数据**（脱敏后）——演示的说服力 90% 来自"这是我们的东西"。拿不到就用高保真 mock（见 4.2），并明说。
- **场景从客户嘴里来**：演示脚本里的问法用他们一线的真实问法（访谈时录音记录的那种），别用 FDE 自己编的书面语。
- **闭环必须完整**：从提问到产出物（答案/工单/报告）走通，不演示半截。
- **当场展示边界**：主动演示一次"知识不足 → 拒答/转人工"（ADP 3.2 的兜底回复路径）——客户对"知道自己不知道"的系统信任度显著更高，还能预防验收阶段的超范围期待。

### 4.2 mock 数据策略

| 情形 | 策略 | 注意 |
|---|---|---|
| 客户能给脱敏数据 | 优先，签数据使用范围说明 | 提前对好脱敏口径（姓名/手机号/证件号/薪资一律假名化，日志同样规则，ADP 4.1） |
| 给不了 | 结构保真 mock：字段名、格式、量级照抄客户描述，内容虚构 | 明确告知"效果待真实数据验证"，写进演示页脚 |
| 数据脏是痛点本身 | 现场演示"脏数据进 → 结构化出"的清洗价值 | 这往往是最打动人的演示 |
| 知识库未授权 | 用公开资料或 2-3 页样例文档搭骨架 | 演示后立即销毁，别留在个人环境 |

### 4.3 演示脚本模板

```markdown
# Demo 脚本：<项目> POC 演示（时长 20 分钟 + 10 分钟 Q&A · 2026-09-28）

## 参会人：[名单/角色]  演示人：____  环境：[链接]（备用：录屏 §4.4）

## 开场（2 min）
- 一句话重述需求与本次演示目标（对齐 §5.1 的范围，防超纲期待）
- 声明数据口径："以下演示基于贵司脱敏数据 / 结构保真模拟数据"

## 主线演示（10 min，3-5 个场景，每个场景：问法 → 过程 → 产出 → 价值数字）
- 场景1（核心痛点）：<一线真实问法> → 展示引用来源与结构化结果 → "今天人工要 X 分钟，现在 Y 秒"
- 场景2（流程类）：<工单/报告场景> → 展示系统写入与留痕
- 场景3（边界演示，务必保留）：知识不足问题 → 拒答话术 → 转人工路径

## 技术底座（3 min）：架构图一页（§3.2），只讲"数据没出贵司边界/权限怎么隔离"等客户关心项
## 里程碑与下一步（3 min）：POC 通过线 → 一期范围（§5.1）→ 排期
## 预案：Q&A 高频问题清单（§4.4 反问清单）｜每场景录屏备份｜环境故障切换口径
```

### 4.4 翻车防护三件套

- **降级预案**：演示前问自己"哪个环节最容易挂"（联网检索超时、接口断、模型抽风），每个高危环节准备替代路径——现场版本关掉联网走纯知识库、接口断了切 mock 响应、整个平台挂了切录屏。ADP 3.2 有一条直接可用：**"如果设置兜底回复，请关闭联网搜索"**——边界场景演示优先用稳定配置。
- **录屏备份**：演示前一天，把所有场景完整录一遍（连同拒答场景）。现场成功用现场，现场失败放录屏并诚实说明"演示环境出现网络问题，我们看预录实况"。录屏别用摆拍数据——客户分得出来。
- **客户反问清单**（演示前预演，答案提前写好）：①"准确率多少？怎么测的？"②"接了我们的真实数据会掉点吗？"③"知识库更新了它知道吗？"④"价格/资源消耗怎么算？"⑤"哪些情况会答错？"⑥"和上一个供应商的方案比好在哪？"——答不上第 ② 条（真实数据掉点）最伤信任，回答口径见 §7.1 成本与 §5.3 验收。

### 4.5 Demo 反模式集（每条都是真实翻车模式）

| 反模式 | 症状 | 解法 |
|---|---|---|
| 沙盒幻觉 | 只用自己编的数据和问法，演示完美、POC 通过后寸步难行 | §4.2 用客户数据；问法从一线录音来 |
| 超纲演示 | 演示了范围外能力，客户当场把演示当承诺 | 演示页首页放 in/out of scope；超纲问题答"列入二期评估" |
| 概率性成功赌博 | 演示场景没实测过，靠运气 | 演示脚本里每个问法提前跑 3 遍 |
| 魔改环境 | 演示环境 secretly 配了生产没有的东西（白名单、超长超时） | 演示环境=未来生产环境的等比缩小，差异写出来 |
| 只报喜不报忧 | 从不演示拒答/失败场景 | 把边界演示固定为脚本场景3（§4.3） |
| 一言堂 | 全程念稿不给客户提问空隙 | 每个场景后停 30 秒，让客户亲手输入一个问题——**客户自己问出来的答案，比自己演示三遍都可信** |

## 5. 交付物模板集

六份模板 = §1.2 流水线的交接物。每份：模板 → 填写要点 → 填例（填例统一用"连锁零售门店助手"场景，与 ADP 3.1 的练习需求同源，方便对照课程）。

### 5.1 需求规格说明（SRS-lite）

```markdown
# 需求规格说明：<项目名>（v<版本> · <日期>）

## 1. 背景与痛点（客户原话摘录 2-3 句 + 现状流程描述）
## 2. 目标与指标（必须可测量）
| 目标 | 指标 | 现状基线 | 第一期目标 | 测量方式 |
|---|---|---|---|---|
| 例：减少答疑人力 | 高频问题自助解决率 | 0%（全人工） | ≥60% | 会话日志抽样 + 人工判卷 |

## 3. 用户与场景（谁、在哪、多久用一次、典型问法 3 条）
## 4. 范围界定（in/out of scope，贴 §2.3 模板）
## 5. 知识与数据（资料清单/负责人/更新频率/分级与脱敏要求）
## 6. 系统与集成（读/写哪些系统、接口现状、鉴权方式、操作分级结论）

```

**填写要点**：指标表没有"现状基线"列就先别签——没有基线的"提升 60%"是空话；未决事项不许留白，每条带决策人和截止日，否则会拖到验收。

**填例（节选）**：
```markdown

| 目标 | 指标 | 现状基线 | 第一期目标 | 测量方式 |
|---|---|---|---|---|
| 门店答疑自助化 | 高频问题自助解决率 | 0% | ≥60% | 知识命中日志/总会话，周抽样 100 条 |

```

```markdown

- 验收对象：<应用/工作流清单 + 版本号>；验收环境：<环境与渠道>
- 指标口径声明：每个指标写明 分子/分母定义、判卷方式（人工判卷规则或裁判模型提示词）、抽样方式

## 2. 功能验收（逐条可勾选）
- [ ] F1 <场景>：<具体行为描述>（例：知识不足时输出兜底话术并建议补充资料，不编造）
- [ ] F2 <场景>：<具体行为描述>（例：投诉类诉求创建工单且工单字段与诉求一致）

## 3. 指标验收
| 指标 | 定义（分子/分母） | 判卷方式 | 通过线 | 样本量 |
|---|---|---|---|---|
| 知识命中率 | 命中且正确 / 总提问 | 人工双判（分歧仲裁） | ≥80% | ≥50 |

| 响应时长 | P95 | 平台监控 | ≤<X>s | 全量 |

## 4. 安全与合规验收
- [ ] 权限隔离实测：<越权访问用例> 被正确拒绝
- [ ] 日志脱敏实测：抽查 N 条日志无明文敏感字段

## 5. 验收流程
- 双方各出 2 人判卷 → 分歧仲裁人 <姓名> → 连续一轮达标即通过；
- 未达标：出问题清单 + 归因（按 §8 故障树分类）+ 修复排期，修复后**回归全量测试集**（防"修好一个坏三个"，ADP 4.1）
```

**填写要点**：三条铁律——①**每个指标必须同时写"判卷方式"**，只写"准确率 90%"的验收标准等于没写；②样本量写死（ADP 3.2 素材给的下限是 20-50 条，真实项目 ≥50 更稳）；③把"回归全量"写进流程，否则修复动作会引入新问题而无人发现。

```markdown

| # | 事项 | Owner | 截止 | 完成标志 |
```

### 6.3 变更请求（CR：Change Request）处理流程

口头变更 = 项目利润的漏斗。流程四步：

1. **登记**：任何范围外诉求（会上、群聊、走廊里提的都算）一律登记 CR 单，当日回执"已登记，下期评估"；
2. **评估**：影响三件套——工作量（人天）、成本（token/资源）、排期（挤占哪一期）；按 §3.4 评估新增风险；
3. **决策**：小改（<0.5 人天且不动验收指标）→ 直接进当前迭代并同步周报；大改 → 出选项让客户决策（"加钱/顺延/挤掉某项"三选一，**永远给选项而不是说"不行"**）；
4. **归档**：批准的 CR 更新 §5.1 范围界定和 §5.3 验收标准，形成新版本——**范围文档永远是最新版，这是验收不吵架的根**。

CR 单模板（三行就够）：`CR-013 · 日期 · 提出人 ｜ 诉求描述（原话）｜ 评估结论：+3 人天 / 二期 / 挤掉 F5 ｜ 决策：接受-<日期>-<决策人>`

### 6.4 坏消息沟通话术

原则（对内对外通用）：**早说、当面（或电话）先说、带选项、带根因、留书面**。

| 场景 | 反例 | 话术模板 |
|---|---|---|
| 进度延期 | "可能要延几天"（到截止日才说） | "原计划 X 的验收点预计延 N 天。根因是 <具体>。两个选项：A. 缩减 F3 保 X 日期；B. 全范围延 N 天。我建议 A，因为 <理由>。今天想跟您对齐。" |
| 效果不达标 | "效果不太好，我们再努力" | "测试集首轮 72%，未达 80% 线。归因分析显示 <Top 问题，如：3 类问法知识库无覆盖>。对策 <补资料/调提示词>，预计重测日期 <D>。若重测仍不达线，回退方案是 <降级承诺范围>。" |
| 承诺了做不到（填售前的坑） | 拖 | "售前阶段对 <能力> 的理解与工程现实有偏差：<具体差异>。现在可行的替代是 <方案 A/B>。这是我的责任范围内的纠偏，方案对验收标准的影响我已列好（附表）。" |
| 数据/安全事故 | 隐瞒或淡化 | 按预案升级链立即上报 + "影响范围目前是 <事实>、已采取 <动作>、下一步 <动作>、下次通报时间 <时间>"——事实分级说，猜测不说 |

### 6.5 验收争议处理

争议三类与拆法：
- **口径争议**（"我说的 90% 不是你测的 90%"）→ 回到 §5.3 的口径声明表逐字核对；没写的按行业惯例补签口径备忘再测。**预防大于解决：DoD 里的"判卷方式"栏就是为此存在的。**
- **样本争议**（"你们测的题太简单"）→ 当场加测客户现场抽的 N 条（提前约定抽样规则），并把新样本回流评测集——争议样本是最有价值的测试资产（[eval-handbook §4.1](../eval-handbook/Agent评测与质量工程手册.md)）。
- **期望争议**（"感觉不够智能"）→ 拆回具体场景清单："感觉"逐条翻译成可测用例，落在范围内的进 CR，范围外的引 §2.3 out of scope。

升级判据：三轮协商无果 → 引入双方立项负责人按合同验收条款走，FDE 的角色退回"提供测量证据"——**证据链（测试用例表、日志、录屏）从项目第一天就要按可呈堂的标准留**。

## 7. 成本与报价思路

### 7.1 token 成本估算表

**价格口径**（三个维度，报价前逐项确认）：
1. **分输入/输出计价**：输出单价通常是输入的 3-4 倍，估算时分开算；
2. **缓存命中价**：系统提示词、知识库前缀命中缓存后单价大幅下降（Anthropic 缓存读 0.1×、OpenAI 缓存输入 10%、DeepSeek 低至未命中价的 2-3.3%，国产锚点 GLM-5.3 缓存命中约 ¥2/百万 tokens）——完整四家厂商速查表见 [tuning-handbook §6.6](../tuning-handbook/Agent调优手册.md)（2026-09-28 对四个官方定价页实抓）；GLM 锚点为 2026-09-28 检索的 2026-08 发布口径，**报价前以 [bigmodel.cn 定价页](https://open.bigmodel.cn) 当日为准**；
3. **隐性消耗**：调试对话、评测集批量运行、裁判模型打分、多模型对比——全部产生 token 消耗（ADP 4.1 原话："裁判模型打分会产生 token 消耗，请在严格验证提示词准确性后再启动任务"）。**经验系数：开发调试阶段的消耗约为上线稳态的 2-4 倍。**

> **与 tuning-handbook 当日实抓数据互引**：Anthropic（Sonnet 5 输入 $2/输出 $10、缓存读 0.1×）、OpenAI（gpt-5.2 $1.75/$14、缓存输入 10%）、Gemini（3.8-flash $0.75/$3.75）、DeepSeek（缓存命中价为未命中的 2-3.3%、错峰一律半价）——四家官方定价页 2026-09-28 实抓的完整速查表见 [Agent调优手册 §6.6](../tuning-handbook/Agent调优手册.md)；缓存策略（稳定前缀放前面是成本第一杠杆）见其 §2.4，批处理/错峰折扣与成本-质量-延迟取舍见其 §7。报价时两表并用，以厂商定价页当日核对。

估算表模板（填例：日均 2000 次会话的知识助手，单次平均 输入 3k tokens（含检索内容）+ 输出 0.8k tokens，缓存命中率 60%）：

| 项目 | 计算 | 月消耗 | 说明 |
|---|---|---|---|
| 输入（缓存命中） | 2000 次 × 3k × 60% × 30 天 = 1.08 亿 tokens × ¥2/M | ¥216 | 前缀稳定才吃得到缓存：系统提示词固定、知识库检索内容前置 |
| 输入（未命中） | 2000 × 3k × 40% × 30 = 0.72 亿 × ¥8/M | ¥576 | |
| 输出 | 2000 × 0.8k × 30 = 0.48 亿 × ¥28/M | ¥1,344 | 输出是大头：控制回答长度是最有效的省钱杠杆 |
| 联网搜索/工具调用 | 按 <次数×单价> | <计> | 平台计费项逐项核 |
| 评测消耗（一次性/回归） | 50 条 × 3 版本 × (调用+裁判) | <计> | 每次发布前回归都花这笔 |
| **稳态月成本** | | **约 ¥2,150 + 工具/评测** | × 冗余系数 1.3（峰值与重试）≈ ¥2,800 |

要点：①表里**每一行都要能对到监控数据**（上线后用实际消耗回填校准）；②成本突增排查见 §8 故障树第 6 类；③单会话 token 基线可以用 [tuning-handbook 实验框架](../tuning-handbook/code/mini_tuning_lab.py) 的 `avg_tokens` 指标在开发期就测出来——调优（砍提示词、控输出长度）对成本的影响先在实验环境量化再上线（闭环方法论见 [Agent调优手册 §1](../tuning-handbook/Agent调优手册.md)，成本-质量-延迟取舍见其 §7）。

### 7.2 人天估算方法

- **有模板 ÷1，首次 ÷2**：§5 六件套里写过的东西，第二个项目直接套 → 按模板估；第一次踩的类型，按"最顺情况 × 2"估（AI 交付项目的偏差几乎全是负向）。
- **工作类型拆分**（知识助手类项目的实测结构，供校准）：需求诊断与文档 25-30% / 搭建与调试 30% / 评测与修复 20-25% / 会议沟通与培训 15-20%——**纯搭建只占三分之一**，报价时按全周期算，别按"搭个机器人两天"算。
- **客户配合度系数**：资料齐、接口现成、有运维 owner → ×1.0；每缺一项 +15-25%（缺接口排期最贵）。
- **估算粒度**：按 §1.2 阶段估 + 每阶段给区间（下限=顺，上限=含 §3.4 黄红项的应对），合同写区间价或封顶价。

### 7.3 报价结构与 ROI 话术

**报价结构**（分层报，别报一口价）：
| 层 | 内容 | 定价方式 |
|---|---|---|
| 一期交付 | 固定范围（§5.1）的交付实施 | 人天 × 单价（或固定总价+封顶） |
| 运营托管 | 周检/月检/badcase 回归（§5.6） | 月费（按 SLA 分档） |
| 变更与二期 | CR 按 §6.3 评估 | 按 CR 计价 |
| 平台与资源 | ADP 订阅、模型 token、专线 | 实报实销或按量转售（透明列明，别赚差价——信任资产） |

**ROI 话术**（对立项领导的语言）：
- 省人力：`（替代工时 × 人力单价 × 12 - 年运营成本）`——用 §5.1 的现状基线数字，别用行业 averages；
- 提速：`单次处理时长 6 分钟 → 1 分钟，日均 N 单 → 折合 <N> 个 FTE 的窗口释放`；
- 口径一致（风险类）：`口径不一导致的返工/客诉单量 × 单均成本`——金融/医药/法务场景这条最有说服力；
- 一句话收口："首年 ROI = <X>，回收期 <Y> 个月，前提是验收指标表（§5.3）达成"——**把 ROI 和 DoD 绑在一起报**，既诚实又专业。

## 8. 现场排障速查

方法论先行（ADP 4.1 单次调试五步法 + [workflow-handbook §6](../workflow-handbook/Agent工作流编排手册.md) 三层定位）：**先问三句——触发了没有？经过了哪些节点？失败在哪个节点？** 再按下面故障树查。改动纪律：一次只改一个变量（否则无法归因）；每次排查留六项记录（问题/期望/实际/归因/动作/复测——ADP 4.1 的六项记录，直接成为评测集样本）。

### 8.1 故障树六类

**① 模型超时 / 无响应**
```
现象：请求超时或长时间无回复
├─ 单次偶发 → 重试 + 幂等保护（workflow-handbook §5 军规①）
├─ 输入过长（含检索内容）→ 压缩检索条数/截断策略/切分粒度
├─ 模型配置错误（思考模型参数/最大输出）→ 核对模型设置
├─ 高峰限流 → 降级：切换备选模型 / 排队机制 / 非核心功能降级
└─ 持续且平台侧 → 查平台状态页，按 §8.3 升级
```

**② 检索不准（答非所问 / 该答不答）**——最高频类
```
现象：答案错误或漏答
├─ 该答不答 → 知识库有没有这条？（没有→补资料，别调模型）
│   ├─ 有但没召回 → 同义词缺失（用户换说法，ADP 3.2 Step9）→ 补同义词组
│   ├─ 召回了但被淹没 → 切分粒度问题 → 调切分方式（按标题/按行）
│   └─ 表述与库内口径冲突 → 版本问题（引用旧口径）→ 过期资料下线
├─ 答非所问 → 意图路由错误？（ADP 3.3 的意图分支先查）
│   └─ 检索范围过宽 → 按知识库范围限定检索问题（把提取字段拼进检索 query）
├─ 高频题不稳定 → 补问答对直接绑定标准答案（ADP 3.2 Step8）
└─ 系统性偏差 → 跑回归评测集定位类别，按类别修（别逐条救火）
```

**③ 集成失败（接口/工具调用错）**
```
现象：工具调用报错 / 返回结构异常
├─ 鉴权失效 → 凭证过期/轮换（§5.5）→ 更新凭证
├─ 参数错误 → 上游字段没传到（契约断裂，workflow-handbook §3 第一根因）
│   └─ 单节点调试看入参 → 修变量引用/参数提取提示词
├─ 接口变更 → 客户系统改了没通知 → 对接口契约版本
├─ 超时/限流 → 客户侧系统扛不住 → 加重试间隔与熔断，必要时异步化
└─ 重复副作用 → 重试没配幂等 → 立即补幂等键，核查已产生的重复单据
```

**④ 权限问题（越权 / 该看不看）**
```
现象：A 部门看到 B 部门内容 / 合法用户被拒
├─ 越权召回 → 身份校验缺失（只信对话自报身份）→ 接入应用端权限变量（ADP 3.2 权限四条）
├─ 知识库混放 → 默认/共享知识库权限错配 → 拆库 + 检索范围按角色隔离
├─ 提示词越权声明 ≠ 权限隔离（ADP 3.2 原话："提示词中的禁止越权只能辅助约束，不能替代身份校验和检索隔离"）
├─ 合法用户被拒 → 组织调整后授权未更新 → 权限复核流程（§5.6 月检）
└─ 日志无审计 → 补齐：谁在何时问了什么、命中什么、调了什么
```

**⑤ 性能瓶颈（慢 / 并发扛不住）**
```
现象：P95 时延超标 / 并发下跌
├─ 串行链路过长 → 工作流节点并行化（无依赖的分支并行，workflow-handbook §2）
├─ 检索内容过大 → top-k 调优 + 重排序替代全量注入
├─ 模型档位过高 → 分级路由：简单意图走轻量模型（ADP 4.x 的模型选择与路由策略）
├─ 渠道瓶颈 → 渠道侧并发/超时配置核对
└─ 基线缺失 → 先建性能基线（§5.3 指标）再谈优化，避免"感觉变慢"
```

**⑥ 成本突增**
```
现象：月 token 消耗跳升
├─ 会话量涨（好事）→ 与业务确认后调预算
├─ 单会话膨胀 → 检索内容/历史堆积 → 压缩注入、历史窗口截断
├─ 输出失控 → 提示词输出长度约束丢失（最近一次发布改了什么？）
├─ 循环调用 → 工作流回环/agent 死循环 → 步数上限 + 熔断
├─ 缓存命中率归零 → 提示词被"优化"成动态前缀 → 恢复稳定前缀结构
└─ 恶意/异常调用 → 日志找异常模式 → 限流 + 渠道鉴权
```

### 8.2 日志与监控清单

上线第一天就要配好的最小集（ADP 2.3 第七步 + ADP 4.1 日志纪律）：

| 类别 | 监控项 | 告警线（示例） |
|---|---|---|
| 流量 | 请求量、成功率 | 成功率 < 95% |
| 质量 | 拒答率突升（=检索失效前兆）、差评/转人工率 | 转人工率环比 +50% |
| 性能 | P95 时延 | 超验收线 1.5× |
| 成本 | 日 token 消耗 vs 基线 | 日消耗 > 基线 2× |
| 安全 | 越权尝试、异常调用模式 | 任何命中即告警 |

日志纪律三条（ADP 4.1 原话精神）：**最小采集**（只留定位和运营所需）；**脱敏**（姓名/手机号/证件号/薪资/健康字段不入日志明文）；**有限期**（明确保留周期与删除机制，日志不能因"用于调优"无限期全量保存）。

### 8.3 何时升级给研发/平台

自己修（FDE 层）→ 升级（研发/平台层）的判据：

| 自查可修（先做满这些再升级） | 达到即升级 |
|---|---|
| 提示词/知识库/同义词/问答对配置问题 | 平台功能缺陷：同类请求稳定失败于平台节点，且有请求 ID 证据 |
| 工作流变量引用与分支逻辑 | 接口/网关问题在客户系统侧且无权限修改 |
| 评测集建设与回归验证 | 数据面事故：疑似数据泄露/越权，立即升级 + 按预案（§5.6 应急） |
| 重试、幂等、兜底降级配置 | 性能问题已排除配置因素，指向模型服务/基础设施 |

升级提单必带四件（研发同事的真实痛点）："请求 ID / 复现步骤与概率 / 期望与实际差异 / 已排除项清单"。带证据的升级单解决速度差一个数量级。

## 9. 企业案例与工具链

### 9.1 公开 FDE 实践精读（2026-09-28 当日实抓）

**精读一：Palantir 官方博客《A day in the life of a Palantir Forward Deployed Software Engineer》**（[链接](https://blog.palantir.com/a-day-in-the-life-of-a-palantir-forward-deployed-software-engineer-45ef2de257b1)）
一手自述：为什么加入（想直接在真实世界的问题上工作、看到自己的软件被真实用户使用）；典型一天如何在**客户环境**里度过——和客户一起定义问题、在客户数据上写代码、部署进生产环境，然后**盯着真实使用反馈继续迭代**，以及"这次讨论必须开会吗"的会议纪律。与 [FDE转行手册 §1.2](FDE转行手册.md) 的 Echo/Delta 模型互为印证：Palantir 官方对 FDSE 的期待是"像创业公司 CTO——小团队、极少监督、端到端负责"。

**精读二：Latent.Space《Forward Deployed Engineer Best Practices》——Vinoo Ganesh（Kepler 创始人，ex-Palantir/ex-Citadel）**（[链接](https://www.latent.space/p/forward-deployed-engineer-best-practices)，2026-09-28 可访问）
可直接抄进日常工作的七条：
1. **FDE 是产品团队的延伸**，不是销售或服务部门——汇报线挂产品，"每次部署都要产出下次部署能直接用的东西"；以"客户满意但产品没变化"收尾的部署，没有完成 FDE 的使命。
2. **收集名词和动词（collect nouns and verbs）**：摸清这家公司把什么当作真实存在的东西（仓位、交易、对手方…），以及这些名词怎么流动（下单、审批、异常处理）。同一概念在不同部门有不同名字（customer / client / billing entity / org_id），**定义的接缝就是系统断裂的地方**。
3. **观察而非访谈**：§2.2 的 Parquet 查看器案例（17 小时 → 2 小时）出自此文。
4. **把"硬正确性"做进平台**：Kepler 的不变量是 provenance（溯源）——每个数字必须能追到源头，误解表现为系统报错而不是貌似合理的错误答案；**系统不许围绕坏数据即兴发挥**——默默绕过编码错误的系统，永远不会告诉你编码错了。
5. **每个临时补丁都会变成你的资产**：一个下午写的留存脚本 `vinoo.groovy` 在一个约 10 万人的客户那里跑了一年。"你交付的每个捷径都会变成你要养的东西"——所以要知道哪些修复属于平台、哪些故意丢弃。
6. **二手客户知识靠不住**：Palantir 2013 年的 Phoenix 交易存储在测试里正常，到了银行 OOM（内存溢出）——因为空时间戳落到 epoch，而"没有人在那栋楼里看它跑生产数据"。能驻场就是优势。
7. **护城河 = 在平台里积累的、持续更新的、经过验证的行业运作知识**；竞争对手可以挖走工程师，但抄不走"被现实反复纠错"的循环。识别真 FDE 的标准：**"最后回来改变产品走向的工程师"**，而不是"给客户交付最多的那些"。

**精读三：Hashnode《A Complete 2026 Guide to the Forward Deployed Engineer》**（[链接](https://hashnode.com/blog/a-complete-2026-guide-to-the-forward-deployed-engineer)）
- **四段交付环**：scoping（界定）→ prototyping（PoC）→ production（生产部署）→ feedback（反哺产品/研究团队）——与 §1.2 七阶段互相印证。
- **"沙盒演示只是工作的 20%"**：其余 80% 是企业 SSO（单点登录）、遗留 ETL、数据驻留、合规与安全团队的政治——作者称之为 integration wall（集成墙）。**这正是本册 §2.1 第三组问题和 §3.4 清单存在的原因。**
- **T 型能力画像**：深轴（Python/SQL/云/容器 + 2026 年的 AI FDE 条目：RAG、微调、向量库、LangGraph/CrewAI 编排、评测框架、LangSmith/Brainstorm/HoneyHive 可观测）+ 广轴（客户同理心、grit 与完全所有权、问题分解、产品感）——与 [FDE转行手册 §3 能力模型](FDE转行手册.md) 一致，国内平台技能（如 ADP）补上平台轴。
- **面试/分解指导可直接用于需求诊断**：别跳到方案——先澄清目标/用户/数据质量与新鲜度/约束/预算/工期；把问题分块；提出"AI 复杂度之前先交付价值的最小 MVP"；大声说出取舍（Kafka 还是简单轮询）。

## 10. FAQ 与上手清单

### 10.1 FAQ（上岗首季高频十问）

**Q1：客户的需求大到做不完怎么办？**
回到 ADP 3.1 的切口原则：第一期只做"能闭环、可验收"的部分，其余全部写进 out of scope 并给二期路线图（§2.3/§5.2 第 9 节）。把"做不完"翻译成"分期计划"。

**Q2：销售已经答应了客户 XX 功能，技术上根本不现实怎么办？**
不要独自消化。立即用 §6.4 第 3 行的口径找销售和客户三方对齐：偏差 + 可行替代 + 对验收标准的影响表。拖到交付期才说，代价是三倍（返工 + 信任 + 验收）。

**Q3：客户不给数据/接口，要求"先做个效果看看"？**
用 mock 明示口径（§4.2）：结构保真、页脚声明、效果承诺以真实数据 POC 复测为准。同时把"数据可得性"标红（§3.4 第 1 项）书面同步——这是项目最大风险，不是你的态度问题。

**Q4：怎么判断该用工作流还是让模型自由发挥？**
一个变量：控制流（§3.1）。步骤能枚举、错一步代价高 → 工作流；写不死 → agent/Claw。判不准时选便宜的先跑：标准模式冷启动最快，跑不通再升级模式（升级有序，别从 Claw 开始）。

**Q5：评测集什么时候建？建多大？**
主链路跑通后建（ADP 4.1：过早建评测集，样本过期、结果无法归因）；首发 ≥50 条五类覆盖（§5.4），之后随 badcase 持续增长。评测集是项目第一资产，比代码还值得投入。

**Q6：客户说"感觉不够智能"，验收卡住？**
把"感觉"翻译成可测用例（§6.5 第三类）：逐条列出具体问法与期望，范围内的修复，范围外的进 CR。"感觉"不进验收报告，用例进。

**Q7：现场写的临时脚本怎么管理？**
建补丁台账：脚本、解决什么、影响面、是否值得反哺平台、废弃条件（§9.1 精读二第 5 条的教训）。台账每月清一次——该晋升的晋升，该销毁的销毁，绝不留无主脚本。

**Q8：上线后我该撤到什么程度？**
按 §5.5 的交接确认单：接收人每项实操当场跑通签字后才撤。撤场不等于断联——运营托管（§7.3 月费）是更健康的持续模式，也是 FDE 复利的一部分。

**Q9：一个人被当三个人用（方案/开发/运维都找我），怎么排优先级？**
顺序：线上事故 > 验收期项目的证据链 > 在建项目 > 新需求诊断。每类都有模板兜底（§8 / §5.4 / §5.2 / §2），**模板是你并发三个角色的唯一方式**。

**Q10：什么值得沉淀成个人资产？**
三样：行业知识库（名词与动词 + 权威口径表，§9.1 第 2 条）、评测集与 badcase 库（可跨项目复用）、模板库（§5 六件套的你的版本）。国内自由职业 FDE 的经验：10+ 个行业技能包是接单底气（[转行手册 §2.3](FDE转行手册.md)）。
