## 一、LangChain 是什么：一分钟定位

**LangChain 是一个"组件 + 编排"框架**：它把调用 LLM（Large Language Model，大语言模型）需要的通用件——消息格式、提示词模板、输出解析、工具调用（tool calling，让模型发起函数调用的机制）、RAG（Retrieval-Augmented Generation，检索增强生成）组件——做成统一接口，再用一个表达式语言（LCEL）把它们串成链。

2026 年的 LangChain 1.x 时代，它明确定位为 **"The agent engineering platform"**（顶层 README:12）。两个关键事实：

1. **复杂编排下沉到了 LangGraph**（README:42 明确引流）。LangChain 1.x 的 `create_agent` 内部就是把 agent 编译成 LangGraph 的 `StateGraph`（见本文第十节）。
2. **LangGraph 可以脱离 LangChain 单独使用**。官方文档原话："you don't need to use LangChain to use LangGraph"（docs.langchain.com/oss/python/langgraph/overview，2026-09-27 访问核实）。

一句话记住两者关系：**LangChain 管"零件和标准件"，LangGraph 管"引擎和流水线"；v1 时代 LangChain 的官方 agent 就是用 LangGraph 引擎组装出来的。**

官方立场文章（讲清何时用哪个）：langchain.com/blog/how-to-think-about-agent-frameworks（Harrison Chase, 2025-04-20，多数第三方对比文都是它的转述）。

## 三、预备：8 个核心概念

| # | 概念 | 英文 | 一句话 | 源码位置 |
|---|---|---|---|---|
| 1 | 可运行单元 | Runnable | 一切组件的统一协议：有 invoke/batch/stream 三件套 | `runnables/base.py:133` |
| 2 | 链式表达 | LCEL（LangChain Expression Language） | 用 `\|` 把组件串成链的表达式语言 | `runnables/base.py:648` |
| 3 | 聊天模型 | Chat Model | 把"消息列表进、消息出"统一化的模型封装 | `language_models/chat_models.py:284` |
| 4 | 消息 | Message | Human/AI/Tool/System 四类消息对象 | `messages/base.py:93` 等 |
| 5 | 工具 | Tool | 带参数 schema（模式）的可调用函数，模型可点名调用 | `tools/base.py:433` |
| 6 | 提示词模板 | Prompt Template | 带变量的模板，渲染后产出消息 | `prompts/prompt.py:24` |

先记住一个总纲：**core 里所有东西都实现了 Runnable 协议**。模型、提示词、解析器、工具甚至普通函数，全都能 invoke，全都能用 `|` 串。学会一个，等于学会全部。

**最重要的架构认知：组合子层不知道组件层的存在。** `RunnableSequence.invoke` 只会依次调 `step.invoke`——每个 step 是提示词、模型还是解析器，它一概不关心，也不关心回调是谁（config 里带什么就用什么）。这和 01-claude-code 的"内核不知道界面的存在"是同一种设计哲学：**把稳定的编排逻辑和易变的具体能力彻底分开。**

## 五、LCEL 精读：`a | b` 到底发生了什么

### 5.1 协议本体：Runnable（base.py:133）

```python
class Runnable(ABC, Generic[Input, Output]):   # base.py:133
```

泛型基类：每个 Runnable 声明输入输出类型。核心三件套 `invoke`（单条）、`batch`（批量并发，base.py:931）、`stream`（流式）。所有组合子都是它的子类或函数。

### 5.2 管道符的实现：`__or__`（base.py:648）

```python
    def __or__(                                  # base.py:648-673
        self,
        other: Runnable[Output, Other]
        | Callable[[Iterator[Output]], Iterator[Other]]   # 生成器函数
        | Callable[[Output], Other]                       # 普通函数
        | Mapping[str, Runnable[Output, Any] | Callable | Any],  # 字典
    ) -> RunnableSerializable[Input, Any]:
        ...
        return RunnableSequence(self, coerce_to_runnable(other))
```

> **[注]** LCEL 的魔法就这一行：`a | b` 不是什么 DSL（Domain-Specific Language，领域专用语言），就是 Python 的运算符重载。右侧可以是 Runnable、函数、字典（字典会被包成 RunnableParallel），统一经 `coerce_to_runnable`（base.py:6640）归一化，再装进 `RunnableSequence`。`__ror__`（base.py:697）是对称的反向版本：处理 `dict | runnable` 这种左侧不是 Runnable 的写法。

### 5.3 串行管道：RunnableSequence（base.py:3075）

```python
class RunnableSequence(RunnableSerializable[Input, Output]):   # base.py:3075
    def __init__(self, *steps, name=None):       # 3169
        # 关键行为：把嵌套的 RunnableSequence 拍平成一级 steps 列表
        # 所以 (a|b)|c 和 a|(b|c) 拼出来都是 [a,b,c] 一层
```

> **[注]** `__init__`（3169-3208 行）在拼接时把子序列展开拍平，保证链不会越拼越深——`invoke`（3430 行）就是普通的 for 循环依次调 `step.invoke`，把上一步输出传给下一步，并用 `patch_config` 给每步挂上子回调（回调树，见第六节）。第一个 step 额外透传 `**kwargs`（3453-3456 行）——这就是为什么链首可以是 `prompt` 且能把运行时变量带进去。

### 5.4 批量并发：batch（base.py:960-979）

```python
        with get_executor_for_config(configs[0]) as executor:
            return list(executor.map(invoke, inputs, configs))
```

> **[注]** `batch` 默认就是"线程池并发跑 N 次 invoke"：每个输入配一条独立 config（`get_config_list`），并发度受 `max_concurrency` 键控制。`RunnableParallel.invoke`（4139-4189 行）的 fan-out 同理——`executor.submit` 每个分支，子 run 命名 `map:key:{key}`。**LangChain 的"并行"没有黑魔法，就是 Python 标准库线程池 + config 传递（第六节）。**

### 5.5 动态组合的两个彩蛋：RunnableLambda（base.py:4703）

`RunnableLambda._invoke`（5156 行起）藏了两个值得知道的行为：

```python
        if inspect.isgeneratorfunction(self.func):    # 5163
            for chunk in call_func_with_variable_args(...):
                output = output + chunk   # 生成器函数 → 自动"流式累积"语义
        ...
        if isinstance(output, Runnable):              # 5183
            output = output.invoke(input_, patch_config(config,
                recursion_limit=recursion_limit - 1)) # 返回 Runnable → 递归调用
```

> **[注]** ① 函数 yield 多段输出时，LangChain 会把它们逐段相加——这就是"为什么 lambda 里 yield 能参与流式"；② 函数返回另一个 Runnable 会被继续执行，消耗 `recursion_limit`（默认 25，config.py:109-113）——这是 LCEL 的动态组合能力，也是防无限递归的闸门。

### 5.6 路由：Branch 与 Router

- `RunnableBranch`（branch.py:43）：`invoke`（185-241 行）逐个求值条件，首个为真则执行该分支，for-else 全不命中走 `default`。
- `RouterRunnable`（router.py:46）：极简，`invoke`（107-117 行）读 `input["key"]` 选分支、`input["input"]` 透传。

## 六、RunnableConfig：config 怎么沿链与线程传递

**位置勘误**：`RunnableConfig` 不在 schema.py（那里只有流式事件 TypedDict，schema.py:56-188），而在 `runnables/config.py:57`。

```python
class RunnableConfig(TypedDict, total=False):    # config.py:57
    # 8 个键（80-128 行）：
    # tags / metadata / callbacks / run_name / max_concurrency /
    # recursion_limit / configurable / run_id
```

三个关键函数构成 config 传递机制：

1. **`ensure_config`（config.py:255-308）**——先从 `ContextVar`（上下文变量，Python 标准库的线程隔离全局量）取父链 config 打底，再合并显式传入的 config；**未知键一律塞进 `configurable`（293-296 行）**。这就是"为什么你在任何节点里都能拿到 config"的隐式传递实现。
2. **`patch_config`（config.py:357）**——子调用前把 `callbacks` 换成父 run 的 child 回调。整棵回调树（LangSmith 追踪的基础）就是靠每次递归 patch 一层层长出来的。
3. **`ContextThreadPoolExecutor`（config.py:607-628）**——并发时跨线程保 config 不断链的核心 5 行：

```python
        return super().submit(                       # config.py:610-628
            cast("Callable[..., T]",
                 partial(copy_context().run, func, *args, **kwargs))
        )
```

> **[注]** 每个提交到线程池的任务先 `copy_context()`——把当前上下文（config、tracing 上下文）快照进子线程。没有这 5 行， fifth 节里所有"线程池并发"都会丢回调、丢追踪。这是理解"为什么子线程里还能拿到 config"的钥匙。

## 七、ChatModel 三层结构：invoke → generate → _generate

`chat_models.py`（约 2300 行）是**分层模板的教科书**。四层调用链全部实测：

```
invoke (475)                    第 1 层：Runnable 入口，薄壳
  └─ generate_prompt (1869)     PromptValue 适配
      └─ generate (1592)        第 2 层：批量 + 回调生命周期
          └─ _generate_with_cache (1892)   第 2.5 层：缓存/限流/流式分派
              ├─ _generate (2209)  第 3 层：抽象方法，集成包唯一必实现
              └─ _stream (2255)    第 3 层可选，默认抛 NotImplementedError
```

### 7.1 第 1 层：invoke 是纯薄壳（chat_models.py:483-499）

```python
        config = ensure_config(config)
        return cast(
            "AIMessage",
            cast(
                "ChatGeneration",
                self.generate_prompt(
                    [self._convert_input(input)],
                    stop=stop,
                    callbacks=config.get("callbacks"),   # 透传回调
                    ...
                ).generations[0][0],
            ).message,
        )
```

> **[注]** `invoke` 自己不做任何事：输入转 `PromptValue`、参数透传、结果拆包。逻辑全部下沉——上层接口稳定，下层各自演化，这是"分层降低复杂度"最干净的示范。

### 7.2 第 2 层：generate 是回调生命周期的家（1592-1716 行）

`generate` 先 `CallbackManager.configure`（1653-1664），发 `on_chat_model_start`（1668-1676），逐条调 `_generate_with_cache`（1681-1690），结束统一 `on_llm_end` / `on_llm_error`（1708-1715）。**回调的 start/end 全在这一层管，第 3 层完全无感。**

### 7.3 第 2.5 层：缓存与限流插在哪（1892-2049 行）

- 缓存查询：`llm_cache.lookup(prompt, llm_string)`（1899-1929 行），命中走 `_replay_v2_events_for_cache_hit`（1918-1924，缓存命中还要重放事件！）
- 限流器：在缓存查询之后、真实 API 调用之前（1934-1935）
- 缓存写回：2047-2048 行 `llm_cache.update(...)`

### 7.4 假流式：为什么没实现 _stream 也能 .stream()（chat_models.py:735-740）

```python
        if not self._should_stream(async_api=False, **{**kwargs, "stream": True}):
            # Model doesn't implement streaming, so use default implementation
            yield cast("AIMessageChunk",
                self.invoke(input, config=config, stop=stop, **kwargs))
```

> **[注]** `_should_stream`（549-585 行）判定顺序：子类没覆写 `_stream` → 不走真流式；否则看显式开关/流式回调。不支持流式的模型调 `.stream()` 时，**整段 invoke 一次、包装成单个 chunk 吐出**——接口统一但非真流式。反方向也成立：`_generate_with_cache`（1969-2020 行）在需要时能把 `_stream` 的 chunk 累积回完整 `ChatResult`。两个方向的"伪流式桥接"都在基类完成，子类只需实现最小接口。

### 7.5 集成包对照：BaseChatOpenAI（partners/openai/.../chat_models/base.py:783）

- **直接继承 core 的 BaseChatModel，无中间层**（783 行）。
- `_generate`（1927-2049 行）三路分派：带 `response_format` 走 `completions.parse`；命中 Responses API 走 `responses.create`；否则普通 `client.create`。
- `_stream`（1850 行）逐 chunk 解析（1609 行 `_convert_chunk_to_generation_chunk`）。
- 厂商错误统一转成 LangChain 标准异常层级（638-676 行）。

**这个文件是"三层协议在真实厂商落地"的最佳对照读本**——读完它你就知道写一个新模型集成需要实现什么：`_generate`（必须）、`_stream`（可选）、消息格式转换。


## 附录 A：术语表

### 基础概念
- **LCEL**（LangChain Expression Language）：LangChain 表达式语言；用 `|` 组合组件的语法糖。
- **Runnable**：可运行单元协议；invoke/batch/stream 三件套。
- **Chat Model**：聊天模型；消息列表进、AIMessage 出的统一封装。
- **Tool Calling**（工具调用）：模型输出结构化 tool_calls、由应用执行再回填的机制。
- **RAG**（Retrieval-Augmented Generation，检索增强生成）：先检索外部知识再让模型作答。
- **ReAct**（Reasoning + Acting）：推理-行动循环，agent 的经典形态。
- **Middleware**（中间件）：v1 中在模型调用前后织入逻辑的钩子系统。

### Python / 工程相关
- **TypedDict**：带类型注解的字典形状定义（state/config 都用它表达）。
- **Annotated**：类型注解元数据；LangChain 用它挂 reducer（LangGraph 侧）与 schema 信息。
- **ContextVar**（上下文变量）：Python 标准库的线程隔离全局量，config 隐式传递的载体。
- **ABC**（Abstract Base Class，抽象基类）：强制子类实现抽象方法的机制。
- **Pydantic**：Python 数据校验库；工具 schema 与结构化输出的校验底座。
- **fan-out**（扇出）：一个输入并发分发给多个分支的模式（RunnableParallel）。
- **薄壳**（thin wrapper）：只做转发不做逻辑的包装层（如 BaseChatModel.invoke）。
