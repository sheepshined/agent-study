## 一、LangGraph 是什么：一分钟定位

**LangGraph 是一个低层编排框架与运行时（"low-level orchestration framework and runtime"，官方 overview 页原文，2026-09-27 访问核实）**。核心两件事：

1. **把 agent / 工作流建模成带状态的有向图**：节点（node）是函数，边（edge）决定走向，所有节点通过读写共享状态（state）通信。
2. **用 Pregel 模型执行这个图**：借 Google Pregel 论文（2010）的 BSP（Bulk Synchronous Parallel，整体同步并行）计算模型——一拍（superstep）内所有活跃节点并发执行，节点间不直接通信，写入只在一拍结束后统一生效。

官方立场：LangGraph 可以脱离 LangChain 独立使用；LangChain 1.x 的 `create_agent` 则是构建在它之上（07 号文档第十节）。一句话记住：**LangGraph = 图的建模 API（StateGraph）+ Pregel 运行时（pregel/）+ 持久化（checkpoint）+ 人在环（interrupt）。**

| # | 概念 | 英文 | 一句话 | 源码位置 |

| 7 | 检查点保存器 | Checkpointer | 快照的存取接口；配 thread_id 实现会话记忆 | `checkpoint/base/__init__.py:177` |

先记一个总纲：**LangGraph 的全部执行语义，就是"通道 + 版本号 + 超步"三个词**。后面所有源码都在实现它们。

```
┌───────────────────────────────────────────────────────────────┐
```

**最重要的架构认知：节点之间从不直接调用。** 你 `add_edge("a", "b")` 连出"先 a 后 b"，运行时真正发生的是：a 写通道 → 版本号前进 → b 因看到新版本而被规划为下一拍任务。**"边"是规划规则的语法糖，不是函数调用。** 这就是为什么任意两个节点能天然并发（只要互不依赖同一通道）、为什么任意一拍都能停下来存档。

## 五、建图：StateGraph 精读

### 5.1 节点签名与 reducer 的约定（state.py:131-145）

```python
class StateGraph(Generic[StateT, ContextT, InputT, OutputT]):   # state.py:131
    """A graph whose nodes communicate by reading and writing to a shared state.

    The signature of each node is `State -> Partial<State>`.        # 134

    Each state key can optionally be annotated with a reducer function that
    will be used to aggregate the values of that key received from multiple
    nodes. The signature of a reducer function is `(Value, Value) -> Value`.  # 136-138
    """
```

> **[注]** 两条铁律都在 docstring 里：① 节点返回**部分更新**而非全量 state（LangGraph 只 merge 你返回的键）；② 用 `Annotated[list, add_messages]` 这样的类型注解给键挂 reducer——同一个键被多个节点（或并发的多个任务）同时更新时，靠 reducer 合并而不是报错。

reducer 的合法性校验在 `state.py:1885-1920`：从 `Annotated` 元数据里提取 reducer，校验签名必须是 `(a, b) -> c`（1920 行），否则构造期就报错——错误左移到建图阶段，是个值得学的工程习惯。

### 5.2 三种边（state.py）

| API | 行号 | 语义 |
|---|---|---|
| `add_edge(start, end)` | 928 | 固定边：多个 start 时等**全部**完成再走（979 行存入 `waiting_edges`） |
| `add_conditional_edges(source, path, path_map)` | 982 | 动态边：`path` 函数算出下一个（或多个）节点名；返回 END 则终止 |
| `add_sequence(...)` | 1032 | 线性小链条的语法糖 |

```python
        path = coerce_to_runnable(path, name=None, trace=True)   # state.py:1019
        name = path.name or "condition"                           # 1020
        self.branches[source][name] = BranchSpec.from_path(path, path_map, True)  # 1027
```

> **[注]** 条件边不是"边"，是挂在源节点上的 **branch（分支）声明**：compile 时每个节点带着自己的 branches 列表，执行完该节点后逐个求值 branch 拿目的地。`coerce_to_runnable`（1019）复用了 07 号文档第五节那个 LangChain 函数——条件函数也被纳入统一回调与追踪体系。

### 5.3 compile：从声明到可执行（state.py:1177-1256）

`compile(checkpointer=..., interrupt_before/after=..., store=...)` 做三件事：
1. **schema → 通道**：每个 state 键按注解实例化对应 Channel（LastValue 或带 reducer 的 BinaryOperatorAggregate）。
2. **边 → 触发规则**：静态边和条件边编译成"节点 × 通道触发"的映射（`trigger_to_nodes`）。
3. **装配可执行图**：产出 `CompiledStateGraph`（state.py:1404）——它实现了 Runnable 接口，所以 `graph.invoke/stream/batch` 与 LangChain 组件同构。

`thread_id` 的提示就在 compile 的 docstring 里（state.py:1204-1214）：**启用 checkpointer 后，config 里的 `thread_id` 就是存档槽位的 key**——同一个 thread_id 反复 invoke，状态自动续上（会话记忆）；换一个 id 就是一个新会话。

## 六、通道：状态是怎么合并的

### 6.1 通道协议（channels/base.py:49-112）

```python
    def checkpoint(self) -> Checkpoint | Any: ...     # 49  快照值
    def from_checkpoint(self, checkpoint): ...        # 61  从快照恢复
    def get(self) -> Value: ...                       # 70  读（可能 EmptyChannelError）
    def is_available(self) -> bool: ...               # 75  是否有可读值
    def update(self, values: Sequence[Update]) -> bool: ...  # 90  批量写入+合并
    def consume(self) -> bool: ...                    # 101 消费（一次性通道用）
    def finish(self) -> bool: ...                     # 112 终局通知
```

> **[注]** 全部 9 种通道都实现这 7 个方法——这就是 LangGraph 的"存储接口"。合并语义、消费语义、检查点格式全在通道内部，引擎（第七节）对通道种类无感知。**状态 schema 到通道的映射是 compile 干的，运行时引擎只认 BaseChannel。**

### 6.2 LastValue：默认通道，"每拍只能写一个值"（last_value.py:20）

```python
class LastValue(Generic[Value], BaseChannel[Value, Value, Value]):   # last_value.py:20
    """Stores the last value received, can receive at most one value per step."""

    def update(self, values: Sequence[Value]) -> bool:    # 56
        if len(values) == 0:
            return False
        if len(values) != 1:
            msg = create_error_message(
                message=f"At key '{self.key}': Can receive only one value per step. "
                        "Use an Annotated key to handle multiple values.",
                error_code=ErrorCode.INVALID_CONCURRENT_GRAPH_UPDATE,
            )
            raise InvalidUpdateError(msg)                  # 59-64
        self.value = values[-1]                            # 66
        return True
```

> **[注]** 两个关键行为：① 普通键（不带 reducer）在一拍内被两个并发节点同时写 → 直接抛 `InvalidUpdateError`——这就是新手最常见的 `INVALID_CONCURRENT_GRAPH_UPDATE` 报错的出处；② 报错信息明确指路"Use an Annotated key"——用 reducer 才能合并并发写。

### 6.3 BinaryOperatorAggregate：reducer 通道（binop.py:65）

> **[注]** `Annotated[list, operator.add]` 这类键编译成此通道：一拍收到 N 个值就按二元运算符折叠 N 次（`add_messages` 本质也是它的高级版——按消息 id 去重追加）。143 行就是"reducer 语义"的最终执行处。另外它支持 `Overwrite` 覆写指令（129-141 行）：节点返回 `Overwrite(value)` 可跳过折叠直接改值，一个超步最多允许一个 Overwrite（135-138 行，多了照样报错）。

## 七、执行引擎：BSP 超步主循环

### 7.1 引擎自述：官方注释就是最好的教材（main.py:2959-2963）

> **[注]** 四条注释翻译过来：① 计算按"步"推进，只要通道还有更新就继续；② **第 N 步的写入，第 N+1 步才可见**；③ 步进行中通道不可变；④ 写入只在步间统一生效。这三行性质就是 BSP 的定义，而整个引擎就是外面这层 `while tick() → runner.tick() → after_tick()`。

### 7.2 一拍的开始：PregelLoop.tick（_loop.py:599-681）

```python

        # check if iteration limit is reached
        if self.step > self.stop:                             # 607
            self.status = "out_of_steps"; return False        # 608-609
        # prepare next tasks
        self.tasks = prepare_next_tasks(                      # 612-629
            self.checkpoint, self.checkpoint_pending_writes,
            self.nodes, self.channels, ...)
        # if no more tasks, we're done
        if not self.tasks:                                    # 653
            self.status = "done"; return False
        # apply pending writes from a previous loop (断点续跑)
        if not self.is_replaying and self.checkpoint_pending_writes:  # 662
            self._reapply_writes_to_succeeded_nodes(self.tasks)
        # before execution, check if we should interrupt
        if self.interrupt_before and should_interrupt(...):   # 667-671

            raise GraphInterrupt()
        return True                                           # 681
```

> **[注]** tick 只做"规划"不"执行"：算出这一拍该跑哪些任务（prepare_next_tasks，_algo.py:349），没任务就 done。规划的核心规则在 `_algo.py` 的 `prepare_single_task`（524 行）：**节点的 versions_seen 与通道当前版本比对**——某节点读过 version=5 的通道，现在通道已是 version=6，它就有新任务；没变就跳过。这就是"边"的运行时真相：**版本对比触发，而非图遍历。**

```python
            checkpoint["channel_versions"][chan] = next_version
    for chan, vals in pending_writes_by_channel.items():      # 315-323
        if channels[chan].update(vals) and ...:               # ← reducer 在这里被调用
            checkpoint["channel_versions"][chan] = next_version
            updated_channels.add(chan)
    if bump_step:   # 本拍没被更新的通道也推进版本号（step 信号）  # 326-333
        ...
    if bump_step and updated_channels.isdisjoint(trigger_to_nodes):  # 336
        for chan in channels: channels[chan].finish()         # 338 终局通知
```

> **[注]** 一拍结束的完整动作：把所有任务的写入按通道分组 → 调各通道的 `update`（reducer 在此执行，319 行）→ 推进 `channel_versions` → 更新 `versions_seen`（263-269 行，下一拍规划的依据）→ **每拍必存 checkpoint（718 行）**——这就是"任意一拍可恢复"的来源。`bump_step`（326 行）保证"步数信号"也能触发依赖节点（比如用 `int` 键计数的图）。

### 7.5 一拍的一生（时序图）

```
   ┌────────────────────────── 超步 N ──────────────────────────┐
   │ tick()          规划：版本对比 → 任务列表（_loop.py:599）     │
   │   无任务? → done；超步数上限? → out_of_steps                  │
   │   interrupt_before 命中? → 抛 GraphInterrupt 暂停            │
   │ runner.tick()   执行：线程池并发跑所有任务（_runner.py:176）    │
   │   每个任务：读通道 → 跑节点函数 → 产出 writes → commit         │
   │ after_tick()    收尾（_loop.py:683）                         │
   │   apply_writes：reducer 合并 → channel_versions 前进          │
   │   _put_checkpoint：存档（每拍必存，718）                       │
   │   interrupt_after 命中? → 抛 GraphInterrupt                  │
   └─────────────────────────────────────────────────────────────┘
                     │ 下一拍才可见的写入
                     ▼
   ┌────────────────────────── 超步 N+1 ─────────────────────────┐
   │  tick() 重新规划：版本变了才规划新任务……循环至 done             │
   └─────────────────────────────────────────────────────────────┘
```

## 八、Checkpoint：持久化与时间旅行

### 8.1 Checkpoint 结构（checkpoint/base/\_\_init\_\_.py:93-124）

```python
class Checkpoint(TypedDict):                    # base/__init__.py:93
    v: int                                      # 96  格式版本，当前 1
    id: str                                     # 98  唯一且单调递增（可排序！）
    ts: str                                     # 103 ISO 8601 时间戳
    channel_values: dict[str, Any]              # 105 各通道的值（反序列化后的快照）
    channel_versions: ChannelVersions           # 110 通道名 → 版本号（单调递增）
    versions_seen: dict[str, ChannelVersions]   # 116 节点名 → 它见过的版本
    updated_channels: list[str] | None          # 122
```

> **[注]** 六个字段就是"时间旅行"的全部家底：`channel_values` 是状态本体，`channel_versions`/`versions_seen` 是"谁该在下一拍跑"的判定依据（第七节 7.2）。`id` 单调递增意味着 checkpoint 历史天然是一条可回放的链（`CheckpointTuple.parent_config` 指向父档，140-147 行）。

### 8.2 BaseCheckpointSaver 与 thread_id（177 行起）

接口层只有抽象方法（put/get_tuple/list/delete_thread 等），`libs/checkpoint-sqlite` 与 `checkpoint-postgres` 各自实现。**学习期用 `InMemorySaver` / `SqliteSaver` 足够；生产用 PostgresSaver。** thread_id 语义（state.py:1204-1214）：同一 thread_id 的多次 invoke 状态自动续接——这就是官方说的"短期记忆"，本质是 checkpoint 链。

### 8.3 何时写档

- **每拍必写**：`after_tick` → `_put_checkpoint({"source": "loop"})`（_loop.py:718）
- `durability="sync"` 时主循环还会等待落盘完成再继续（main.py:2987-2988）
- 中断/恢复全部基于已存档：断点续跑时 tick 里 `_reapply_writes_to_succeeded_nodes`（_loop.py:736-748）把上次成功任务的写回放、失败任务重跑（跳过 ERROR/INTERRUPT 等控制信号，746 行）

## 九、中断与人在环：interrupt

### 9.1 interrupt 的三条语义（types.py:887-909 docstring）

```python
def interrupt(value: Any, *, response_schema=None) -> Any:   # types.py:887
    """Interrupt the graph with a resumable exception from within a node.
    ...
    The graph resumes from the start of the node, **re-executing** all logic.  # 902
    If a node contains multiple `interrupt` calls, LangGraph matches resume
    values to interrupts based on their order in the node.                     # 904-906
    To use an `interrupt`, you must enable a checkpointer.                     # 908-909
    """
```

> **[注]** 三条语义都要背下来：① interrupt 抛 `GraphInterrupt` 异常把图挂起（配合 7.2 的 interrupt_before/after 与 7.4 的每拍存档，状态不会丢）；② **恢复时整个节点从头重跑**——所以 interrupt 之前的副作用（API 调用、写库）要能幂等或挪到节点外；③ 一个节点里多次 interrupt 按**出现顺序**配对恢复值，恢复值来自 `Command(resume=...)`；④ 没配 checkpointer 直接报错——中断依赖存档。

### 9.2 典型用法（types.py:932-954 官方示例浓缩）

```python
def node(state: State):
    answer = interrupt("what is your age?")   # 第一遍：抛异常挂起；恢复后拿到人类输入
    return {"human_value": answer}

graph = builder.compile(checkpointer=InMemorySaver())
# 第一次 invoke → 结果里带 __interrupt__
# 第二次 invoke(Command(resume=18), config={"configurable": {"thread_id": ...}})
#   → 节点重跑，interrupt 返回 18
```

**与六家 agent 的对照**：01-claude-code 的权限确认是"同步弹窗阻塞进程"（canUseTool 回调），LangGraph 的 interrupt 是"存档挂起、跨进程恢复"——后者才能服务长时间人类审核（几小时甚至几天），这是为什么 LangGraph 反复强调"durable execution（持久化执行）"。

## 十一、流式输出

`Pregel.stream`（main.py:2616 起，多重重载）的 `stream_mode` 支持（实测与 docstring）：

| 模式 | 产出 |
|---|---|
| `values` | 每拍结束后的完整状态（7.4 的 values emit，_loop.py:700-707） |
| `updates` | 每个节点返回的部分更新 |
| `messages` | LLM 的消息分片（token 级，走 LangChain 回调体系） |
| `custom` | 节点里 `get_stream_writer()` 手写的进度事件 |
| `debug` | 任务规划/检查点等全量调试事件（tick 里的 tasks/checkpoints emit） |

可多选（`stream_mode=["updates","messages"]`），输出为 `(mode, payload)` 元组。实现要点：任务并发执行时结果先进线程安全队列（stream/），主循环通过 waiter（main.py:2936-2957）等数据就绪再 `yield`——**流式不是异步魔法，就是"生产者队列 + 主循环排水"**。

## 十二、与六家 agent 的对照

把 LangGraph 放进本工作区的坐标系：

| 维度 | 01-claude-code | 04-zcode（dynamic-workflow） | 08-langgraph |
|---|---|---|---|
| 执行模型 | 单文件 while 主循环（query.ts，工具驱动） | TS 脚本的控制流 + 子代理 fan-out | BSP 超步 + 通道版本触发 |
| 状态 | 消息数组（进程内） | 脚本变量 | 显式 state schema + reducer |
| 持久化 | compact 压缩 + 会话文件 | 运行日志 | 每拍 checkpoint，任意拍恢复 |
| 人在环 | 同步权限弹窗（canUseTool 回调） | 脚本内确认 | interrupt 存档挂起 + Command 恢复 |
| 并发 | 顺序工具调用为主 | subagent 并行 | 同拍多任务线程池（apply_writes 合并） |
| 扩展点 | 工具/MCP/Skill | 脚本即编排 | 节点/分支/中间件/checkpointer 全可换 |

三个值得一想的问题：
1. **claude-code 为什么不用图？** 它的流程高度固定（一个 ReAct 环 + 权限），硬编码循环最简单；LangGraph 的图是为"结构需要变化"的工作流（多智能体、动态路由、人审分支）付的成本。
2. **zcode 的 dynamic-workflow 和 LangGraph 像在哪？** 都是"把编排从模型手里拿回来交给程序"——但 dynamic-workflow 是普通控制流（if/loop），LangGraph 是声明式图 + 引擎执行，后者买到了 checkpoint/interrupt/时间旅行。
3. **BSP 模型对 agent 的意义？** 同拍多任务天然并行（map-reduce 式 subagent），且"拍间统一写入"给了确定性重放——这对调试 agent 至关重要。

## 附录 A：术语表

### 框架概念
- **BSP**（Bulk Synchronous Parallel，整体同步并行）：并行计算模型——计算分成"超步"，超步内各单元并发、互不通信，超步间同步一次。Pregel 论文的骨架。
- **superstep**（超步）：BSP 的一拍；LangGraph 里就是一次 tick → 并发执行 → apply_writes。
- **Channel**（通道）：状态键的运行时载体，封装合并/消费/快照语义。
- **reducer**（归约器）：`(Value, Value) -> Value` 的合并函数，挂在 state 键上。
- **Checkpointer**（检查点保存器）：状态快照的存取接口；`thread_id` 是存档槽位 key。
- **durable execution**（持久化执行）：任意一拍可存档、可恢复的执行语义。
- **interrupt / resume**（中断/恢复）：节点内抛异常挂起，人类输入后从节点头重跑。
- **Command**（命令）：节点返回值，可同时带状态更新、走向指令（goto）与 resume 值。
- **Send**（发送）：动态给节点发私有输入，实现 map-reduce 式分发。

### Python / 工程相关
- **TypedDict / Annotated**：字典形状声明 / 类型注解元数据（reducer 靠 Annotated 挂载）。
- **ContextVar**：线程隔离的上下文变量（07 号文档第六节同款机制）。
- **Pregel**：Google 2010 年的大图计算论文/系统；LangGraph 引擎的同名灵感来源。
- **时间旅行**（time travel）：基于 checkpoint 链回到任意历史拍、改状态重算。
- **幂等**（idempotent）：同一操作执行多次与一次效果相同——interrupt 重跑语义下节点副作用必须幂等。
