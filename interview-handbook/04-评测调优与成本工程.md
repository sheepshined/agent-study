## 题目正文

> **Q061. 怎么向面试官证明你的 agent 应用"变好了"？**（难度：初 ｜ 频次：高）
> - 考察点：有没有"用数字说话"的评测体系意识，还是停留在"demo 跑通了、感觉变好了"——这是 evals（评测）素养的第一道分水岭。
> - 参考回答：
>   - 评测是"demo 者与能上线者的分水岭"：FDE 社区 16 个头部仓库里 11 个把 Evals 列为硬技能；MIT NANDA 报告指出 95% 的企业 GenAI 项目无可入账价值，根因之一就是没有验收标准。
>   - "变好"必须由固定评测集上的指标定义：按被测粒度分三层——单元评测（单工具/单 prompt/检索命中）、轨迹评测（工具调用序列、步骤效率、失败归因）、端到端评测（任务完成率），层的顺序不可跳。
>   - 按时机分三种：离线评测（发布前跑固定评测集，是安全网）、在线评测（生产流量抽样打分，是体温计）、灰度回放（生产 trace 回流成数据集再离线回放，是传送带）。
>   - 判据第一原则：能用代码验证的绝不交给 LLM 打分——状态断言（跑测试/查数据库）> 精确匹配 > 可判定规则 > rubric + LLM judge（LLM 当评委）；SWE-bench 用单元测试、τ²-bench 用数据库最终状态做判据，这是它们可被信任的原因。
>   - POC 验收的标准动作：固定评测集前后跑基线 vs 方案、出对比报告——FDE Capstone 验收标准原文就是"有评估报告（基线→改进）"。
>   - 迭代护航：任何变更过回归集，回答"修复旧问题有没有引入新错误"——这是评测集三用途（覆盖性验证/版本对比/回归验证）之一。
> - 追问与陷阱：
>   - 追问"没有标注团队、预算很少怎么起步"：用单次调试的六项记录（问题/期望/实际/归因/动作/复测）攒样本，每条修好的 bug 天然是一条带期望输出的评测样本。
>   - 追问"离线分数和线上表现不一致怎么办"：离线集再好也有分布偏差，在线指标是唯一真实信号，两者要并排看、互相旁证。
>   - 常见错误：只报一个整体通过率就宣布"变好"，或拿演示样例当验收证据——没有分场景指标与基线对比的报告，在面试官眼里等于没有评测。
> - 加分项：能画出腾讯 ADP 课程的"五堵墙"（知识/工具/流程/权限安全/评测运营），指出评测运营是最后一堵但必须最先问——一开始就没有成功判据，后面所有工作都失去对齐目标。
> - 延伸阅读：[eval-handbook §1 为什么评测是 agent 落地的第一问](../eval-handbook/Agent评测与质量工程手册.md)、[eval-handbook §2 评测谱系总览](../eval-handbook/Agent评测与质量工程手册.md)、[FDE转行手册 §8.6 高频面试题](../fde-handbook/FDE转行手册.md)

> **Q062. LLM-as-judge 是什么？它有哪些偏差？怎么校准？**（难度：初 ｜ 频次：高）
> - 考察点：是否知道 LLM-as-judge（LLM 当评委）是"放大器不是标尺"——未经校准的 judge（裁判）是噪声源，以及有没有系统的偏差防御与校准方法。
> - 参考回答：
>   - 定义：用一个通常更强的模型，按书面评审协议给被测输出打分——它是唯一能把"开放式质量"（语气、详略、风格）规模化的手段；ADP 课程把"裁判模型打分/规则打分/代码打分"并列为三种打分方式。
>   - 三种评审形态：pointwise（逐点评分，答"及格线"）、pairwise（两两对比，答"谁更好"）、listwise/参照评分（多输出排序或给参照答案再评）。
>   - 四个已知偏差：位置偏差（pairwise 偏好某个位置——交换顺序重评，AB 与 BA 各评一次、一致才采纳、翻转判平）；长度偏差（偏好长答案——rubric 里显式写"简洁性"维度）；自我偏好（偏好同源同风格输出——judge 与被测模型不同家族、多 judge 投票）；随机性（温度 0 + 强制 JSON 结构化输出）。
>   - 第五个更隐蔽的是判据泄漏：judge 提示词里复述了期望答案导致"背答案式打分"——裁判提示词必须引用评测集的字段（query/reference），而不是把答案写进提示词正文。
>   - 校准（calibration）流程：抽 50-100 条样本，人按同一 rubric（评分细则）背靠背打标 → judge 跑同一批 → 计算一致率与 Cohen's κ（kappa，去随机一致后的加权一致度，κ>0.6 可用、>0.8 可信）→ 不达标的维度回去改 rubric，不要直接上线。
>   - 协议五件套：任务上下文（judge 要知道 agent 的职责边界）、分维度 rubric（1-5 档语义锚定，每档写清"什么样的回答算 X 分"）、强制 JSON 输出带证据字段（先摘录原文再打分，压幻觉判分）、引用式打分、低置信度出口（输出 needs_human 而不是硬给分）。
>   - 仲裁结构是金字塔不是全量 judge：规则判据先行 → judge 处理开放维度 → 低置信度/高分歧进人审；上线后永远保留约 10% 的人审抽样监控 judge 漂移，换 judge 模型版本 = 重新校准。
> - 追问与陷阱：
>   - 追问"judge 分数能进回归门禁吗"：校准通过（一致率/κ 达标）才有资格参与门禁，且要周期性用人工标注重校。
>   - 追问"为什么不给 1-10 分取均值"：pointwise 绝对分数的语义随 prompt 微调漂移，改 1-5 档语义锚定才稳。
>   - 常见错误：拿没校准过的 judge 直接当标尺用；pointwise 打 1-10 分然后比较均值。
> - 加分项：能写出 pairwise 交换仲裁的最小实现（AB/BA 两次结论一致才采纳，翻转判 tie），说明理解"位置偏差被显式吞掉而不是随机二选一"。
> - 延伸阅读：[eval-handbook §5 LLM-as-judge](../eval-handbook/Agent评测与质量工程手册.md)、[ADP 课程 4.1 智能体调试与评测基础](../fde-handbook/tencent-adp-fde-course/lessons/4.1_智能体调试与评测基础.md)、[python-handbook §8 评测三件套](../python-handbook/Python大模型应用开发手册.md)

> **Q063. 评测判据有哪些类型？优先级怎么排？**（难度：初 ｜ 频次：中）
> - 考察点：是否掌握成功判据（success criteria）的谱系与"可验证 reward 优先"的第一原则，而不是张口就是"让大模型打个分"。
> - 参考回答：
>   - 五类判据按可靠性从高到低：状态断言（跑测试/查数据库最终状态/编译通过/文件 diff）→ 精确/结构匹配（期望值比对、JSON schema 校验）→ 可判定规则（断言工具调用序列包含/不包含某调用、参数区间）→ rubric + LLM judge（分维度打分表）→ 人工评审（专家按协议打标）。
>   - 人工评审可靠性最高却排最后，因为它最贵——它的位置是当 judge 校准的基准真值与争议样本仲裁者，不是日常打分。
>   - 第一原则：能用代码验证的绝不交给 LLM 打分——头部公共基准的判据全部是可执行验证：SWE-bench 用单元测试、τ²-bench 用数据库最终状态与动作序列、GAIA 用精确匹配、BFCL 用 AST 匹配，这是它们能被信任的原因。
>   - 判据写在设计期、不写在跑分期："期望什么"必须与题目同时冻结，写不出可判定期望的题先别进评测集——"无二值成功标准的任务 = 高风险未知项"纪律在数据集层的落地。
>   - 一条题只测一件事：混合判据（既要答案对又要步骤省）无法归因失败原因；步骤效率是轨迹层指标，不要混进端到端判据。
>   - 区分"答案"与"动作"：τ²-bench 的 reward（奖励判据）分两层——该做的动作做了没（actions）与最终状态，答案对但没做必须的动作不算过；业务 agent 几乎都该抄这个设计。
>   - 判定函数返回"判定 + 证据"而不是裸布尔：证据字段（差在哪、命中了什么）供报告与失败归因使用。
> - 追问与陷阱：
>   - 追问"LLM judge 什么时候才该上"：只用于"人的判断本身模糊"的场景（语气、详略、风格），且必须先校准。
>   - 追问"判据要不要覆盖拒答"：要——拒答题/策略题的期望行为是"明确说不知道或转人工"，拒答正确也算通过。
>   - 常见错误：跑分时人肉看答案定对错（既不可复现也不可回归）；或给所有题都上 judge，评测账单超过被测 agent 本身。
> - 加分项：判据函数的签名是这个体系最重要的不变量——换 judge 不换接口（verify(task, output) 返回统一的 Verdict 结构），judge 可以插拔升级而不动评测报告结构。
> - 延伸阅读：[eval-handbook §2.3 判据谱系：可验证 reward 优先](../eval-handbook/Agent评测与质量工程手册.md)、[eval-handbook §4.3 成功判据设计](../eval-handbook/Agent评测与质量工程手册.md)

> **Q064. 为什么改一行 prompt 也要跑回归评测？**（难度：初 ｜ 频次：高）
> - 考察点：有没有回归（regression，回归测试）意识——理解 prompt 是"全局变量"，改动的影响面是全部流量而不是那一个 badcase（坏例）。
> - 参考回答：
>   - agent 是多环节系统（意图理解→检索→规划→工具调用→生成），prompt 是整条链路的共享输入：改一句话改变的是模型行为分布，除今天要修的那类问题外，其它场景同样被改了。
>   - ADP 4.1 的结论："修好一个问题，又引入三个新问题"是常态——回归集的存在就是防"按下葫芦浮起瓢"，评测集三用途之一就是回归验证。
>   - 回归评测三要素：固定评测集 + 固定判据 + 数据集指纹（对全量样本取 SHA-256，两次跑分指纹不同就不是同一场考试，结果不可比）。
>   - 配套纪律是单变量变更：每轮只改一个主要变量（ADP 4.2 原话），否则变好无法归因、变差无法回滚——"改一行 prompt"恰恰是理想的最小变更单元。
>   - 工程落地：评测脚本进 CI，退出码非零卡合并（promptfoo 式门禁）——"变好"由门禁裁决，不由感觉裁决。
>   - 成本上完全负担得起：判据用代码验证零 judge 费；离线跑批用批处理 API 一律 -50%（2026-09-28 四家官方定价页实抓）；高频跑小 dev 集、大版本才跑 held-out（留出集）。
>   - 实测证据：tuning-handbook 的最小实验框架里，v1 版本在 dev 集 8 条上 100% 通过，held-out 复跑只有 75%——dev 全绿不等于 held-out 全绿，这正是每轮都要复测的原因。
> - 追问与陷阱：
>   - 追问"改动很小也要跑全量吗"：分集治理——dev 集每次变更都跑，held-out 只在大版本发布跑，但"跑"这个动作本身不能省。
>   - 追问"用什么当回归集"：生产 badcase 清洗成的回归样本优先——它们是真实分布里真正咬过你的题。
>   - 常见错误：用生产小流量的波动当回归判据——抖动被当回归、回归被当抖动；正确做法是离线固定集裁决 + 在线指标旁证。
> - 加分项：能引用"门禁必须用同一切分的同类指标相比"这条真实踩坑——基线记录里要同时固化 held-out 指标，否则门禁会拿 held-out 成绩比 dev 基线而误报 FAIL。
> - 延伸阅读：[tuning-handbook §1.1 闭环五步](../tuning-handbook/Agent调优手册.md)、[tuning-handbook §9 最小调优实验框架](../tuning-handbook/Agent调优手册.md)、[eval-handbook §2.2 三时机：离线/在线/灰度回放](../eval-handbook/Agent评测与质量工程手册.md)

> **Q065. 单次调试和批量评测的分工是什么？调试五步法怎么走？**（难度：初 ｜ 频次：中）
> - 考察点：是否分得清"调这一条"与"证明整体变好"两件事，以及有没有可复述的单次调试操作规程（ADP 4.1 的课程结论）。
> - 参考回答：
>   - 一句话分工：调试更像"边搭边修"，解决"这一条为什么错、错在哪一环"；评测更像"阶段验收"，证明"整体是否稳定、A 版还是 B 版好"。
>   - 五步法：定目标 → 可解释输入 → 看全链路 → 一次改一个变量 → 复测 + 相邻检查。
>   - "看全链路"是关键动作：不只看最终回复，还要看中间变量、检索结果、节点输出和工具返回——同一个错误可能来自 prompt、知识没命中、节点变量为空、工具返回异常或输出格式不稳定。
>   - 每轮调试产出六项记录：问题、期望结果、实际结果、定位原因、修改动作、复测结果——既是调试纪律，也是评测集最低成本的样本来源。
>   - 正确节奏是三段式：单次调试主链路跑通 → 小样本专项验证 → 评测集批量评测（覆盖性验证/版本对比/回归验证）→ 每次重要优化后回归。
>   - 顺序不可跳：主链路没跑通就上批量评测，失败信号无法归因（可能是变量没传、工具没配好，而不是模型差）；只有调试没有回归，就会反复翻车。
> - 追问与陷阱：
>   - 追问"为什么复测之后还要相邻检查"：一次修改可能影响相邻功能，复测只证明本条修好，相邻检查证明没有顺手改坏别处。
>   - 追问"怎么判断该结束调试"：按问题现象反推最可能出错的环节并验证假设，而不是反复追问直到某次输出"看起来满意"。
>   - 常见错误：把批量评测当调试用（跑一轮 100 条只看总分，说不清哪条为什么错）；或调试时一口气改了三个变量，"好了"但下周复现不出来。
> - 加分项：能把三段式节奏对应到评测三时机（离线评测/在线评测/灰度回放），说明理解调试-评测-回归是同一个度量体系在不同阶段的表现。
> - 延伸阅读：[ADP 课程 4.1 智能体调试与评测基础](../fde-handbook/tencent-adp-fde-course/lessons/4.1_智能体调试与评测基础.md)、[tuning-handbook §1.3 单次调试/批量评测/回归的分工](../tuning-handbook/Agent调优手册.md)、[eval-handbook §1.3 调试与评测的关系](../eval-handbook/Agent评测与质量工程手册.md)

> **Q066. SWE-bench、τ-bench、GAIA 这些公共基准怎么选？能当验收标准吗？**（难度：高 ｜ 频次：中）
> - 考察点：是否理解公共基准是"对标仪器"不是"验收仪器"，能否讲出数据污染（contamination，基准题泄进训练语料）、运行成本与版本管理三个工程现实。
> - 参考回答：
>   - 结论先行：公共基准能回答"我的 agent 大概在什么水位"，不能回答"我的业务场景够不够格上线"——后者是自建评测集的事；基准分数与自建集分数冲突时，信自建集。
>   - 规模与判据口径（2026-09-28 当日实抓）：SWE-bench Verified 500 题（判据=仓库单元测试）、GAIA 466 题（判据=精确匹配）、WebArena 812 任务（判据=站点最终状态）、OSWorld 369 任务（判据=执行后虚拟机状态）——判据全部是可执行验证。
>   - 选型直觉：选与业务形态最像的那一个做对标，不要全跑——客服/策略 agent→τ²-bench；coding agent→SWE-bench Verified；浏览器/GUI→WebArena、OSWorld；模型工具调用底座选型→BFCL；通用水位→GAIA。
>   - 数据污染是公共基准的第一威胁：题目泄进训练语料，分数虚高。主流应对：Verified 式人工重验子集（SWE-bench Verified 500 题逐题人工审核）、私有 held-out（SWE-bench Pro 用商业仓库、GAIA 测试集答案不公开）、环境私有化（WebArena/OSWorld 任务在私有实例执行，答案不在语料里）。
>   - 你的业务问题模型没见过，天然无污染——这是"公共基准不能替代自建集"的根本原因；反过来自建集也要防"泄漏给自己"（held-out 永不参与调参）。
>   - 运行成本决定评测频率：低成本基准（BFCL/GAIA，纯 API）可进 CI 当回归；中成本（τ²-bench 需要 user simulator，每步多一次 LLM 调用、成本翻倍且引入模拟器方差）；高成本（SWE-bench 需要 120GB 磁盘的 Docker 镜像池、OSWorld 要 VM 集群）只做里程碑对标。企业实践是"低频对标公共基准（月/季度）+ 高频回归自建集（每次变更）"。
>   - 版本管理教训：τ²-bench v1.0.1 修复 75+ 个任务后官方公开声明"新旧结果不可比"，排行榜历史成绩重打分——引用任何基准分数先问版本，这是数据集版本管理的教科书操作。
>   - 维护状态也是选型项：AgentBench 低维护、SWE-Lancer 已归档——官方不再投入的基准不要选作长期对齐仪器。
>   - 企业落地姿势：公共基准给出对外可讲的对标数字，自建集给出上线门禁，两者互补而非二选一。
> - 追问与陷阱：
>   - 追问"leaderboard 分数能直接写进客户汇报吗"：可以但必须注明基准版本与判据口径，并配自建集分数佐证业务适配性。
>   - 追问"跑一遍基准要花多少"：分三档——纯 API 基准半天接好、一轮百美元级；带模拟器的成本翻倍；带完整环境的是一笔实打实的工程账（环境快照与并发管理）。
>   - 常见错误：十个基准全跑一遍当"全面评测"；把榜单名次当验收结论——"分布相似的能力"不保证"你的业务分布"。
> - 加分项：SWE-bench 的 run_id 陷阱——同一 run_id 重跑不重评，换 diff 必须换 run_id，这是最常见的"为什么分数没变"事故；再补一句 GAIA 论文口径上人类 92% vs 当年 GPT-4+插件 15%，说明基准测的是 agentic 系统全链路而非裸模型。
> - 延伸阅读：[eval-handbook §3 基准与数据集](../eval-handbook/Agent评测与质量工程手册.md)、[eval-handbook §3.5 怎么选：决策树](../eval-handbook/Agent评测与质量工程手册.md)

> **Q067. 自建评测集怎么建？要多少条？从哪来？**（难度：中 ｜ 频次：高）
> - 考察点：golden dataset（黄金数据集）的建设路径——样本来源、规模、覆盖设计与版本管理；这是已进入面试必考范围的题型。
> - 参考回答：
>   - 规模答案：50-150 条起步，多样性比数量重要——评测集不是题目的堆叠，而是能力空间的采样。
>   - 来源优先生产日志，按价值排序的四个信号：无结果/空检索；低分信号（检索分偏低、工具返回错误码、步数/token 超预算）；换措辞重问（用户短窗口内换说法再问，最容易被忽略的强信号）；点踩会话。
>   - agent 特有的两个补充来源：调试六项记录（每条修好的 bug 天然是一条带期望输出的样本，最低成本起步方式）；工具轨迹异常（幻觉工具名、同参重复调用、参数被重试改写，从 trace 按规则筛）。
>   - 反面纪律：不要用 LLM 凭空合成第一批题目——agent 任务的期望行为（该调哪个工具、策略边界怎么判）几乎无法凭空合成；合成只适合给已有文档生成检索问答对、或扩容已有人工确认的题型。
>   - 先分类再采样：任务类型 × 难度层级（L1 单跳/L2 多跳 2-5 步/L3 长时程 >5 步）建覆盖矩阵，空白格就是采样的优先方向。
>   - 三类边界样本必须包含：拒答题（知识库没有/工具做不到，期望"明确说不知道"）、策略题（表面可做但按业务该拒绝/转人工）、对抗题（提示注入、无关信息、模糊指代）。
>   - 每条样本最小字段：稳定 id、任务类型、难度、输入、context、criteria（判据类型与期望）、expected_tools、来源溯源（来自哪条 trace/哪次调试记录）。
>   - 版本管理四纪律：评测集进 git、走 review；schema 版本 + 内容指纹（SHA-256，报告必须带指纹）；dev/held-out 两子集划分，held-out 只在大版本发布跑；只增不删——过时的题标 deprecated 保留，以复现历史报告。
>   - held-out 被拿去调参 = 自己污染自己的基准——与公共基准的数据污染是同一个镜像问题。
> - 追问与陷阱：
>   - 追问"样本不够怎么办"：优先补覆盖矩阵的空白格而不是同类型堆量；新题必须带可判定判据才准入集。
>   - 追问"判据写不出来怎么办"：写不出可判定期望说明这条题先别进集子——需求本身还是高风险未知项。
>   - 常见错误：凭空编一批题；判据在跑分期才补写；改题不记版本导致新旧报告混比。
> - 加分项：τ²-bench v1.0.1 的修题流程是标准答案——修题进 CHANGELOG、公开声明新旧不可比、提供旧版 tag 复现；企业内对应"改一条题 = 一次 commit，说明为什么改、影响哪些历史报告"。
> - 延伸阅读：[eval-handbook §4 自建评测集：从生产日志到黄金集](../eval-handbook/Agent评测与质量工程手册.md)、[rag-handbook §6.4 反馈闭环与坏例挖掘](../rag-handbook/RAG搭建文档.md)、[eval-handbook §4.4 数据集版本管理](../eval-handbook/Agent评测与质量工程手册.md)

> **Q068. agent 用 15 步做完 3 步的任务，怎么调试？（轨迹评测）**（难度：高 ｜ 频次：高）
> - 考察点：轨迹（trajectory）评测——最终答案对不等于过程对；能否用轨迹断言与失败归因把"15 步"拆解成可修的问题。
> - 参考回答：
>   - 先说为什么这是问题：多出的 12 步意味着 token 成本、延迟与脆弱性——多出来的每一步都可能在生产环境抖动中翻车；端到端评测告诉你"过没过"，轨迹评测告诉你"为什么、贵不贵、稳不稳"。
>   - 第一步是归因不是改 prompt：把 trace 拉出来，先看多出来的步骤属于哪类——规划冗余（该查不查/顺序颠倒/绕路）、工具失败引发的重试风暴、还是检索空转。
>   - 失败归因五分类：工具错（工具返回错误/超时/数据错——修工具工程，不是模型）、规划错（步骤序列不合理——修 prompt/工作流）、幻觉（编造事实/工具/参数——修检索与约束）、环境错（沙箱/网络/权限——修基础设施）、判据错（agent 其实对，是期望值写错——修评测集本身，走变更流程）。
>   - 轨迹断言清单：只能调用注册过的工具（幻觉工具是安全与稳定性事故源）；期望工具必须出现过；依赖顺序断言（A 必须先于 B）；步数与 token 预算断言（over_budget）；同工具同参数连续重复调用检测（重试风暴前兆）。
>   - 步骤效率看 P95 不看均值：步数分布（P50/P95）、token 用量、墙钟时间、超时率——生产事故来自尾部。
>   - 一致性用 pass^k（同一任务独立采样 k 次、k 次全过才算过，τ-bench 招牌指标）：比 pass@k（k 次里一次过就算过）更接近生产要求，k=3~5 是常见配置——步数多且脆弱的 agent 在 pass^k 下会现原形，因为"全过"概率随步数指数下降。
>   - "Verify the world, not the self-report"（验证世界，而不是验证自述）：agent 声称"已完成/已修复"不算数，成功判定只能来自环境最终状态或可复跑的证据——15 步里的"自我汇报成功"步骤尤其要警惕。
>   - 修复对应关系：规划冗余→工作流/提示词补步骤约束或减轮次；工具重试→修工具与失败兜底；检索空转→查询改写与检索参数——每类修法不同，这正是五分类的价值。
>   - 把效率写进判据：步数与 token 预算做成轨迹断言（"效率是约束不是加分项"），否则调好了答案又悄悄退化回 15 步没人知道。
> - 追问与陷阱：
>   - 追问"步数越少越好吗"：不是——欠步骤（漏掉必须的动作）同样是失败，τ²-bench 把"该做的动作做了没"单独设为判据层。
>   - 追问"怎么防止修好后回退"：把这条 case 连同步数预算清洗成回归样本，轨迹断言进回归门禁。
>   - 常见错误：只看最终答案对就放行——端到端判据全过、轨迹层照样不合格（手册里的反例：幻觉工具 + 超预算的轨迹，final_answer 与好轨迹一模一样）。
> - 加分项：能指出 15 步与 3 步的两个版本"在生产上是两个产品"（质量相同、成本差十倍）；再补一句成本与质量要并排出现（BFCL 榜单把 cost/latency 与分数并列展示的做法）。
> - 延伸阅读：[eval-handbook §6 轨迹评测：不只看最终答案](../eval-handbook/Agent评测与质量工程手册.md)、[eval-handbook §6.3 失败归因五分类](../eval-handbook/Agent评测与质量工程手册.md)、[FDE转行手册 §8.6 高频面试题](../fde-handbook/FDE转行手册.md)

> **Q069. badcase 从哪里来？怎么把它变成资产？**（难度：中 ｜ 频次：高）
> - 考察点：badcase（坏例）的采集信号、记录纪律与"回流成回归样本"的闭环——把线上问题变成评测资产是 FDE 的核心工作流。
> - 参考回答：
>   - 来源一：生产日志四信号（按价值排序）——无结果/空检索；低分信号（检索分低、工具错误码、超预算）；换措辞重问（最容易被忽略的强信号：用户换说法再问说明第一次没答中）；点踩会话。
>   - 来源二（agent 特有）：调试六项记录与工具轨迹异常（幻觉工具名、同参重复调用、参数被重试改写）——每条修好的 bug 都是现成的带期望样本。
>   - 采集方式是采样不是全量：生产流量按比例抽样进人审队列（全量人审不可持续），按四信号排优先级。
>   - 记录纪律是 Badcase 四要素：问题现象、优先归因、调整动作、调整后效果；同一 badcase 多次复发不是单条问题，是某类知识组织/切分/策略的系统性问题，升级为专项。
>   - 变成资产的关键一步：每个修复直接转成回归用例——进 dataset 时必须带溯源字段（trace_id、时间、反馈类型），修正该样本时能回到原始现场。
>   - 闭环形态：trace → 筛坏例（四信号+轨迹异常）→ dataset（输入+期望判据+来源）→ experiment 跑分（新版本 vs 基线）→ 回归门禁（退步卡发布）——Langfuse/Phoenix 都把这个闭环做成了产品功能，自建一张表也能跑。
>   - 去路排序：修知识（补文档/补问答对）、修管线（切分/检索参数）、沉淀问答（高频口语问法固化为问答对）。
>   - 反面清单：修完就丢（同一问题换皮再来）；badcase 不带期望判据就入库（它只是日志不是资产）；点踩样本不回流（负反馈是最高价值样本）。
> - 追问与陷阱：
>   - 追问"用户很少点踩怎么办"：隐式信号（换措辞重问、无结果、超预算）权重更高，配合按比例抽样人审补齐。
>   - 追问"badcase 越攒越多怎么治理"：按主题聚类，高频失败优先修复——修一类而不是修一条。
>   - 常见错误：把 badcase 当工单流水而不是评测资产——没有溯源字段与判据的样本无法进回归门禁。
> - 加分项：用"离线是安全网、在线是体温计、回放是传送带"概括三时机——灰度回放正是 badcase 资产化的传送带（生产 trace 回流成 dataset 再离线回放）。
> - 延伸阅读：[rag-handbook §6.4 反馈闭环与坏例挖掘](../rag-handbook/RAG搭建文档.md)、[eval-handbook §4.1 样本从哪来](../eval-handbook/Agent评测与质量工程手册.md)、[eval-handbook §7.3 trace→dataset→评测的闭环](../eval-handbook/Agent评测与质量工程手册.md)

> **Q070. 线上 agent 的可观测（observability）栈怎么搭？**（难度：中 ｜ 频次：中）
> - 考察点：trace（调用链路）的协议选型、平台横评，以及"可观测是评测的进料口"这个定位理解。
> - 参考回答：
>   - 定位先行：可观测是评测的进料口——没有结构化 trace，在线评测、灰度回放、坏例回流全部断粮；trace 树（invoke_agent 根 span + chat/execute_tool 子 span）就是轨迹评测的原始数据。
>   - 协议层选 OpenTelemetry GenAI 语义约定（OTel GenAI semantic conventions）：2026-05 已独立成仓（semantic-conventions-genai），独立演进本身就是"这块在快速变化"的信号；spans 文档仍是 Development（开发中）状态，属性名还可能改。
>   - 核心属性：gen_ai.operation.name（枚举已含 chat/embeddings/retrieval/execute_tool/invoke_agent/plan——agent 的规划、工作流、工具执行都有专属操作名）、gen_ai.provider.name、gen_ai.usage.input/output_tokens，以及缓存与推理细分（cache_read、reasoning tokens）——缓存命中与推理 token 天然进了标准字段，成本核算直接受益。
>   - 内容字段默认 opt-in（gen_ai.input/output.messages 不主动上报）——呼应日志脱敏纪律：只采集最小范围、敏感字段脱敏。
>   - 平台横评（2026-09-28 实抓）：Langfuse 35.1k star、server v4.46.0，MIT 内核可自托管，Python SDK v4 直接构建在 OTel 上，trace→dataset→experiments→评分回写的闭环最全；Arize Phoenix 11.6k、v20.16.0，Apache-2.0、OTel-native，数据进出无厂商锁定；LangSmith 是闭源 SaaS，LangChain/LangGraph 生态集成最深。
>   - 选型直觉：看重自托管与闭环 → Langfuse；看重协议开放与厂商中立（或已有 OTel 基础设施）→ Phoenix；LangChain 全家桶 → LangSmith 顺路。
>   - 协议统一的工程价值：换可观测平台从"重写埋点"变成"换 exporter"——所以接入层要集中定义抽象，不要把 gen_ai.* 属性字符串硬编码散落各处。
>   - 闭环五步要在平台里落成功能：生产 trace → 四信号筛坏例 → 入 dataset（带溯源字段）→ experiment 跑分对比 → 回归门禁。
>   - 两条纪律：trace 入 dataset 必须带溯源字段（trace_id、时间、反馈类型）；采样而非全量进人审。
> - 追问与陷阱：
>   - 追问"spans 还是 Development 状态敢不敢用"：敢，但要集中封装接入层——约定升级时只改一处，这正是"模式持久、封装易朽"。
>   - 追问"全量上报消息内容行不行"：隐私与成本双重否决——内容字段 opt-in、敏感字段脱敏、最小范围采集。
>   - 常见错误：只装了平台 SDK 没有判据与 dataset——有 trace 没有评测，可观测退化成"日志好看"；或把属性名写死散落各处，约定一升级全线返工。
> - 加分项：能说出 usage 里 cache_read_tokens 要进成本报表——命中率异常下跌即前缀漂移告警；以及"约定统一后，换平台 = 换 exporter"这层架构收益。
> - 延伸阅读：[eval-handbook §7 可观测与追踪：OTel GenAI 约定与三大平台](../eval-handbook/Agent评测与质量工程手册.md)、[python-handbook §8 评测三件套](../python-handbook/Python大模型应用开发手册.md)

> **Q071. agent 调优的标准闭环是什么？为什么必须单变量变更？**（难度：中 ｜ 频次：高）
> - 考察点：tuning（调优）方法论的主干——闭环五步与单变量纪律的因果；区分"玄学调参"与"度量驱动工程"。
> - 参考回答：
>   - 闭环五步：定位瓶颈 → 形成假设 → 单变量变更 → 回归评测 → 固化；线上 badcase 回流再触发下一轮。
>   - 入口不变量：闭环的入口是度量不是直觉——没有固定评测集就没有"变好"的定义，这时唯一正确的动作是先建评测集（50-150 条起步），而不是先改 prompt。
>   - ① 定位瓶颈：用 trace/调试视图分诊到层（单次调试五步法 + 看全链路）；② 形成假设：按失败分类学反推最可能出错的环节，而不是反复追问直到某次看起来满意。
>   - ③ 单变量变更：ADP 4.2 原话"每轮只改一个主要变量"。
>   - 为什么必须单变量：同时改 prompt、模型、知识库、检索参数——变好无法归因（不知道谁的功劳，也无法复制成功）、变差无法回滚（不知道动哪一行救火）。
>   - ④ 回归评测：固定集 A/B 配对比较 + 判据用"代码 > 规则 > 裁判模型"的优先级 + 分场景不回退门禁；⑤ 固化：六项记录与版本记录落盘、基线更新带指纹、badcase 清洗成回归样本——"上次那个 0.3 效果好来着"就是没有固化的事故现场。
>   - 要组合实验怎么办：用矩阵而不是连续改——promptfoo 把 prompts 写成数组就是 A/B 矩阵、providers 数组就是多模型矩阵，笛卡尔积一次跑完，每行结果天然带完整变量上下文，不存在"改了什么来着"的考古。
>   - 已验证的最小实现：tuning-handbook 的 mini_tuning_lab（纯标准库、本机验证通过）——分层切分 dev/held-out、配对比较、三道门禁、基线指纹（数据集+切分参数的 SHA-256 前 12 位，如 5155cafcdc90）。
> - 追问与陷阱：
>   - 追问"时间紧能不能同时改两个"：可以并行跑两个单变量分支，但不要把两个变量压进一次变更——矩阵实验就是解法。
>   - 追问"固化具体固化什么"：版本、变量、指标三件事落盘，基线带数据集与切分指纹——指纹变了显式判 INVALID，不悄悄混比。
>   - 常见错误：一次改多个变量；参数乱试不记录；优化产物直接上线不过 held-out（搜索/优化产物会过拟合评测集）。
> - 加分项：能说出"调优是评测的下游、上线的上游——没有度量就没有调优"，再补 promptfoo 的三句话概括：配置即实验、断言即判据、CI 即门禁。

> **Q072. 六类失败（检索/推理/工具/格式/延迟/成本）怎么分诊？**（难度：中 ｜ 频次：高）
> - 考察点：失败分类学（fail taxonomy）与分诊（triage）能力——"回答不对"只是表象，能否先定层再动手。
> - 参考回答：
>   - 总纲：先分诊到层再动手——每类失败有专属调优手段，病急乱投医（一律先改 prompt）是最大的浪费。
>   - F1 检索没召回：知识库"明明有"但答错/答不全、引用缺失——优先怀疑知识准备→切分→检索参数→检索范围，首选手段是文档规范化、chunk 重切、混合检索+重排、查询改写。
>   - F2 推理跑偏：命中了资料仍扩展无依据内容、意图走错分支、答非所问——system prompt 补齐任务/依据/边界/格式要素、few-shot、问题分解，必要时升级模型。
>   - F3 工具误用：幻觉工具、参数错、漏字段硬调、返回值被误读——工具名称/描述/入参说明重写、参数提取节点+缺失追问、返回值具名 JSON、失败兜底。
>   - F4 格式不合规：下游 JSON 解析失败、字段名漂移、多一段解释文字——结构化输出模式/固定字段模板+校验重试、确定性逻辑（时间戳/编号/计算）放进工具而不是提示词。
>   - F5 延迟超预算：P95 超时、用户流失——并行化、缓存、小模型路由、per-task 超时与预算熔断。
>   - F6 成本失控：账单爆炸、单任务 token 异常、缓存命中率趋零——模型路由/级联降级、缓存前缀工程、批处理、预算断言。
>   - 同一表象映射多类：同样是"回答错误"，可能是意图分支走错（F2）也可能是知识没命中（F1）——先看中间信号（检索命中、变量、节点输出、工具返回）再定类；ADP 的"三问分诊"（有没有知识→有没有命中→有没有正确生成）是速查版。
>   - F5/F6 是"约束型失败"：不改变答案对错，但在生产上是事故——把延迟与成本做成轨迹断言（over_budget）让它们在评测里"可见"，是治理的前提；且知识没命中时单纯加长 prompt 治不了根因。
> - 追问与陷阱：
>   - 追问"六分类和轨迹归因五分类什么关系"：六类是按调优战线重切，五分类（工具错/规划错/幻觉/环境错/判据错）是按证据归因——一个指导"怎么修"，一个指导"错在哪"。
>   - 追问"分诊的第一动作是什么"：拉 trace 看中间信号，先确认检索命中与工具返回，再下结论。
>   - 常见错误：只调 prompt 不治检索（知识没命中，prompt 写到天上也没用）；把 F5/F6 当"非质量问题"不管——它们在生产上是事故。
> - 加分项：能背出 F1-F6 的"优先怀疑层"与"首选手段"映射，并指出 ADP 4.1 的快速诊断表与 4.3 的"三问分诊"是同一思想的课程版。
> - 延伸阅读：[tuning-handbook §1.2 失败分类学：六类失败×调优手段映射表](../tuning-handbook/Agent调优手册.md)、[tuning-handbook §3 检索与 RAG 调优](../tuning-handbook/Agent调优手册.md)、[eval-handbook §6.3 失败归因五分类](../eval-handbook/Agent评测与质量工程手册.md)

> **Q073. prompt 调优有哪些杠杆？**（难度：中 ｜ 频次：中）
> - 考察点：prompt 调优是不是"把话写得更漂亮"——能否列出结构化杠杆并说清每个杠杆的实证边界。
> - 参考回答：
>   - 前置动作：prompt 效果差通常不是"写得不够长"，而是要素缺失——先分诊是 F1（没拿到依据）、F2（没听懂任务）还是 F4（输出没被约束），知识没命中时加长 prompt 治不了根因。
>   - 杠杆一 system prompt 结构：ADP 七要素（角色/背景/目标/依据/步骤/边界/输出）当检查清单用，缺哪补哪而不是整段重写——缺"依据"出编造、缺"边界"出越权、缺"输出"出格式漂移；"写在哪一层"也是调优动作（全局风格→角色指令，命中了但不会用→用户输入模板，单节点不稳→该节点提示词）。
>   - 杠杆二 few-shot（少样本示例）：输出格式/判断标准"不容易说清楚"时，1-3 个高质量示例通常胜过继续堆规则；选"一个标准样例+一个边界样例+一个缺失信息样例"——让模型既会正常处理也会兜底；放开头或结尾（lost in the middle 位置偏差）；示例块放系统提示词稳定区还能吃缓存。
>   - 杠杆三 CoT/ReAct 触发词的实证边界：快思考模型上零样本 CoT（"让我们一步一步思考"）有可复现提升；推理模型自带内部推理预算，外部触发词的边际收益消失甚至为负——"要不要 CoT"已从提示词层下沉到模型档位层；触发词有没有用不抄结论，在自己的评测集上跑 A/B。
>   - 杠杆四提示缓存（prompt caching）：把稳定前缀（工具定义→系统提示词→few-shot 稳定区）放最前并保持字节级稳定，动态内容（检索结果、用户输入）一律放后缀——Anthropic 显式断点最多 4 个、放稳定段末尾；命中率趋零通常意味着时间戳/流水号混进了前缀。
>   - 给模型留中间出口：允许输出"无法确认/需补充信息/建议转人工"——在评测里是判据（拒答正确也算通过），在生产里是 HITL（human-in-the-loop，人在环）插点。
>   - 实证口径：ADP 4.2 的四组 Before/After 对比里，稳定提升的从来不是"加一句思考"，而是补齐依据、边界与输出约束。
>   - judge 场景例外：判分协议里"先摘录证据再打分"（evidence-before-score）是触发词在 2026 年最确定的正面用例，能显著压幻觉判分。
> - 追问与陷阱：
>   - 追问"示例是不是越多越好"：不是——token 成本与"过度模仿样例"风险同步上升；many-shot 只在长上下文模型上可考虑。
>   - 追问"示例按相似度动态选行不行"：行，但动态内容会打断缓存前缀——稳定示例放前缀、动态部分放后缀。
>   - 常见错误：把每次变化的日期/用户数据写进本该稳定的示例区——缓存全灭，账单翻倍。
> - 加分项：知道 DSPy（"调优=编译"框架，38,374 star）把人工手法变成搜索空间——但硬前提是先有可判定的 metric 与有代表性的 trainset（30-50 条即可驱动），优化产物要人审入库，且换模型=重新编译。
> - 延伸阅读：[tuning-handbook §2 Prompt 调优](../tuning-handbook/Agent调优手册.md)、[prompt-handbook 提示词搭建文档](../prompt-handbook/提示词搭建文档.md)

> **Q074. A/B 评测怎么设计才可信？**（难度：中 ｜ 频次：低）
> - 考察点：实验设计的严谨性——配对比较、三道门禁、held-out 封存与指纹；小数据集上"结论来回跳"的根因诊断。
> - 参考回答：
>   - 前提三件套：两个版本只差一处变更（单变量）、同一样本集、同一判据，温度 0——任何一条不满足，A/B 结论就是噪声。
>   - 配对比较（paired comparison）而不是比均值：小数据集上两次独立均值的对比来回跳——逐样本对照方向（变好/变差/双通过），配对抵消样本噪声。
>   - 三道门禁依次过：dev 集非劣（不回退超过容差）→ 分场景不回退 → held-out 复跑非劣。
>   - 分场景门禁是红线：场景 A 涨 20%、场景 B 跌 20%，整体通过率没变但业务炸了——只看整体是第 6 号坑。
>   - 真实踩坑（tuning-handbook FAQ 第 1 条）：门禁必须用同一切分的同类指标相比——框架初版拿 held-out 成绩比 dev 基线导致固化后误报 FAIL；修法是基线记录里同时固化 held-out 指标，比 held-out vs held-out。
>   - held-out 封存纪律：只在 promote（晋升基线）前跑——参与调参则门禁越跑越绿、上线翻车。
>   - 指纹判可比性：数据集+切分参数的 SHA-256 指纹，变了显式判 INVALID 而不是悄悄混比——与 τ²-bench v1.0.1"新旧结果不可比"声明同一思想。
>   - 实验落盘：每轮记录（版本、变量、指标）——"参数乱试不记录"是第 8 号坑；裁决用离线固定集 + 在线指标旁证，不用生产小流量当判据。
> - 追问与陷阱：
>   - 追问"不做统计显著性检验行不行"：小样本下配对方向计数（变好 vs 变差）比显著性检验更实用；关键是别比独立均值，样本量上来后再补检验。
>   - 追问"能用 judge 做 A/B 对比吗"：可以——校准过的 pairwise judge 做版本对比（ADP 的对比评测即此），但分数语义要靠语义锚定稳住。
>   - 常见错误：换 embedding/换 judge 后新旧分数硬比（向量空间或判分口径不可比）；一次改多个变量的实验当单变量结论用。
> - 加分项：能复述 mini_tuning_lab 的运行实录——v0 基线 dev pass=50%，v1 在 dev 100% 但 held-out 75%（bnd-02 的"无法办理"措辞未命中），门禁 PASS 后固化指纹 5155cafcdc90：一段话证明真跑过闭环。
> - 延伸阅读：[tuning-handbook §9 最小调优实验框架](../tuning-handbook/Agent调优手册.md)、[tuning-handbook §9.4 常见坑 FAQ](../tuning-handbook/Agent调优手册.md)、[tuning-handbook code/mini_tuning_lab.py](../tuning-handbook/code/mini_tuning_lab.py)

> **Q075. 延迟预算怎么分解与优化？**（难度：中 ｜ 频次：中）
> - 考察点：能否把"慢"拆成可归因的分量并对应杠杆——延迟工程的第一步是测而不是猜。
> - 参考回答：
>   - 三笔账：TTFT（time to first token，首字延迟——发请求到第一个 token 出现）、生成速率（decode throughput，首 token 后每秒吐多少 token）、工具往返（tool round-trip——模型停→工具执行→结果回→模型续的墙钟）。
>   - TTFT 的杠杆：缓存命中（OpenAI 实测延迟最高降约 80%）、前缀缩短、小模型、流式开启。
>   - 生成速率的杠杆：输出长度约束（结构化输出天然短）、小模型、Fast 档（Anthropic Opus 5.5 Fast 模式：2× 价格换至多 2.5× 提速，2026-09-28 官方页实抓）。
>   - 工具往返的杠杆：无依赖工具并行化、预取（prefetch，投机执行）、工具自身超时与缓存、减少轮次。
>   - 示例分解（tuning-handbook §7.5，数字为方法示意）：目标交互 P95 ≤ 8s = TTFT 0.8s（缓存后）+ 生成 250 token ÷ 80 tok/s ≈ 3.1s + 2 次工具往返 2×1.5s = 3.0s + 编排开销 0.3s + 余量 0.8s——先测各分量再选杠杆，"平均错方是最常见的浪费"。
>   - P95 比均值重要：生产事故来自尾部，轨迹层的步骤效率指标要看 P50/P95 分布与超时率。
>   - 兜底机制：per-task 超时（卡死任务判环境类失败，不允许拖垮整轮）与整轮预算熔断；重试必须带幂等（idempotency）约束，否则超时重试可能重复下单。
>   - 投机执行两招：预取——参数提取节点一有部分结果就并行发起候选检索/工具请求，路由确定后取消多余分支（cancel-on-decide）；有副作用的调用禁止投机。感知延迟另有一路：流式先渲染首段、工具结果分块流回——感知延迟的下降不依赖真实延迟的下降。
>   - F5 定位清单：串行长链、上下文过长、模型过大、无超时预算——对照失败分类学先归类再动手。
> - 追问与陷阱：
>   - 追问"用户抱怨慢，先干什么"：拉 trace 实测三笔账的占比，别上来就换更快的模型——工具往返主导时换模型没用。
>   - 追问"并行化有没有前提"：无依赖才并行、有副作用必须串行+幂等。
>   - 常见错误：只优化模型生成段（因为好测），结果大半墙钟耗在工具往返；超时无预算，一个卡死任务拖垮整轮评测。
> - 加分项：能说出工作流层的编排纪律"无依赖即并行、有副作用即串行"，并把"减轮次"当成延迟杠杆而不只是成本杠杆。
> - 延伸阅读：[tuning-handbook §7.5 延迟预算分解](../tuning-handbook/Agent调优手册.md)、[tuning-handbook §7.4 投机执行](../tuning-handbook/Agent调优手册.md)、[eval-handbook §8.3 评测 run 的并行度与超时预算](../eval-handbook/Agent评测与质量工程手册.md)

> **Q076. token 成本怎么精算？缓存怎么把钱省下来？**（难度：高 ｜ 频次：高）
> - 考察点：成本核算公式与四档单价、缓存命中率工程——能否从"看账单心疼"升级到"归因到 trace 的精算"。
> - 参考回答：
>   - 公式：成本 = Σ_calls [plain_in × 价_in + cached_in × 价_cached + out × 价_out + 缓存写部分 × 价_write]——注意缓存命中 token 通常已含在输入用量里，计费时要从普通输入里拆出来单独计价，否则账单虚高。
>   - 归因不变量：账单最小粒度是"单次调用"，向上聚合到任务/会话/租户——归因链不可断；OTel GenAI 约定的 gen_ai.usage.* 与 cache_read 细分字段让它变成标准能力。
>   - 四档单价（2026-09-28 官方定价页实抓）：普通输入 1×；缓存读约 0.1×（Anthropic 缓存读 0.1×、OpenAI gpt-5.x 缓存输入 10% 价、DeepSeek 缓存命中 $0.006 ≈ 未命中 $0.30 的 2%，四家里最激进）；缓存写仅 Anthropic 收（1.25×，5 分钟 TTL）；输出 = 输入的 4-10×（Sonnet 5 $2/$10、gpt-5.2 $1.75/$14 = 8×）。
>   - 为什么缓存是第一杠杆：agent 每轮重发整个上下文（历史+系统提示词+工具定义），输入 token 是复利结构——命中率对账单是非线性影响。
>   - 缓存工程清单：稳定前缀顺序（工具定义→系统提示词→few-shot 稳定区，动态内容止步于此）；Anthropic 显式断点最多 4 个、放稳定段末尾；OpenAI prompt_cache_key 按租户/会话分组路由，注意同前缀 ~15 req/min 的溢出阈值；命中率（cached_tokens）进 trace 与报表，异常下跌 = 前缀漂移告警——元凶常是时间戳/流水号。
>   - 输出比输入贵 4-10× 的推论：让模型少生成废话（约束输出长度、结构化输出）与"大模型读、小模型写"是两条主要省钱方向。
>   - 批处理一律 -50%（四家当日实抓）：夜间评测跑批、数据集批量打标、回归集复跑没有理由不用；DeepSeek 错峰即时半价；在线交互链路不适用。
>   - 语义缓存（semantic cache）作为第二层：公开报告单层最高省约 68.8%、与模型路由叠加综合 60-85%——但有正确性风险（两个"语义相近"问题答案可能不同，如改一个日期），要设相似度阈值+失效策略，并把缓存命中当一类轨迹信号监控。
>   - 评测 run 也要预算管理：整轮设 token/费用上限，触顶提前出部分报告——评测的产出是信息，不是烧完预算。
> - 追问与陷阱：
>   - 追问"按 token 单价选模型对吗"：第三方观点（虎嗅 2026-05）——应按"每次任务验收通过的实际成本"评估，路由、缓存、步数对总成本的影响远大于单价表。
>   - 追问"命中率怎么看健康度"：趋零不是缓存失效就是前缀漂移——先查有没有动态内容混进前缀。
>   - 常见错误：缓存命中没从普通输入里拆出来计价；低频长会话忘开 1 小时 TTL 的写费翻倍（Anthropic 2×）就硬开。
> - 加分项：六家源码对照——OpenCode 用 Decimal 精算 + context tier 定价 + 各家缓存变体键归一化；ZCode 的 usage 三表与 cacheHint:"stable" 显式缓存锚点——说明"成本是常驻机制不是事后报表"。
> - 延伸阅读：[tuning-handbook §7.1 token 成本核算](../tuning-handbook/Agent调优手册.md)、[tuning-handbook §7.2 缓存命中率：第一杠杆](../tuning-handbook/Agent调优手册.md)、[eval-handbook §8.1 成本核算：账单要能归因到 trace](../eval-handbook/Agent评测与质量工程手册.md)

> **Q077. 模型路由与级联降级怎么设计？**（难度：高 ｜ 频次：高）
> - 考察点：routing（路由）与 cascade（级联）的机制、收益与两条硬纪律——尤其"路由器自己也要过评测集"这条反直觉约束。
> - 参考回答：
>   - 机制：按任务难度/类型分档——简单子任务（意图分类、格式化、检索改写）路由小模型，复杂子任务（规划、策略判断）升级大模型；分工参考是"推理模型管规划与判卷、快思考小模型管分类抽取改写"。
>   - 为什么值得做：推理模型与快思考的价差 7-35×（gpt-5.2-pro $21/$168 vs gpt-5-nano $0.05/$0.40，2026-09-28 实抓）；路由与语义缓存叠加的综合省钱报道在 60-85%。
>   - 级联两种形态：先小后大——小模型置信度不足或失败再升级旗舰；或先旗舰拿结果、降级副本做旁路校验——每级之间要有明确的升级判据（置信度阈值、失败类型），不是"感觉不行"。
>   - 纪律一（最重要）：路由器自己也要过评测集——路由错了（难题给了小模型）等于把错误率做进架构；路由决策是轨迹树上的一个节点，把它纳入轨迹评测（"工具调用正确性"扩展为"模型调用正确性"）。
>   - 纪律二：每档模型各自的 pass 率与成本并排监控——BFCL 排行榜把 cost/latency 与分数并列展示的做法值得抄：分数永远和成本延迟并排出现。
>   - 参数跟角色走：OpenCode 给每个 agent 独立 temperature/topP——档位不只是模型，还包括按角色配置的采样参数。
>   - 模型目录外置：OpenCode 把模型清单（含 cost/limit/status(deprecated) 字段）外置到 models.dev 并 TTL 缓存——模型信息当配置管不当代码管，换模型从"发版"变"改配置"。
>   - 选型先做维护状态扫描：RouteLLM 5,549 star 但 2024-08 后未再推送——开源路由框架要先查维护状态再进生产。
>   - 三角表定位：模型路由/级联 = 成本↓↓、延迟↓、质量需监控——它是把质量风险显式接过来的降本手段，所以评测与监控是它的对价。
> - 追问与陷阱：
>   - 追问"升级阈值怎么定"：在评测集上按难度分层标定，而不是拍脑袋——阈值本身也是要过评测的参数。
>   - 追问"路由层会不会成为新故障点"：会——路由器要有兜底档（默认走大模型或固定档），并把路由 miss 当一类轨迹信号监控。
>   - 常见错误：只报省了多少钱不报每档 pass 率；把路由当黑盒、没有显式升级判据。
> - 加分项：能补充"级联降级也是稳定性设计"——旗舰限流/故障时自动降到可用档位，配重试与幂等约束；再引用原文"路由错了等于把错误率做进架构"。
> - 延伸阅读：[tuning-handbook §6.5 模型路由与级联降级](../tuning-handbook/Agent调优手册.md)、[tuning-handbook §6.6 四家模型价格速查](../tuning-handbook/Agent调优手册.md)、[eval-handbook §8.2 模型路由：大小模型分流](../eval-handbook/Agent评测与质量工程手册.md)

> **Q078. 成本、质量、延迟三角冲突时怎么取舍？**（难度：高 ｜ 频次：低）
> - 考察点：工程判断力——能否放弃"三个都要"，按业务场景显式取舍并写进设计文档。
> - 参考回答：
>   - 三角的正确用法不是"同时优化三个"，是显式选择放弃哪个——取舍写进设计文档，而不是留在事后解释里。
>   - 策略层候选（成本/质量/延迟三轴影响）：提示缓存（成本↓↓、质量不变、延迟↓↓，几乎无条件该做）；批处理/错峰（-50%，但时效 ≤24h，只用于离线负载）；模型路由/级联（成本↓↓，质量需监控，路由错=错误进架构）；上下文压缩/剪枝（输入 token ↓，但质量有损——摘要有偏，必须配回归集，剪枝先于摘要）；工具并行/预取（延迟↓↓、成本≈，仅限无依赖无副作用）；结构化输出（成本↓、质量↑——F4 根治、延迟↓）；Fast 档/优先服务（2× 价格换延迟，交互链路兜底）；减 agent/减轮次（成本↓、质量↑——少交接损耗、延迟↓）。
>   - 场景取舍三例：客服场景通常弃成本保延迟与质量；数据管线弃延迟保成本与质量；评测跑批弃延迟保成本、质量由判据保证。
>   - 反面教材：Anthropic 实测多 pass 配置 90.2% 任务提升但 token 翻 15×——不加鉴别地"再加一层"就是放弃成本轴；好的调优文化对加法保持警惕，"减法是一等公民"（六家设计模式之一）。
>   - 单看任何一个维度都是自欺：分数永远和成本、延迟并排出现（BFCL 榜单做法）——质量相同、成本差十倍的两个版本在生产上是两个产品。
>   - 业务口径收口：按"每次任务验收通过的实际成本"评估而非 token 单价（虎嗅 2026-05 观点）——三角取舍最终都落在这个口径上。
>   - 机制化：取舍不是一次会议而是常驻机制——成本归因到 trace（账单可按会话/租户聚合）、延迟与 token 预算断言（over_budget）、预算熔断；六家 agent 都这么做（ZCode 连续失败熔断、openclaw 六条限流、OpenCode usage 三表）。
>   - 底线思维：先和业务方约定质量门禁红线（哪些场景不允许回退），在红线之上做成本与延迟优化——红线来自分场景回归门禁，不是拍脑袋。
> - 追问与陷阱：
>   - 追问"老板只要求降本 50% 怎么办"：先给出质量门禁现状与可牺牲场景清单，用三角取舍表汇报"降哪一档、丢哪个轴"，而不是默默压质量。
>   - 追问"上下文压缩看起来免费为什么危险"：摘要有偏是有损优化——必须配回归集验证，剪枝先于摘要（context-handbook 的不变量）。
>   - 常见错误：三个轴同时优化（结果互相抵消）；把"加模型、加 agent"当万能解——多 pass 配置 token 翻 15× 的教训。
> - 加分项：能引用"减 agent 的撤退判据"（转交不稳定就合并回单 agent/工作流）说明降本与质量可以同向——减法既降本又提质。
> - 延伸阅读：[tuning-handbook §7.6 成本-质量-延迟三角：取舍表](../tuning-handbook/Agent调优手册.md)、[multiagent-handbook §1.2 协同的成本收益](../multiagent-handbook/Multi-Agent协同手册.md)、[context-handbook §2.2 剪枝先于摘要](../context-handbook/Context与记忆系统手册.md)
