## 题目正文

> **Q113. 手写一个最小 agent loop（模型→工具→回填）。**（难度：初 ｜ 频次：高）
> - 考察点：能否把 agent（智能体）的内核——"调模型 → 执行工具 → 结果回填 → 再调模型"的循环——在白板上落成二十行代码，并说清消息回填不变量与停止条件设计；这是区分背概念与动手过的第一题。
> - 参考回答：
>   - 接口设计要点：入参四件套（工具注册表 `tools`：名字 → 真函数；`schemas`：给模型看的 JSON Schema（JSON 模式描述规范）；system 提示词；user 输入），返回值是最终文本；循环体内部只做三件事——调模型、判停、执行回填。
>   - 工具调用是"两段式"：模型只点菜（返回 `tool_calls`），执行永远在开发者手里（python-handbook §3.2 的表述）；本工作区六家 agent 的主循环都是这个形状——anon-kode 的 `query()` 就是把"助手消息 + 全部工具结果"追加进历史后递归调用自身（01-claude-code/架构拆解 §3）。
>   - 代码骨架（python-handbook §9.3 自研循环的工程化版）：
>
> ```python
> import json
>
> def run_agent(tools: dict, schemas: list, system: str, user: str, max_steps: int = 10) -> str:
>     messages = [{"role": "system", "content": system},
>                 {"role": "user", "content": user}]      # 无状态协议：历史全量重发
>     for _ in range(max_steps):                          # 步数上限：防死循环的第一道闸
>         msg = client.chat.completions.create(
>             model="gpt-5", messages=messages, tools=schemas).choices[0].message
>         messages.append(msg)                            # 不变量①：模型的消息先回填历史
>         if not msg.tool_calls:                          # 模型不再点菜 → 任务完成
>             return msg.content
>         for call in msg.tool_calls:                     # 逐个执行模型点的菜
>             try:
>                 result = tools[call.function.name](**json.loads(call.function.arguments))
>             except Exception as e:                      # 工具报错也要回填，别让循环崩掉
>                 result = f"tool error: {e}"
>             messages.append({"role": "tool", "tool_call_id": call.id,
>                              "content": str(result)[:4000]})   # 不变量②：按 call.id 回填
>     return "已达步数上限，需人工介入"                    # 兜底出口：显式失败优于静默截断
> ```
>
>   - 关键不变量/边界：① 模型带 `tool_calls` 的消息必须先 `append` 进历史，再执行工具——顺序错了 API 直接报"tool_call 无对应结果"；② 每个工具结果用 `tool_call_id` 与调用一一对应，回填内容的 `role` 是 `tool` 而不是 `user`；③ 必须有步数上限与工具报错兜底两个出口。
>   - 怎么测：mock 掉模型返回（第一次返回带 `tool_calls`、第二次返回纯文本），断言历史长度、`tool_call_id` 对应关系与最终返回值；真模型下测"连续点同一道菜"是否会撞步数上限。
> - 追问与陷阱：
>   - 追问：循环什么时候停？常见错误：只答"模型不调工具就停"——生产还要三个强制出口：步数/轮数上限、预算上限、用户中断（abort 后产出中断消息并退出，anon-kode 的 `abortController` 就是干这个的）。
>   - 追问：工具执行报错怎么办？常见错误：让异常直接炸掉整个循环，或者把报错吞掉不回填——正确做法是把"错误文本"作为工具结果回填，让模型自己决定重试、换工具还是收尾（模型看不见错误就无法纠正）。
>   - 追问：模型说调了工具但历史里找不到对应结果，为什么？常见错误：忘了回填模型消息本身、或并发执行后没按原始 `tool_use` id 排序就回填（01-claude-code/架构拆解 §3.1 第 7 步专门为此重排）。
> - 加分项：能对比六家的演进方向——最简 20 行之上叠的是权限闸门、上下文预算、并发与持久化；或指出 `stop_reason === 'tool_use'` 不可靠，anon-kode 以"内容块里有没有 `tool_use`"为准（§3.1 第 4 步）。
> - 延伸阅读：[python-handbook §9.3 自研循环：20 行看清六家 agent 的内核形状](../python-handbook/Python大模型应用开发手册.md)｜[01-claude-code/架构拆解.md §3 Agent 主循环（核心）](../01-claude-code/架构拆解.md)｜[python-handbook §3.2 openai SDK：方言的基准实现](../python-handbook/Python大模型应用开发手册.md)

> **Q114. 手写工具调用封装：JSON Schema 定义 + 执行分发 + 错误兜底。**（难度：初 ｜ 频次：高）
> - 考察点：能否把"模型点菜"与"厨房做菜"解耦成一个注册表 + 分发层的结构：schema 怎么生成、未知工具/非法参数/实现抛错三类错误怎么兜底成模型可读的结构化返回。
> - 参考回答：
>   - 接口设计要点：一个工具 = schema + 描述 + 实现（01-claude-code/架构拆解 §4.1 的定义）；schema 不要手写 JSON，用 Pydantic 类生成（`model_json_schema()`），类上的 `Field(description=...)` 会进 schema——模型选不选这个工具、参数填得对不对，全看这段描述。
>   - 分发层返回具名 JSON：成功 `{"result": ...}`、失败 `{"error": ...}` 二选一，错误永远是字符串字段而不是抛异常——异常只在分发层之内消化（结构化回传的纪律同 multiagent-handbook §3.3 交接协议：回传可定位的结构化结果，不回传半截文本）。
>   - 代码骨架：
>
> ```python
> from pydantic import BaseModel, Field, ValidationError
>
> class WeatherArgs(BaseModel):                     # ① 定义：类即 schema（类型即协议）
>     city: str = Field(description="城市名")        # description 会进 JSON Schema 给模型看
>
> REGISTRY: dict[str, dict] = {}                    # ② 注册表：工具名 → {schema, fn}
>
> def register(schema):
>     def deco(fn):
>         REGISTRY[fn.__name__] = {"schema": schema, "fn": fn}
>         return fn
>     return deco
>
> @register(WeatherArgs)
> def get_weather(city: str) -> dict:               # ③ 返回具名 JSON：result / error 二选一
>     return {"result": f"{city} 晴 25°C"}
>
> def dispatch(name: str, raw_args: str) -> dict:   # ④ 分发层：所有错误在这里兜底
>     if name not in REGISTRY:                      # 兜底①：模型点了不存在的菜
>         return {"error": f"unknown tool: {name}"}
>     try:                                          # 兜底②：参数不合法 → 校验错误定向回喂
>         args = REGISTRY[name]["schema"].model_validate_json(raw_args or "{}")
>     except ValidationError as e:
>         return {"error": f"invalid args: {e.errors()[:2]}"}
>     try:
>         return {"result": REGISTRY[name]["fn"](**args.model_dump())}
>     except Exception as e:                        # 兜底③：实现抛错 → 错误进结果而非炸循环
>         return {"error": f"execution failed: {e}"}
> ```
>
>   - 关键不变量/边界：① 注册表是唯一分发入口，模型给的 `function.name` 必须查表，绝不能 `eval`/动态 import；② 参数先过 Pydantic 校验再解包进函数，`json.loads` 失败与校验失败都归入兜底②；③ 错误信息要"定向"（哪个字段、什么错），模型拿着才能自我修正——笼统的 "error" 会诱发盲试。
>   - 怎么测：三类错误各写一个用例（未知名、非法 JSON、合法 JSON 但缺字段/超范围），断言返回的都是 `{"error": ...}` 且不抛异常；再用 ` Expense.model_json_schema()` 断言生成的 schema 与预期字段一致（python-handbook §2.4 的 pytest 用例同款）。
> - 追问与陷阱：
>   - 追问：为什么用 Pydantic 生成 schema 而不是手写？常见错误：答"省事"——真正的原因是"定义 → 校验 → 生成 schema"统一在一个类上，手写 schema 与校验逻辑会漂移；这条链是工具定义、结构化输出、MCP 工具共用的不变量（python-handbook §2.4）。
>   - 追问：工具执行很慢怎么办？常见错误：在分发层里无限等——分发层应带超时，超时也作为一种 `{"error": ...}` 回填；有副作用的工具另配幂等键，防止重试造成重复写入（见 Q126）。
>   - 追问：工具描述写多长合适？常见错误：塞成小作文——描述进每轮请求的 token（词元）预算，工具一多应描述失控；纪律是"一句话说清干什么、什么时候不该用"，与 MCP 工具设计同款。
> - 加分项：能指出 MCP（Model Context Protocol，模型上下文协议）工具与内置工具在注册表层面完全同构（`getMCPTools()` 动态并入同一张表，01-claude-code/架构拆解 §4.2），说明这套注册表设计能无痛接协议化工具源；或引 python-handbook §9.1 十几行把检索封成 MCP server 的实例。
> - 延伸阅读：[python-handbook §2.4 类型标注与 Pydantic：大模型应用的"类型即协议"](../python-handbook/Python大模型应用开发手册.md)｜[python-handbook §3.2 openai SDK：方言的基准实现（工具两段式）](../python-handbook/Python大模型应用开发手册.md)｜[multiagent-handbook §3.3 交接协议四条（可以直接抄）](../multiagent-handbook/Multi-Agent协同手册.md)

> **Q115. 手写一个流式聊天接口：SSE 端点 + 前端打字机效果。**（难度：初 ｜ 频次：中）
> - 考察点：能否写清 SSE（Server-Sent Events，服务器推送事件）的帧协议与生成器式响应：`data: ` 前缀 + 空行结尾的帧格式、异步客户端、断连清理，以及前端逐帧追加成打字机效果。
> - 参考回答：
>   - 接口设计要点：GET/POST 端点返回 `StreamingResponse`，媒体类型 `text/event-stream`；后端用 AsyncOpenAI（异步客户端）——同步客户端会阻塞整个事件循环，这是 LLM 服务端第一大坑（python-handbook §7.2 / §10.6）。
>   - 生成器是惰性的：token 到一批才推一批，天然背压（backpressure，消费端反压生产端）；客户端断开时生成器被取消，取消要传导到上游流（关掉模型请求），否则请求悬着继续烧钱。
>   - 代码骨架（python-handbook §7.2 的最小实现）：
>
> ```python
> from fastapi import FastAPI
> from fastapi.responses import StreamingResponse
> from openai import AsyncOpenAI                    # 异步客户端：同步会阻塞事件循环
>
> app, llm = FastAPI(), AsyncOpenAI()
>
> @app.get("/chat")
> async def chat(q: str) -> StreamingResponse:
>     async def gen():                              # 生成器惰性：token 到一批推一批
>         stream = await llm.chat.completions.create(
>             model="gpt-5", messages=[{"role": "user", "content": q}], stream=True)
>         try:
>             async for chunk in stream:
>                 if delta := chunk.choices[0].delta.content:
>                     yield f"data: {delta}\n\n"    # SSE 帧不变量：data: 前缀 + 空行结尾
>             yield "data: [DONE]\n\n"              # 自定义结束帧，前端据此收尾
>         finally:
>             await stream.close()                  # 客户端断开 → 取消上游流，别让请求悬着
>     return StreamingResponse(gen(), media_type="text/event-stream")
>
> # 前端打字机（JS 伪代码，消费同一帧协议）：
> # const es = new EventSource("/chat?q=你好")
> # es.onmessage = e => { e.data === "[DONE]" ? es.close()
> #                       : (el.textContent += e.data) }   # 逐帧追加即打字机效果
> ```
>
>   - 关键不变量/边界：① 帧格式是硬约定：每帧 `data: ` 开头、空行结尾，漏空行前端永远不触发 `onmessage`；② 结束标记是自定义契约（`[DONE]`），前后端必须同版本约定，前端据此 `close()`；③ 每帧只放增量 delta，服务端不替前端拼全文。
>   - 怎么测：`curl -N http://localhost:8000/chat?q=hi` 肉眼看帧格式（前缀/空行/结束帧）；再用断言脚本收集全部 delta 拼接后与同步接口结果对比一致；断网/提前关连接测 `finally` 分支是否触发。
> - 追问与陷阱：
>   - 追问：为什么不用 WebSocket？常见错误：答不出取舍——聊天补全是"单向服务端推送"，SSE 够用且是纯 HTTP（代理/网关友好，自动重连内建）；需要双向交互（语音、协作）才上 WebSocket。MCP 的 Streamable HTTP 传输用的也是同族机制，学一次两处通用。
>   - 追问：生产里直接用裸 StreamingResponse 行吗？常见错误：可以但会缺心跳——长连接被网关空闲超时掐断，生产换 sse-starlette 的 `EventSourceResponse` 拿 ping 心跳与标准事件字段。
>   - 追问：多轮对话怎么接入流式接口？常见错误：每轮只发当轮消息——messages 是"完整历史全量发送"（无状态协议），服务端不替你记对话；历史管理在客户端/会话层做（见 Q123）。
> - 加分项：能给出延迟视角的收益解释——流式改善的是 TTFT（time to first token，首字延迟）之后的感知延迟而非真实总时长；或对比 Gradio `ChatInterface` 生成器逐步 yield 的三行版（python-handbook §7.3），说明"生成器逐步产出"是三种交付形态共享的同一机制。
> - 延伸阅读：[python-handbook §7.2 FastAPI + SSE 流式：LLM 服务的工业标准](../python-handbook/Python大模型应用开发手册.md)｜[python-handbook §3.2 openai SDK：流式与异步形态](../python-handbook/Python大模型应用开发手册.md)

> **Q116. 手写带超时与重试的 LLM API 客户端（指数退避）。**（难度：初 ｜ 频次：中）
> - 考察点：能否写一个对网络抖动、限流、瞬时故障稳健的 API 客户端：什么错误值得重试、退避怎么算、超时设在哪，以及"重试"与"幂等"的关系。
> - 参考回答：
>   - 接口设计要点：两层参数——`timeout`（单次请求的硬期限，连接+读取都要覆盖）与 `max_retries`（总尝试上限）；错误分两类：可重试（429 限流、5xx 服务端故障、超时/传输异常）与不可重试（4xx 参数/鉴权错，重试也没用）。
>   - 退避策略：指数退避（exponential backoff，间隔逐次翻倍）+ 随机抖动（jitter，打散重试时间防雪崩）+ 封顶（无限退避等于变相挂死）。SDK 内建的重试参数（如 openai SDK 的 `max_retries`）与 tenacity 这类库是生产首选，手写是为了面试讲清机制。
>   - 代码骨架：
>
> ```python
> import time, random, httpx
>
> RETRYABLE = {429, 500, 502, 503, 504}             # 只有"过会儿能好"的错误值得重试
>
> def chat(messages: list, max_retries: int = 3, timeout: float = 30.0) -> dict:
>     for attempt in range(max_retries + 1):
>         try:
>             r = httpx.post(API_URL, json={"model": "gpt-5", "messages": messages},
>                            headers=AUTH, timeout=timeout)   # 不变量①：必须显式设超时
>             if r.status_code < 400:
>                 return r.json()
>             if r.status_code not in RETRYABLE:            # 4xx 参数错：重试也没用
>                 raise RuntimeError(f"non-retryable {r.status_code}: {r.text[:200]}")
>         except (httpx.TimeoutException, httpx.TransportError) as e:
>             if attempt == max_retries:
>                 raise RuntimeError(f"retries exhausted: {e}") from e
>         backoff = min(1.0 * 2 ** attempt, 30)             # 指数退避：1s→2s→4s…封顶 30s
>         time.sleep(backoff + random.uniform(0, 0.5))      # 抖动：防雪崩式同时重试
>     raise RuntimeError("unreachable")
> ```
>
>   - 关键不变量/边界：① 必须显式设超时——httpx/requests 默认不超时，一个挂死的请求能拖垮整个 worker；② 重试耗尽要抛出带上下文的异常（最后一次错误），而不是返回 None 让上游猜；③ 重试只对幂等调用安全——纯推理调用天然可重试，带副作用的工具调用必须配幂等键才能重试（workflow-handbook §5.3 重试三要素）。
>   - 怎么测：mock 三种响应序列（一次成功、先 429 后 200、连续 429 耗尽），用假时钟或把退避参数注入为 0 避免测试变慢；断言尝试次数、退避序列与最终异常类型。
> - 追问与陷阱：
>   - 追问：429 要不要读 `Retry-After` 头？常见错误：无脑用本地退避——服务端明确给了等待时间就优先遵从，本地退避只在没给时兜底。
>   - 追问：重试会不会放大账单？常见错误：只算成功调用——每次尝试都产生 token 计费，重试预算要计入成本核算（Q117），评测跑批还要配预算熔断防止重试风暴烧穿预算（Q128）。
>   - 追问：流式调用怎么重试？常见错误：收到一半断流后从头重发却不处理"用户已看到的半截输出"——要么重发前通知上层重置 UI，要么改用可续传的会话协议；整体重试策略只包住"建流"阶段。
> - 加分项：能说出工作流视角的完整重试语义——重试三要素（条件/次数/间隔）+ 幂等约束 + 超时预算（workflow-handbook §5.3），以及评测执行器里 per-task 超时与全轮预算熔断的分工（eval-handbook §8.3）。
> - 延伸阅读：[python-handbook §3.2 openai SDK：方言的基准实现](../python-handbook/Python大模型应用开发手册.md)｜[workflow-handbook §5.3 幂等与重试：重试三要素 + 引擎默认值对照](../workflow-handbook/Agent工作流编排手册.md)

> **Q117. 手写一个 token 成本计算函数（四档单价）。**（难度：初 ｜ 频次：低）
> - 考察点：能否把"成本 = Σ(每档 token × 单价)"落成代码，并说清四档（普通输入/缓存读/缓存写/输出）的量级关系与缓存 token 的子集拆分——这是"能报账"的 FDE 基本功。
> - 参考回答：
>   - 接口设计要点：输入是模型名 + 单次调用的 usage（用量）字典，输出美元数；单价表外置成配置（模型信息当配置管不当代码管），换模型改表不改函数。
>   - 价格事实（官方定价页 2026-09-28 实抓，$/M）：Anthropic Fable 5.1 输入 $10 / 输出 $50（缓存写 $12.50、读 $0.25）；OpenAI gpt-5.2 输入 $1.75 / 输出 $14（缓存输入为 10% 价）；输出比输入贵 4-10×；批处理统一 -50%（tuning-handbook §7.1）。
>   - 代码骨架：
>
> ```python
> PRICING = {  # $/M token 四档（2026-09-28 官方定价页实抓）
>     "fable-5.1": {"in": 10.0, "cached_in": 0.25,  "cache_write": 12.50, "out": 50.0},
>     "gpt-5.2":   {"in": 1.75, "cached_in": 0.175, "cache_write": 0.0,   "out": 14.0},
> }                # OpenAI 免缓存写费；Anthropic 写 1.25×、读折扣价
>
> def call_cost(model: str, usage: dict) -> float:
>     """单次调用成本 = Σ(每档 token × 单价)。关键：cached_in/cache_write 是
>     普通输入的子集（usage.in 已包含它们），计费前必须先拆出来，否则重复计费。"""
>     p = PRICING[model]
>     cached  = usage.get("cached_in", 0)           # 命中缓存读的输入 token
>     written = usage.get("cache_write", 0)         # 写入缓存的输入 token
>     plain   = usage["in"] - cached - written      # 全价输入
>     return (plain   * p["in"]
>           + cached  * p["cached_in"]
>           + written * p["cache_write"]
>           + usage["out"] * p["out"]) / 1e6
> ```
>
>   - 关键不变量/边界：① 缓存命中的 token 已含在总输入里，计费前必须拆出，否则按全价重复计费（账单虚高）；② 账单最小粒度是"单次调用"，向上要能聚合到任务/会话/租户——归因链不可断，否则"降本"无从下手（eval-handbook §8.1）；③ provider 没回 usage 时按 0 处理会让成本被低估，宁可打标记也别静默跳过。
>   - 怎么测：构造已知 usage（如 in=50000、cached_in=40000、out=8000）手工算期望值断言；再加一条"cached_in > in 时应报错"的防呆用例。
> - 追问与陷阱：
>   - 追问：怎么让这个函数算出来的数和账单对上？常见错误：拿字符数估 token——中文按约 1.6 字符/token、英文按 4 字符/token 只是粗估（context-handbook §8.2 的 est_tokens 口径），对账必须用 API 返回的真实 usage。
>   - 追问：为什么说缓存命中率是成本第一杠杆？常见错误：只答"缓存便宜"——agent 每轮全量重发历史，输入是复利结构，命中率对账单是非线性影响：命中读价约为全价的十分之一（DeepSeek 低至约 2%），命中率异常下跌往往等于前缀漂移（Q128）。
> - 加分项：能顺手写出输出 token 视角的推论——输出比输入贵 4-10×，所以"约束输出长度、结构化输出"与"用大模型读小模型写"是两条主要省钱方向；离线评测/打标用批处理 API 统一 -50% 没有理由不用（tuning-handbook §7.1/§7.3）。
> - 延伸阅读：[tuning-handbook §7.1 token 成本核算：四档单价 × 用量](../tuning-handbook/Agent调优手册.md)｜[eval-handbook §8 成本与延迟工程](../eval-handbook/Agent评测与质量工程手册.md)

> **Q118. 手写一个 RAG 检索管线：切分→嵌入→混合检索→重排→组装。**（难度：中 ｜ 频次：高）
> - 考察点：能否把 RAG（Retrieval-Augmented Generation，检索增强生成）检索层写成一条两阶段管线：双路召回（稠密+稀疏）→ RRF 融合 → 交叉编码器重排 → 带引用组装，并说清每一步存在的理由（rag-handbook §2.5 接口规范 + python-handbook §5.5 的 40 行骨架）。
> - 参考回答：
>   - 接口设计要点：检索层对内暴露一个函数（`query/top_k/recall_k/filters/acl/mode` 参数即契约）；入库侧先做递归字符/结构感知切分（256-512 token、重叠 10-20%）与嵌入（归一化），检索侧双路各召回 `recall_k ≈ 50`，重排后取 `top_k = 5`。
>   - 两个"为什么"必须会答：RRF（Reciprocal Rank Fusion，倒数排名融合，按 Σ1/(k+rank) 合并排名）只用排名不用分数，免去稠密余弦分与 BM25 分的量纲校准；交叉编码器把 query 和 doc 拼在一起逐对精算，贵但准——所以"召回便宜取 50、重排昂贵取 5"是分工而非浪费。
>   - 代码骨架（python-handbook §5.5 混合检索 + 组装层）：
>
> ```python
> def hybrid_search(query: str, recall_k: int = 50, top_k: int = 5) -> list[dict]:
>     dense  = dense_search(query, recall_k)        # ① 稠密路：归一化嵌入 + 内积（语义）
>     sparse = sparse_search(query, recall_k)       # ② 稀疏路：BM25，接住错误码/型号/人名
>     fused: dict[str, float] = {}                  # ③ RRF 融合：只看排名不看分数，
>     for ranked in (dense, sparse):                #    免去两套分数量纲校准
>         for rank, (doc_id, _) in enumerate(ranked):
>             fused[doc_id] = fused.get(doc_id, 0.0) + 1 / (60 + rank + 1)
>     cand = [d for d, _ in sorted(fused.items(), key=lambda x: -x[1])][:top_k * 4]
>     scores = reranker.compute_score([[query, texts[d]] for d in cand])   # ④ 交叉重排：
>     order = sorted(zip(scores, cand), reverse=True)[:top_k]              # 逐对精算，贵但准
>     return [{"chunk_id": d, "score": s, **metas[d]} for s, d in order]   # ⑤ 元数据随行
>
> def answer(question: str) -> dict:                # 组装层：引用是可信度的一部分
>     hits = hybrid_search(question)
>     ctx = "\n\n".join(f"[{h['source_uri']}] {texts[h['chunk_id']]}"
>                       for h in hits if h["score"] >= SCORE_FLOOR)  # 低分宁可不喂
>     return {"answer": llm(q=question, ctx=ctx), "citations": [h["source_uri"] for h in hits]}
> ```
>
>   - 关键不变量/边界：① 嵌入必须 `normalize=True`，之后内积才是余弦相似度；换嵌入模型 = 换向量空间，新旧向量绝不可混存；② BM25 中文必须先分词（jieba），不分词整句当一个词召回为 0；③ 元数据过滤与 ACL（权限）在检索层做，不在生成层做；④ 分数低于阈值的片段宁可不给，低相关要显式告警而不是硬编。
>   - 怎么测：黄金数据集回归（一组"问题 → 应命中的 chunk_id"），跑 Recall@k 与端到端答案断言；改切分参数/换嵌入模型前后各跑一遍，分数与 embedding 版本一起留指纹（rag-handbook §6.2/§6.3）。
> - 追问与陷阱：
>   - 追问：BM25 都有向量了还要它干嘛？常见错误：答"可有可无"——错误码、型号、人名这类精确词是嵌入的盲区，稀疏路就是补这个的；双索引（稠密+稀疏）是企业 RAG 的标配（rag-handbook §2.4）。
>   - 追问：检索对了答案还是错，查哪？常见错误：无差别调参——先分诊：召回率低治切分/嵌入，召回高但答案错治生成约束与引用；忠实度和召回率是两个指标别混着治（tuning-handbook §3.1）。
>   - 追问：`recall_k` 和 `top_k` 为什么不等？常见错误：直接一路取 top-5——重排要看候选才有得挑，先粗筛 50 再精排 5 才是"便宜召回 + 昂贵精算"的两阶段结构；想省重排成本时也只应缩 `top_k*4` 的候选池。
> - 加分项：能报出 Anthropic Contextual Retrieval 的量级证据（每个 chunk 前置小模型生成的上下文说明，top-20 检索失败率 5.7% → 上下文嵌入 3.7% → +上下文 BM25 2.9% → +重排 1.9%，合计 -67%，rag-handbook §2.2），说明检索质量的提升空间主要在索引侧而不是换更大的生成模型。
> - 延伸阅读：[rag-handbook §2.5 检索接口规范](../rag-handbook/RAG搭建文档.md)｜[rag-handbook §3.3 生产化三步：混合检索 + 重排 + 父子检索](../rag-handbook/RAG搭建文档.md)｜[python-handbook §5.5 端到端最小混合检索](../python-handbook/Python大模型应用开发手册.md)

> **Q119. 手写一个评测脚本：dataset→runner→judge→报告。**（难度：高 ｜ 频次：中）
> - 考察点：能否搭出评测（evaluation）的最小闭环四文件：评测集（jsonl）→ 被测 agent → 判据分派 → 跑分报告，并说清判据优先级（代码 > 规则 > LLM judge）、数据集指纹与成本归因三个工程点（eval-handbook §10.1，已本机验证）。
> - 参考回答：
>   - 接口设计要点：被测系统只有一条契约——输入 task dict，输出 `{"final_answer", "tool_calls", "usage"}`（答案+轨迹+用量），这样 agent 实现可整体替换；判据（criteria）写进数据集而不是跑分时现写——设计期冻结判据，判据错是独立于模型错的归因类。
>   - 判据分派按成本递增：`contains_all`（关键词全含）、`refuse`（该拒答的拒答）这类代码判据不花钱且可复现，永远先行；只有开放维度才走 LLM judge，且 judge 上岗前要用 50-100 条人工标注校准（一致率与 Cohen's κ，κ>0.6 可用、>0.8 可信，eval-handbook §5.4）。
>   - 代码骨架（eval-handbook §10.1 的 run.py）：
>
> ```python
> # 四文件闭环：tasks.jsonl（评测集）→ agent.py（被测）→ judge.py（判据）→ run.py（跑分）
> def load_tasks(path: str) -> list[dict]:
>     return [json.loads(l) for l in Path(path).read_text("utf-8").splitlines() if l.strip()]
>
> def fingerprint(tasks: list[dict]) -> str:        # 数据集指纹：改集必留痕，报告才可比
>     return hashlib.sha256("\n".join(sorted(t["id"] for t in tasks)).encode()).hexdigest()[:16]
>
> def main() -> None:
>     tasks = load_tasks("tasks.jsonl")
>     rows, bill = [], 0.0
>     for t in tasks:
>         out = solve(t)                            # 被测 agent：输入 task，输出答案+轨迹+usage
>         ok, evidence = judge(t, out)              # 判据分派：代码判据优先（不花钱可复现），
>         bill += call_cost("gpt-5", out["usage"])  # llm_judge 兜开放维度（须先校准）
>         rows.append({"id": t["id"], "type": t["type"], "pass": ok, "evidence": evidence})
>     passed = sum(r["pass"] for r in rows)
>     print(f"# 报告 指纹={fingerprint(tasks)} 通过 {passed}/{len(rows)} 账单 ${bill:.4f}")
>     for r in rows:
>         print(f"- [{'PASS' if r['pass'] else 'FAIL'}] {r['id']} ({r['type']}) {r['evidence']}")
> ```
>
>   - 关键不变量/边界：① 报告必须带数据集指纹与账单——没指纹的报告换集后不可比，没账单的评测没法算 ROI；② judge 结果要带 evidence（引用原文的证据），"先摘录再打分"等价于 CoT-before-score，能显著压幻觉判分；③ 评测集混入调参集 = 门禁失效，dev 看 dev 集、验收看 held-out（封存集）。
>   - 怎么测：先用规则 stub 当被测 agent 跑通全链路（eval-handbook §10.1 的三条示例任务含一条拒答题），断言报告的通过数与 FAIL 明细；再换真 agent、真 judge 分两步接入，保证任何时刻闭环可跑。
> - 追问与陷阱：
>   - 追问：只评最终答案行不行？常见错误：行但会漏——"答对了但 15 步、带幻觉工具"的坏例抓不到，要加轨迹断言（调用了不该调的工具、步骤数超限、预算超支）与失败归因五分类（eval-handbook §6）。
>   - 追问：通过率怎么报才可信？常见错误：单次采样报通过率——非确定性任务要用 pass^k（每条跑 k 次全过才算过）或分桶报；判据用 1-10 分比均值更不可信，分档语义锚定才是正解。
>   - 追问：评测烧钱怎么控？常见错误：不设预算裸跑——per-task 超时 + 全轮预算熔断（触顶即停并出部分报告），见 Q128；全量 judge 无仲裁会让 judge 账单比 agent 还贵，金字塔仲裁（规则先行→judge→人审争议）才是成本最优结构。
> - 加分项：能说出"评测进 CI"的落地形态——prompt/deepeval 把评测变测试，每次 prompt/模型/工具变更跑 diff；或引 trace→dataset 闭环：线上点踩样本自动回流成回归用例（eval-handbook §7.3）。
> - 延伸阅读：[eval-handbook §10.1 全景：四个文件构成的最小闭环](../eval-handbook/Agent评测与质量工程手册.md)｜[eval-handbook §2.3 判据谱系：可验证 reward 优先](../eval-handbook/Agent评测与质量工程手册.md)｜[eval-handbook §4.3 成功判据设计：每条样本写"可判定"的期望](../eval-handbook/Agent评测与质量工程手册.md)

> **Q120. 手写一个文本切分器：递归字符切分 + 重叠 + 元数据。**（难度：中 ｜ 频次：高）
> - 考察点：能否手写递归字符切分（recursive character splitting，按分隔符层级递归找自然边界）的骨架，说清 chunk（切分块）大小/重叠的取值依据与元数据三硬规则——切分是检索质量的第一因，这题直接检验有没有真搭过知识库。
> - 参考回答：
>   - 接口设计要点：`recursive_split(text, size, overlap)` 返回块列表；外层再包一个 `chunk_with_meta(doc)` 给每块挂元数据。切分目标不是越细越好，而是"每个块既容易被问题命中、又能独立支撑回答"（rag-handbook §2.2 的第一句话）。
>   - 参数基线要背得住：chunk 大小 256-512 token 起步（事实型问答可降到 128-256），重叠（overlap）10-20%；不要套框架默认值，要在自有语料上做参数扫描（256/512/1024 × 0/10/20% overlap）用黄金集对比 Recall@k。
>   - 代码骨架：
>
> ```python
> SEPS = ["\n\n", "\n", "。", "，", ""]             # 分隔符层级：段→行→句→字（最粗优先）
>
> def recursive_split(text: str, size: int = 400, overlap: int = 40) -> list[str]:
>     """递归字符切分：优先在自然边界断开；块间带 overlap，防结论与条件被腰斩。"""
>     if len(text) <= size:
>         return [text.strip()] if text.strip() else []
>     for sep in SEPS:
>         if sep and sep in text:                   # 找到当前能用的最粗边界
>             chunks, cur = [], ""
>             for piece in text.split(sep):
>                 if len(cur) + len(piece) <= size: # 装得下就继续攒
>                     cur += piece + sep
>                 else:
>                     if cur:
>                         chunks.append(cur)
>                         cur = cur[-overlap:]      # 重叠：新块带上前块的尾巴
>                     cur += piece + sep
>             if cur:
>                 chunks.append(cur)
>             return chunks
>     return [text[i:i + size] for i in range(0, len(text), size - overlap)]  # 硬切兜底
>
> def chunk_with_meta(doc: dict) -> list[dict]:     # 元数据三硬规则（rag-handbook §2.3）
>     return [{"chunk_id": f"{doc['doc_id']}#chunk-{i:03d}",   # 可复现：重导不换 id
>              "text": c, "source_uri": f"{doc['uri']}#chunk-{i}",
>              "version": doc["version"], "acl": doc["acl"]}   # 版本与权限随行入库
>             for i, c in enumerate(recursive_split(doc["text"]))]
> ```
>
>   - 关键不变量/边界：① chunk_id 必须可复现（同文档重导不换 id），否则增量更新退化为全量重灌；② 权限元数据与文档同批入库、版本/生效日期必须有——过期制度继续被命中是企业场景第一大事故源；③ 表格按行切、表头随行走，结构感知切分是企业文档的首选而非递归字符。
>   - 怎么测：拿真实制度文档跑切分，人工抽查 10 块看是否"只有结论没有条件/只有数据没有表头"这类坏块；参数扫描后用黄金集 Recall@k 选参，而不是拍脑袋。
> - 追问与陷阱：
>   - 追问：重叠的 overlap 取多大、为什么？常见错误：拍 0% 或照抄默认值——重叠是为了"边界两侧的关键句至少完整出现在一个块里"，10-20% 是业界共识基线（Pinecone/Weaviate 指南，rag-handbook §2.2），具体值用黄金集扫出来。
>   - 追问：小块命中但大块才够回答怎么办？常见错误：把块切得超大——正解是父子检索（小块检索、大块喂模型，small-to-big）：用子块精确命中，返回父块或句子窗口给 LLM。
>   - 追问：长度按字符还是 token 算？常见错误：统一按字符——中文一个字符≈0.6 token（约 1.6 字符/token），混排文档按字符切会系统性偏大；预算口径用 token 实算或至少分语种估算。
> - 加分项：能给出两个进阶技巧的名字与机理——Anthropic Contextual Retrieval（每块前置 50-100 token 的全文背景说明再索引，top-20 失败率合计降 67%）与 Late Chunking（先整篇嵌后切，块向量天然携带全文上下文，rag-handbook §2.2）。
> - 延伸阅读：[rag-handbook §2.2 切分（Chunking）规范：本文最重要的一节](../rag-handbook/RAG搭建文档.md)｜[rag-handbook §2.3 元数据规范：每条 chunk 必须带什么](../rag-handbook/RAG搭建文档.md)｜[python-handbook §5 RAG 工具链 Python 侧](../python-handbook/Python大模型应用开发手册.md)

> **Q121. 手写带权限闸门的工具调用循环（含并行执行）。**（难度：高 ｜ 频次：中）
> - 考察点：能否在 Q113 的裸循环上叠加生产护栏：执行前的 deny-by-default（默认拒绝）权限闸门、"全只读才并发"的并行规则、并发结果按原始 id 排序回填——这是六家 coding agent 主循环之上真正叠加的东西。
> - 参考回答：
>   - 接口设计要点：闸门（gate）是所有危险动作的唯一入口，策略三件套——只读白名单（可并发资格）、危险动作清单、本会话人工批准集；闸门判定发生在执行之前，不是事后审计（security-handbook §6.5 ActionGate 的设计：识别注入靠不住，约束动作才可靠）。
>   - 并行规则抄 anon-kode：全部工具都是只读时才并发（受并发上限约束）；只要有一个写操作就退回串行，保证写操作顺序确定；并发完成后按原始 `tool_use` 的 id 顺序重排回填，保证与请求一一对应（01-claude-code/架构拆解 §3.1 第 5-7 步）。
>   - 代码骨架：
>
> ```python
> class ActionGate:                                 # 权限闸门：deny-by-default
>     def __init__(self):
>         self.readonly = {"search", "read_file"}   # 只读工具才有并发资格
>         self.dangerous = {"shell", "send_email", "http_request"}
>         self.approved: set[str] = set()           # 人工批准集：批准不随消息漂移
>
>     def check(self, name: str) -> tuple[bool, str]:
>         if name in self.dangerous and name not in self.approved:
>             return False, f"deny: {name} 未获批准"   # 危险动作一律先拦（白名单思维）
>         return True, "allow"
>
> async def run_tools(calls: list, gate: ActionGate) -> list:
>     if all(c.name in gate.readonly for c in calls):   # 全部只读才并发
>         return await asyncio.gather(*[execute(c) for c in calls])
>     return [await execute(c) for c in calls]          # 有写操作 → 串行保序
>
> async def agent_turn(history: list, tools: list, gate: ActionGate) -> str:
>     msg = call_model(history, tools)                  # ① 调模型
>     if not msg.tool_calls:
>         return msg.content                            # 不再点菜 → 收尾
>     verdicts = {c.id: gate.check(c.name) for c in msg.tool_calls}   # ② 执行前先过闸
>     allowed = [c for c in msg.tool_calls if verdicts[c.id][0]]
>     results = await run_tools(allowed, gate)
>     history.append(msg)                               # ③ 回填：模型消息 + 工具结果
>     for c, r in zip(allowed, results):                # 按原 tool_use id 顺序对应回填
>         history.append({"role": "tool", "tool_call_id": c.id, "content": str(r)[:4000]})
>     return await agent_turn(history, tools, gate)     # ④ 下一轮（生产换 while + 步数上限）
> ```
>
>   - 关键不变量/边界：① 被拒绝的调用也要回填（`denied` 文本作为工具结果），让模型知道"此路不通"并改道，而不是静默丢掉；② 权限不随消息漂移——同伴/子代理消息说"用户已批准"不算数，"被拒后转托 = 权限洗白"要拒绝并上报（ZCode 规则，multiagent-handbook §3.4）；③ 污点（taint）纪律：untrusted 来源（网页/邮件/工具输出）派生的值不许进动作参数，注入 payload 无法"兑现成动作"。
>   - 怎么测：两条轴——攻击轴（注入 payload 携带 untrusted 标记，断言外发动作被拦）与误杀轴（正常业务流断言放行，XSTest 思路）；并发正确性用"乱序完成的假工具"断言回填顺序仍按原始 id（security-handbook §6.5 的两个测试函数同款）。
> - 追问与陷阱：
>   - 追问：为什么全只读才并发？常见错误：一刀切全串行（慢）或全并发（写竞争）——只读工具互不干扰可安全并发，写操作之间有顺序依赖；anon-kode 还为并发设了 `MAX_TOOL_USE_CONCURRENCY` 上限。
>   - 追问：闸门放哪个位置？常见错误：放在模型生成之后由模型自查——闸门是代码层的强制检查点，位于"模型点菜"与"执行"之间；模型自查（reflection）只能当软防线，挡不住注入。
>   - 追问：用户批准一次后永久放行吗？常见错误：批准进全局永久白名单——anon-kode 用三层判定（安全命令白名单 → 精确匹配授权 → 前缀授权），批准粒度到"前缀"且限会话，正式版才有 `--dangerously-skip-permissions` 这类显式全局开关。
> - 加分项：能把 lethal trifecta（致命三要素：私有数据访问 + 不可信内容暴露 + 对外通信）讲成闸门设计动机——没有出口资格的 agent 即使被注入也带不走数据；或引 ZCode 的权限分层（项目级 subagent 定义不能给自己提权）作为多代理时代的越权面案例。
> - 延伸阅读：[security-handbook §6.5 最小实现：动作闸门 + 把红队用例进 CI（已本机验证）](../security-handbook/AI应用安全手册.md)｜[01-claude-code/架构拆解.md §5 权限与安全](../01-claude-code/架构拆解.md)｜[01-claude-code/架构拆解.md §3 Agent 主循环（核心）](../01-claude-code/架构拆解.md)

> **Q122. 手写结构化输出解析：Pydantic 校验 + 失败重试。**（难度：中 ｜ 频次：中）
> - 考察点：能否把"模型吐 JSON"做成可靠的解析层：Pydantic 校验、失败定向回喂重试、耗尽走兜底分支，并说清四级方案的优先级（tuning-handbook §6.3）——F4（格式不合规）类失败的根治路径。
> - 参考回答：
>   - 接口设计要点：输出合同用 Pydantic 类定义（字段/类型/枚举/约束一次写全），`model_validate_json` 做入口校验；四级方案按优先级组合——① API 级结构化输出（JSON Schema 约束解码，约束在解码层比提示词可靠一个量级）→ ② schema 校验 + 定向重试（一次为限）→ ③ 固定字段模板 + 禁解释（无 schema 支持时的下策）→ ④ 确定性逻辑出提示词（时间戳/编号/计算永远让工具生成，不让模型"写"）。
>   - 重试的关键是"定向"：把校验错误的具体字段与原因回喂（"route 字段必须是枚举值之一"），而不是笼统地说"输出不合法请重来"；重试两次仍失败进人工/兜底分支，绝不硬编一个值。
>   - 代码骨架：
>
> ```python
> from typing import Literal
> from pydantic import BaseModel, Field, ValidationError
>
> class Route(BaseModel):                           # 输出合同：字段/类型/枚举全进 schema
>     route: Literal["退款", "物流", "转人工"] = Field(description="路由分支")
>     order_id: str = ""
>     need_human: bool = False
>
> def parse_structured(raw: str, model: type[BaseModel], retries: int = 1) -> BaseModel:
>     """四级方案组合：① API 约束解码优先；② 校验失败定向回喂重试；耗尽走兜底。"""
>     for _ in range(retries + 1):
>         try:
>             return model.model_validate_json(raw)          # 类型/枚举/缺失字段一次全查
>         except ValidationError as e:
>             hint = "; ".join(f"{'.'.join(map(str, x['loc']))}: {x['msg']}"
>                              for x in e.errors()[:3])      # 具体错误定向回喂，不笼统重问
>             raw = llm(f"你的输出不符合 schema：{hint}。只输出修正后的 JSON，无解释。")
>     return model(route="转人工", need_human=True)          # 重试耗尽 → 兜底分支，绝不硬猜
> ```
>
>   - 关键不变量/边界：① 缺失字段要有显式规则（"无法判断时 intent 输出其他、need_human 输出 true"，ADP 的缺失值纪律），而不是让模型自由发挥；② 兜底分支必须是业务上安全的动作（转人工），不是默认成功；③ 解析层要无状态可重放——同输入同输出才可回归测试。
>   - 怎么测：三组用例——合法 JSON、类型错（数字当字符串）、枚举外值，断言校验拦截与重试后的 hint 文本；把"重试耗尽走兜底"也断言进去；真模型下统计格式合规率作 baseline 再上约束解码对比。
> - 追问与陷阱：
>   - 追问：为什么 API 级结构化输出比提示词约束可靠？常见错误：只答"更准"——约束解码（constrained decoding）在采样时直接禁掉不合法 token，是解码层的硬约束；提示词约束是软约束，模型仍可能"礼貌性"输出解释文字。
>   - 追问：枚举值模型总填错怎么办？常见错误：加重试次数——先检查枚举定义是否进了 schema（Literal/enum），再检查 description 是否说清了每个取值的含义；枚举错误多半是 schema 设计问题不是模型能力问题。
>   - 追问：嵌套模型/列表怎么处理？常见错误：手写递归解析——Pydantic 天然支持嵌套模型与 `list[Model]`，让校验器处理结构，自己只写业务映射。
> - 加分项：能引 python-handbook §3.2⑤ 的服务端 parse 用法（Pydantic 类 → JSON Schema → 约束解码，拿到即合法实例）与 google-genai 的 `response_schema` 直收 Pydantic 类型，说明"类型即协议"这条链在四家 SDK 全通用。
> - 延伸阅读：[tuning-handbook §6.3 结构化输出模式](../tuning-handbook/Agent调优手册.md)｜[python-handbook §2.4 类型标注与 Pydantic](../python-handbook/Python大模型应用开发手册.md)

> **Q123. 手写对话历史管理：滑动窗口 + 摘要压缩。**（难度：中 ｜ 频次：中）
> - 考察点：能否实现上下文（context）管理的核心机制——三层预算（剪枝→摘要→熔断）与"日志为真源，压缩只改投影"不变量，而不是把窗口当记事本无限塞（context-handbook §2/§8，最小实现已本机验证）。
> - 参考回答：
>   - 接口设计要点：两个结构分离——`SessionLog`（原始日志，只追加，永不改写）与 `project()`（从日志投影出模型可见历史，纯函数）；压缩是投影变换：摘要顶到最前、被摘要区间退出投影、旧工具结果换占位符，原始事件原样保留可审计。
>   - 层次要答全：第一层剪枝（microcompact，只把旧 tool result 换占位符，保留最近 5 条）代价近零先做；第二层摘要（compact，历史摘要化，最近几条逐字保留的 tail 策略）有损靠提示词保真；第三层反应式压缩 + 熔断（压缩后仍超预算就抛错，绝不无限压缩）。ZCode 的参数可作参照：阈值 0.9 触发、输出预留与 buffer 分开留。
>   - 代码骨架（context-handbook §8.2 mini_agent 的投影骨架）：
>
> ```python
> class History:
>     """对话历史管理：日志为真源，压缩只改投影（context-handbook §2.3）。"""
>     def __init__(self, budget: int = 4000):
>         self.log: list[dict] = []                  # 原始日志：只追加，永不改写（可审计）
>         self.summary: str | None = None            # 压缩摘要：投影层产物
>         self.cutoff = 0                            # 摘要已覆盖 log[:cutoff]
>         self.budget = budget
>
>     def append(self, msg: dict) -> None:
>         self.log.append(msg)                       # 写路径唯一：一切消息先进日志
>
>     def project(self) -> list[dict]:               # 投影是纯函数：坏了一删了之重投
>         head = [{"role": "system", "content": self.summary}] if self.summary else []
>         tail = self.log[self.cutoff:]
>         return head + prune_old_tool_results(tail, keep=5)   # 剪枝先于摘要（第一层）
>
>     def compact(self, summarize) -> None:          # 第二层：摘要替换
>         victims = self.log[self.cutoff:-2]         # 最近 2 条逐字保留（tail 策略）
>         if len(victims) < 2:
>             return
>         self.summary = summarize(render(victims))  # 摘要提示词：9 段结构 + 安全指令逐字保留
>         self.cutoff = len(self.log) - 2
>
>     def enforce(self, used: int) -> str:           # 预算执行：一层只升一级
>         if used < self.budget * 0.9:
>             return "ok"                            # 90% 触发（ZCode thresholdRatio 0.9）
>         self.compact(summarize)                    # microcompact 已在 project() 内做
>         assert used < self.budget, "压缩后仍超预算：熔断，绝不无限压缩"
>         return "compact"
> ```
>
>   - 关键不变量/边界：① 剪枝先于摘要——工具结果是信噪比衰减最快的部分（第 3 轮读的文件第 30 轮只剩"我读过它"），先清旧工具结果常常就够了；② 摘要提示词必须"安全相关指令逐字保留"（ZCode 摘要提示词两次强调），且旧摘要作为 previousSummary 参与再压缩；③ "压缩-回填死循环"要熔断：压缩后立刻又满说明有东西在快速回灌，继续压只是烧钱。
>   - 怎么测：注入大体积工具输出撑爆预算，断言 trace 显示三层依次升级、投影头部是摘要而原始日志长度不变；再加 untrusted 内容断言其永不进入长期记忆（context-handbook §8.2 实跑输出就是这套断言）。
> - 追问与陷阱：
>   - 追问：为什么不直接截断最老的消息？常见错误：硬截断破坏两样东西——最前面的稳定前缀（缓存锚点，砍了缓存全失效）与安全指令（摘要/截断都可能丢）；从后往前剪 + 摘要顶到 system 位才是六家的通行做法。
>   - 追问：token（词元）预算怎么估？常见错误：字符数÷4——对中文显著低估；CJK 要单独计（约 1.6 字符/token），OpenCode 的"字符/4"就是被点名的粗估反例，provider 有 usage 回报时优先用真值。
>   - 追问：滑动窗口和摘要压缩什么关系？常见错误：当成二选一——滑动窗口（保最近 N 条）只是最粗的截断，生产是"剪枝→摘要→新窗口"的梯度：工具结果→占位符，对话历史→摘要，宁可新开窗口也不无限摘要。
> - 加分项：能给出缓存锚点与压缩的交集纪律——段序稳定 + cache-control 在投影之后统一设置 + 动态内容追加在稳定前缀之后（context-handbook §2.6），并点出"每轮都变的系统提示词（时间戳、随机 ID）"是缓存报废的反面教材。
> - 延伸阅读：[context-handbook §2 上下文预算与压缩机制：三层模型与六家横向对照](../context-handbook/Context与记忆系统手册.md)｜[context-handbook §8 从零搭一个带工作记忆 + 长期记忆的最小 agent](../context-handbook/Context与记忆系统手册.md)

> **Q124. 手写一个 prompt 模板渲染器（变量/条件/版本指纹）。**（难度：中 ｜ 频次：低）
> - 考察点：能否把提示词当工程资产管理：模板与数据分离、条件块控制段落显隐、每次运行固化版本指纹（version fingerprint，模板+变量哈希）——对应调优闭环第五步"固化：版本记录 + 指纹 + 基线更新"（tuning-handbook §1.1）。
> - 参考回答：
>   - 接口设计要点：模板是带 id/version 的资产（不可变，改版 = 新版本号），渲染函数 `render(tpl, **vars)` 只做变量替换与条件块，禁止在渲染层做业务逻辑；每次运行记录 `(version, fingerprint)`，回归报告才能跨版本可比。
>   - 条件块要克制：只支持布尔变量控制段落显隐（`{%if strict%}...{%endif%}`），不要在提示词里发明编程语言——复杂控制流属于代码层编排，不属于模板层；提示词正文的结构照八区块模板组织（身份/任务/上下文/约束/格式/示例/安全/收尾，prompt-handbook §2.4 的生产模板），模板渲染器只负责拼装。
>   - 代码骨架：
>
> ```python
> import hashlib, json, re
>
> TPL = {"id": "support-system", "version": "v3.2.1",
>        "body": "你是{role}。{%if strict%}仅依据资料回答，不知道就承认。{%endif%}"
>                "上下文：{context}"}
>
> def render(tpl: dict, **vars) -> str:
>     text = tpl["body"]
>     for m in re.finditer(r"\{%if (\w+)%\}(.*?)\{%endif%\}", text, re.S):
>         text = text.replace(m.group(0),              # 条件块：布尔变量控制段落显隐
>                             m.group(2) if vars.get(m.group(1)) else "")
>     return text.format(**vars)                       # 变量替换：缺变量 KeyError 直接暴露
>                                                      # （禁止静默填空字符串兜底）
>
> def fingerprint(tpl: dict, vars: dict) -> str:       # 版本指纹：可复现性的锚
>     payload = json.dumps({"id": tpl["id"], "v": tpl["version"],
>                           "body": tpl["body"], "vars": vars},
>                          sort_keys=True, ensure_ascii=False)
>     return hashlib.sha256(payload.encode()).hexdigest()[:12]
> # 用法：每次运行记录 (tpl["version"], fingerprint(...))，回归报告才能跨版本可比
> ```
>
>   - 关键不变量/边界：① 缺变量必须报错而不是静默填空——静默兜底会让"该有的上下文没注入"变成线上事故才发现；② 指纹要覆盖模板正文 + 版本号 + 全部变量值，数据变了指纹就变，旧基线自动失效（"不可比"要显式暴露，tuning-handbook 的基线指纹纪律）；③ 模板渲染是纯函数：同输入同输出，才配得上回归评测。
>   - 怎么测：变量齐全/缺失/条件开闭三组用例；同一输入渲染两次指纹一致；改一个变量断言指纹变化——这条就是"单变量变更"实验能归因的前提（每轮只改一个变量，其余冻结）。
> - 追问与陷阱：
>   - 追问：为什么要版本指纹而不是只在 git 里管模板？常见错误：以为 git 提交记录等于运行指纹——线上跑的是哪版模板+哪组变量要从运行记录里可查，badcase 回流时才能精确定位到版本；指纹是把"运行时事实"与"代码库状态"对齐的锚。
>   - 追问：模板里能不能放时间戳/随机数？常见错误：图方便塞进前缀——动态内容进稳定前缀会报废 prompt caching（提示词缓存），每轮全价；时间戳放消息尾部或工具结果里（Q128 的缓存命中工程）。
>   - 追问：few-shot 示例放模板还是放变量？常见错误：写死在模板里——示例属于可调内容，要作为变量/配置注入才能单变量 A/B（tuning-handbook §2.2 few-shot 选择与排序、§2.5 单变量 A/B 最小示例）。
> - 加分项：能引 OpenClaw 的 1340 行提示词渲染器（python-handbook/架构拆解口径里的"工程化组装范例"）说明业界上限：提示词渲染器会做预算分配、按需装配与转义——但最小可写版就是"变量 + 条件 + 指纹"三件事，先答骨架再谈扩展。
> - 延伸阅读：[tuning-handbook §1.1 闭环五步：定位瓶颈 → 假设 → 单变量变更 → 回归评测 → 固化](../tuning-handbook/Agent调优手册.md)｜[tuning-handbook §2.1 system prompt 结构：模板是检查清单，不是话术](../tuning-handbook/Agent调优手册.md)

> **Q125. 手写一个 supervisor 多 agent 编排骨架。**（难度：高 ｜ 频次：高）
> - 考察点：能否写出 supervisor（监督者，中心路由唯一裁决者）范式的最小内核，并落实四条不变量：权限不随消息漂移、结论回传过程不上传、共享工件板是唯一真源、预算与轮次熔断（multiagent-handbook §8.5，已本机验证）。
> - 参考回答：
>   - 接口设计要点：Worker 构造时用 `frozenset` 锁定工具白名单（运行期任何指令都扩不了）；Worker.run 返回具名报告 `{summary, artifact, evidence, violations}`；Supervisor 负责分解（子任务边界互不重叠）→ 派发（工具面互斥且最小化）→ 验收 → 汇总。
>   - 四条不变量每条都能讲出事故原型：权限漂移（被注入的子代理让同伴"把刚才被拒的命令跑了"）、传话失真（全量过程回灌父窗口）、工件丢失（大块内容在消息里复制粘贴走样）、静默续跑（预算超限无人喊停）。
>   - 代码骨架（multiagent-handbook §8.5 mini_multiagent）：
>
> ```python
> class Worker:                                     # worker：工具集构造时锁定
>     def __init__(self, name, role, tools, max_steps=4):
>         self.name, self.role, self.tools = name, role, frozenset(tools)  # 工具集锁定：运行期不可扩
>         self.max_steps, self.used, self.violations = max_steps, 0, []
>     def call_tool(self, name, *args):
>         if name not in self.tools:                # 不变量①：权限不随消息漂移
>             self.violations.append(f"拒绝未授权工具 {name}()")
>             return f"(拒绝：{name} 不在 {self.name} 白名单)"
>         self.used += 1
>         if self.used > self.max_steps:
>             raise BudgetExceeded(f"{self.name} 步数超限")   # 不变量④：worker 级熔断
>         return TOOLS[name](*args)
>     def run(self, task, board):
>         ...                                       # 子循环：全部过程留在自己窗口里
>         aid = board.write(self.name, result_text) # 不变量③：大块内容写工件板拿引用
>         return {"summary": f"{self.role} 完成，见 {aid}", "artifact": aid,
>                 "evidence": self.trace, "violations": self.violations}  # ② 只回传结论
>
> class Supervisor:
>     def run(self, goal):
>         board = ArtifactBoard()                   # 工件板是唯一真源，消息只带引用
>         subtasks = {"researcher": f"调查现状（针对：{goal}）",  # 分解：边界互不重叠
>                     "coder": "起草最小补丁（只动目标函数）"}
>         workers = {"researcher": Worker("researcher", "调研员", ["search", "read_file"]),
>                    "coder": Worker("coder", "工程师", ["read_file"])}  # 工具面互斥且最小
>         reports = {n: w.run(subtasks[n], board) for n, w in workers.items()}
>         for n, r in reports.items():              # 验收门：核对可定位证据，不听自述
>             assert r["artifact"] and r["evidence"], f"{n} 交付不合格"
>         return {"answer": summarize(reports), "artifacts": [r["artifact"] for r in reports.values()],
>                 "escalations": [v for r in reports.values() for v in r["violations"]]}
> ```
>
>   - 关键不变量/边界：① 回传"简明报告"而非全量过程：报告 = 结论 + 可定位证据（文件:行号、命令与退出码）+ 未决问题，父代理核对证据而不是听自述（verify the world，multiagent-handbook §3.3）；② 只把摘要计入主代理上下文——手册最小实现实测主代理开销约 36 token，两个 worker 的全过程都留在各自窗口；③ 越权尝试不是静默丢弃，要上报（escalations）进验收结果。
>   - 怎么测：三个断言——worker 调白名单外工具被拒且有记录；报告缺工件引用或证据时验收门拒绝；预算/步数超限抛 `BudgetExceeded` 而非静默续跑。手册实跑输出（两个越权拒绝、工件引用、约 36 token 主上下文）就是验收标准。
> - 追问与陷阱：
>   - 追问：worker 之间要不要直接通信？常见错误：默认要——supervisor 范式的定义就是中心路由、唯一裁决者，worker 互聊等于把控制流交给消息传递（swarm 才那么做）；需要协作时由 supervisor 显式转发，权限与上下文边界才可审计。
>   - 追问：子代理能用父代理的全部工具吗？常见错误：默认继承——"隔离即权限"：子代理工具面互斥且最小化（researcher 无写工具、coder 不给检索）；六家里有引擎明文"子代理默认拿不到 session/message 工具"，防横向扩张。
>   - 追问：为什么验收门不能省？常见错误：信 worker 的自述"已完成"——MAST 失败分类学里"投机取巧/提前收工"是高频失败类；验收核对的是工件存在 + 证据非空这类可验证状态。
> - 加分项：能给出撤退判据——多 agent 不是免费的（交接损耗、成本翻倍），"何时合并回单 agent"有明确判据（tuning-handbook §5.4），而六家 coding agent 的选择是"主循环 + 委派"而不是真多 agent，可作为反直觉论据。
> - 延伸阅读：[multiagent-handbook §8.5 从零搭一个最小双 Agent 协作（Python 3，已本机验证）](../multiagent-handbook/Multi-Agent协同手册.md)｜[multiagent-handbook §3.3 交接协议四条（可以直接抄）](../multiagent-handbook/Multi-Agent协同手册.md)｜[context-handbook §3 子代理上下文隔离与信息传递](../context-handbook/Context与记忆系统手册.md)

> **Q126. 手写一个最小工作流编排器：DAG + guard 分支 + 幂等重试。**（难度：高 ｜ 频次：高）
> - 考察点：能否手写工作流引擎的最小内核——DAG（Directed Acyclic Graph，有向无环图）拓扑执行 + guard 条件分支 + 幂等键重试 + 异常分支——并说清四条不变量（workflow-handbook §8 的 miniflow，约 250 行纯标准库，已本机验证）。
> - 参考回答：
>   - 接口设计要点：图定义 = 节点 dict，每个节点声明 `deps`（数据依赖即画布连线）、`run(ctx)`（执行函数）、`outputs`（输出契约：字段名 → 类型）；`ctx` 里带 `deps/seed/error/ikey/attempt`。五个部件：拓扑执行、guard 原语、幂等键重试、on_error 异常锚点、审计留痕。
>   - 四条不变量（引擎的"宪法"）：I1 无环且引用必已产出（拓扑排不出即拒绝执行）；I2 未选中分支只许"跳过"传播（guard 不满足 → SKIPPED 向下游传染，聚合节点显式声明容忍）；I3 重试必幂等（配置重试却未声明幂等 = 引擎拒绝执行；副作用用幂等键去重）；I4 失败必须可路由（on_error 节点承接 FAILED，异常汇回主链路）。
>   - 代码骨架（miniflow 执行器核心）：
>
> ```python
> def topo_order(nodes: dict) -> list[str]:         # Kahn 拓扑排序
>     indeg = {n: len(d["deps"]) for n, d in nodes.items()}
>     ready, order = [n for n, k in indeg.items() if k == 0], []
>     while ready:
>         n = ready.pop(); order.append(n)
>         for m, d in nodes.items():
>             if n in d["deps"]:
>                 indeg[m] -= 1
>                 if indeg[m] == 0: ready.append(m)
>     if len(order) != len(nodes): raise EngineError("图中存在环：拒绝执行")   # I1 无环
>     return order
>
> def run_flow(nodes: dict, seed: dict) -> tuple[dict, dict]:
>     results, states, errors = {}, {}, {}
>     for name in topo_order(nodes):                # 按依赖序逐节点执行（就绪集可并行化）
>         node = nodes[name]; guard = node.get("guard")
>         if guard and _dig(results, guard[0]) not in guard[1]:
>             states[name] = "SKIPPED"; continue    # I2 守卫不满足 → 跳过并向下传染
>         if any(states.get(d) != "OK" for d in node["deps"]):
>             states[name] = "SKIPPED"; continue    # I2 依赖未成功 → SKIPPED 传播
>         if node.get("retries") and not node.get("idempotent"):
>             raise EngineError(f"{name} 配置重试但未声明幂等")   # I3 重试必幂等
>         payload = json.dumps({d: results.get(d) for d in node["deps"]}, sort_keys=True)
>         ctx = {"deps": {d: results[d] for d in node["deps"]}, "seed": seed, "ikey": sha1(f"{name}|{payload}").hexdigest()[:12]}   # I3 幂等键=节点名+输入指纹
>         try:
>             results[name] = invoke_with_retry(node, ctx)     # 重试 + 输出契约校验
>             states[name] = "OK"
>         except Exception as e:
>             states[name] = "FAILED"; errors[name] = f"{type(e).__name__}: {e}"  # I4 失败可路由
>     return results, states
> ```
>
>   - 关键不变量/边界：① 幂等键 = 节点名 + 依赖输入指纹（同一输入的重试拿到同一个键），副作用函数（如建工单）按键去重——"副作用已发生但响应丢失"的重试不会重复建单；② SKIPPED 是状态不是错误：聚合节点要用 `tolerate_skip` 显式声明"至少一支成功即可"；③ 输出契约在引擎层校验（缺字段/类型错即 ContractError），坏节点不污染下游。
>   - 怎么测：四条不变量各一测——带环图拒绝启动、guard 全不命中时下游 SKIPPED、非幂等节点配重试被引擎拒绝、幂等键重试只建一张工单（miniflow 的 `_FLAKY` 注入"响应丢失"就是第三个场景的复现脚本）。
> - 追问与陷阱：
>   - 追问：guard 分支和 ifelse 节点有什么区别？常见错误：等价论——guard 挂在分支节点上（"本节点只在 route ∈ {退款} 时执行"），不满足标 SKIPPED；ifelse 节点 + 两棵子树需要额外处理"未选分支的输出为空"，guard 的 SKIPPED 传播语义更贴近画布真实行为。
>   - 追问：为什么幂等键用"节点名+输入指纹"而不是随机 UUID？常见错误：每次重试生成新键——重试去重的前提是"同一逻辑操作拿到同一个键"，输入不变键就不变；随机键等于没去重。
>   - 追问：这个 250 行轮子和 LangGraph/n8n 差在哪？常见错误：答"功能少"——差的不是功能是工程面：持久化 checkpoint、HITL（human-in-the-loop，人工介入）挂起恢复、回放与灰度发布；但内核语义（拓扑/guard/幂等/错误路由）是同构的，读懂 miniflow 就读懂引擎的"宪法"。
> - 加分项：能指出拓扑执行天然可并行化——就绪节点（依赖全部就绪）可同时执行，生产引擎的并行度控制与 Q121 的"只读并发"同源；或引 ADP"避免重复建单或重复写入"作为 I3 的产品级出处。
> - 延伸阅读：[workflow-handbook §8 从零搭一个最小工作流编排器（Python 3，已本机验证）](../workflow-handbook/Agent工作流编排手册.md)｜[workflow-handbook §5.3 幂等与重试：重试三要素 + 引擎默认值对照](../workflow-handbook/Agent工作流编排手册.md)｜[workflow-handbook §5.4 错误分支：失败也是画布上的一条路径](../workflow-handbook/Agent工作流编排手册.md)

> **Q127. 手写一个 LLM-as-judge 评测器（含位置偏差消解）。**（难度：高 ｜ 频次：高）
> - 考察点：能否写出 pairwise（两两对比）judge（评审模型）的最小协议实现：温度 0、强制 JSON 输出、证据字段强制、交换重评消位置偏差（position bias）——并用"校准先行"说明 judge 什么时候才有资格上岗（eval-handbook §5，最小示例已本机验证）。
> - 参考回答：
>   - 接口设计要点：评审协议五件套——任务上下文（被测 agent 的职责边界）、rubric 分维度（1-5 档语义锚定，每档给"什么样的回答是 X 分"的描述）、输出 schema（强制 JSON：分数+证据+置信度）、引用式打分、不确定时的出口（低置信输出 `needs_human` 而不是硬给分）。
>   - 交换仲裁规则：AB 与 BA 各评一次，只有两次结论一致才采纳，翻转则判平或升级仲裁——位置偏差被显式吞掉而不是随机二选一；judge 模型与被测模型异构（不同家族）以压自我偏好。
>   - 代码骨架（eval-handbook §5.5 的 judge.py）：
>
> ```python
> JUDGE_PROMPT = """你是评审。比较两个客服 agent 的回答，只按以下维度判优：
> 正确性（不确定要说不知道而非编造）、完整性（覆盖参考要点）、简洁性（同等信息量更短者优）。
> 只输出 JSON：{"winner": "A"|"B"|"tie", "evidence": "引用原文片段"}"""   # schema+证据强制
>
> def llm_compare(a: str, b: str, reference: str) -> dict:
>     resp = client.chat.completions.create(
>         model="judge-model", temperature=0,       # 不变量①：温度 0，judge 必须可复现
>         response_format={"type": "json_object"},  # 不变量②：强制 JSON，分数才可聚合
>         messages=[{"role": "user",
>                    "content": JUDGE_PROMPT + f"\n参考：{reference}\n回答A：{a}\n回答B：{b}"}])
>     return json.loads(resp.choices[0].message.content)
>
> def compare_fair(a: str, b: str, reference: str) -> str:
>     """交换仲裁：AB 与 BA 各评一次，只有两次结论一致才采纳（位置偏差消解）。"""
>     ab = llm_compare(a, b, reference)["winner"]   # 第一遍：A 在前
>     ba = llm_compare(b, a, reference)["winner"]   # 第二遍：交换位置
>     verdict = {"A": "b", "B": "a", "tie": "tie"}[ab]   # 把位置标签翻译回真实答案
>     return verdict if verdict == ba else "tie"    # 翻转 = 位置偏差显现 → 判平并留档升级
> ```
>
>   - 关键不变量/边界：① 温度 0 + 强制 JSON 是 judge 可复现、可聚合的前提；② evidence 字段强制要求——"先摘录再打分"等价于 CoT-before-score，显著压幻觉判分；③ 裁判提示词只能引用评测集的列（query/reference），不能把期望答案复述在提示词正文里，否则判据泄漏会污染所有样本。
>   - 怎么测：手册的验证法——good/bad 两答案跑 `compare_fair` 得 "a"，把两参对调再跑仍是 "a"，交换不翻案即稳健性证据；上岗前抽 50-100 条人工标注算一致率与 κ（>0.6 可用、>0.8 可信），不达标的维度回去改锚定描述而不是硬上线。
> - 追问与陷阱：
>   - 追问：为什么不用 pointwise 打 1-10 分？常见错误：拿均值比较——绝对分数的语义随 prompt 微调漂移、不可复现；要"及格线"用 pointwise 分级（语义锚定），要"谁更好"用 pairwise + 交换仲裁。
>   - 追问：judge 会不会偏袒长答案？常见错误：知道长度偏差却不在 rubric 里处理——显式写"简洁性"维度（同等信息量更短者优），判分前剥离长度信息；手册 stub 的评分函数就是"要点覆盖优先、长度作次键"。
>   - 追问：judge 账单爆炸怎么办？常见错误：全量 judge——金字塔仲裁：规则判据先行（能代码判定就不过 judge）→ judge 只处理开放维度 → 低置信/高分歧才进人审；同模型多票 ×3 成本，异构 judge 一票 + 分歧人审更优。
> - 加分项：能报出第五个更隐蔽的偏差——判据泄漏（judge prompt 无意透露期望答案导致"背答案式打分"），以及"换 judge 模型版本 = 重新校准"的运维纪律；或引 pass^k 与分桶统计作为 judge 之外的可靠性手段。

> **Q128. 手写预算熔断器与语义缓存。**（难度：高 ｜ 频次：低）
> - 考察点：能否实现成本工程的两个守门组件：预算熔断（触顶即停并出部分报告）与语义缓存（semantic cache，语义相近问题命中同一条缓存），并说清两者的正确性边界——熔断的产出语义与缓存的失效策略（eval-handbook §8.3、tuning-handbook §7.2）。
> - 参考回答：
>   - 接口设计要点：熔断器是记账闸（`charge(cost)` 后检查上限），语义缓存的正确性来自"相似度阈值 + 失效策略"双保险；两者都要进 trace（熔断事件、缓存命中率是两类必监控信号）。
>   - 熔断的产出语义是本题题眼：触顶后停止派发新任务、丢弃在途任务，但已完成结果照常出报告——评测/批处理的目标是拿到信息，信息随样本线性增长，"什么都不出"比"出部分报告"浪费得多（eval-handbook §8.3 不变量③）；per-task 超时归因为环境类失败，卡死的任务不允许拖垮整轮。
>   - 代码骨架：
>
> ```python
> class BudgetExceeded(Exception): ...
>
> class BudgetGuard:                                # 预算熔断：触顶即停并出部分报告
>     def __init__(self, budget_usd: float):
>         self.budget, self.spent = budget_usd, 0.0
>     def charge(self, cost: float) -> None:
>         self.spent += cost
>         if self.spent >= self.budget:
>             raise BudgetExceeded(f"已花费 ${self.spent:.2f} ≥ 预算 ${self.budget:.2f}")
>         # 熔断语义：停止派发新任务、丢弃在途任务，但已完成的结果照常出报告
>
> def cos(a: list, b: list) -> float:               # 余弦相似度（向量归一化后即内积）
>     return sum(x * y for x, y in zip(a, b))
>
> class SemanticCache:                              # 语义缓存：相似问题命中同一条目
>     def __init__(self, threshold: float = 0.92):
>         self.store: list[tuple[list, str]] = []   # (问题嵌入, 答案)
>         self.threshold = threshold                # 相似度阈值：防"语义相近答案不同"
>     def lookup(self, q_emb: list) -> str | None:
>         if not self.store:
>             return None
>         key, ans = max(self.store, key=lambda kv: cos(kv[0], q_emb))
>         return ans if cos(key, q_emb) >= self.threshold else None
>     def put(self, q_emb: list, answer: str) -> None:
>         self.store.append((q_emb, answer))        # 生产补：TTL 失效、租户隔离、命中率埋点
> ```
>
>   - 关键不变量/边界：① 语义缓存的第一风险是正确性——"语义相近但答案不同"（改一个日期）必须靠阈值与失效策略兜住，命中要当一类轨迹信号监控；② 缓存分两层说清：提示词缓存（prompt caching，前缀级，命中率是第一杠杆）与语义缓存（条目级，省 60-85% 的公开报道成立但带正确性风险），别混为一谈；③ 命中率异常下跌 = 前缀漂移告警，`cached_tokens` 进 trace。
>   - 怎么测：熔断器用假成本序列断言"触顶后不再派发且返回部分结果"；语义缓存用两对查询断言——同义改写命中、只改日期（答案应不同）因低于阈值不命中；再压一条"阈值过低误命中"的反例。
> - 追问与陷阱：
>   - 追问：前缀缓存怎么设计才稳？常见错误：动态内容（时间戳/随机 ID）写进前缀——稳定前缀工程是"工具定义 → 系统提示词 → few-shot 稳定区，动态内容止步于此"；Anthropic 显式断点最多 4 个放稳定段末尾，OpenAI 用 `prompt_cache_key` 分组路由（同前缀约 15 req/min 有溢出阈值，高并发要打散 key）。
>   - 追问：熔断阈值设多少？常见错误：拍 100%——要留余量：per-task 超时先行、熔断线设在"还能出一半报告"的水平；评测烧穿预算的常见原因恰恰是长任务卡死又无 per-task 超时。
>   - 追问：什么负载适合语义缓存、什么不适合？常见错误：在线客服和评测都上——语义缓存适合高频重复问句的在线负载；离线评测每条样本都要求独立可复现，命中语义缓存反而污染结果（评测要的是"每次都真跑"）。
> - 加分项：能接上真实工程件——tuning-handbook/code/mini_tuning_lab.py 的基线指纹与回归门禁是"成本与质量一起管"的成品参照：门禁不过不固化、基线带指纹、数据变了自动失效；或引批处理 -50% 作为熔断之外的错峰杠杆（离线评测没有理由不用）。
