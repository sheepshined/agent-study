## 题目正文

> **Q001. 什么是 token？为什么大模型按 token 计费与限流？**（难度：初 ｜ 频次：高）
> - 考察点：一句话说清 token 的本质，并解释"为什么按 token 计费/限流"背后的成本结构——这是所有成本工程问题的入口。
> - 参考回答：
>   - token（词元）是分词器（tokenizer）把文本切成的最小单位，模型以 token 为序列单位读入与生成；工程粗估口径是英文约 4 字符/token、中文约 1.6 字符/token（即一个汉字通常 1-2 个 token），不同模型的 tokenizer 压缩率不同，精确值必须用 tokenizer 实算。
>   - 按 token 计费与限流的根因是成本结构：注意力计算与 KV cache 的开销随 token 数增长，token 是最接近真实算力成本的计量单位；限流同理，按 RPM（每分钟请求数）与 TPM（每分钟 token 数）双轴限制。
>   - 输入与输出分开计价，且输出贵 4-10×：当日实抓 Anthropic Sonnet 5 为 $2/$10（5×）、OpenAI gpt-5.2 为 $1.75/$14（8×）——让模型少生成废话是第一省钱方向。
>   - Chat API 是无状态协议：服务端不替你记对话，messages 全量历史每轮重发，所以多轮会话的输入成本是"复利"结构，token 计量直接决定账单形状。
>   - token 计量贯穿所有工程决策：上下文窗口预算、成本核算（四档单价：普通输入/缓存读/输出/缓存写）、缓存命中率，全以 token 为单位。
> - 追问与陷阱：
>   - 追问：一个汉字就是一个 token 吗？常见错误：想当然"一字一 token"——中文压缩率因 tokenizer 与字频而异，常用粗估是 1 token≈1.6 汉字，生僻字可能切出更多 token，预算必须用 tokenizer 实算。
>   - 追问：开流式输出能省钱吗？常见错误："流式更便宜"——流式不改变 token 数与单价，只改善首字延迟与感知体验，账单一分不少。
>   - 追问：max_tokens 设大了会多花钱吗？常见错误："设了就按上限收费"——按实际生成 token 计费，max_tokens 只是截断上限。
> - 加分项：能写出四档成本公式"成本 = Σ(普通输入×价 + 缓存读×价 + 输出×价 + 缓存写部分×价)"，并指出缓存读与未命中价差一个数量级、批处理一律 -50%（四家当日实抓一致）；再补一句行业观察：第三方报道显示行业开始按"每次任务验收通过的实际成本"而非 token 单价评估 LLM 应用。
> - 延伸阅读：[tuning-handbook §6.6 四家模型价格速查（2026-09-28 实抓）](../tuning-handbook/Agent调优手册.md)｜[tuning-handbook §7.1 token 成本核算：四档单价 × 用量](../tuning-handbook/Agent调优手册.md)｜[python-handbook §3.2 openai SDK：messages 全量发送的无状态协议](../python-handbook/Python大模型应用开发手册.md)

> **Q002. temperature、top_p、seed 分别控制什么？生产环境怎么设？**（难度：初 ｜ 频次：高）
> - 考察点：三个采样参数的机制边界，以及"生产怎么设"背后的单变量纪律——区分背参数表与真调过参的候选人。
> - 参考回答：
>   - temperature（温度）控制采样分布的锐化/压平：越低越确定、越高越发散。经验起点：判定、抽取、结构化输出、judge（判分）类任务用 0；客服话术、创作、brainstorm 用 0.3-0.7。
>   - top_p（核采样，nucleus sampling）截断累计概率 p 之外的尾部候选；它与 temperature 都在压随机性，两者不要同时大改——同时动就是两个变量，出问题无法归因，默认值起步即可。
>   - seed（随机种子）提供请求级确定性采样，配合温度 0 做可复现的 A/B 与回归定位；但 OpenAI 侧是 best-effort，服务端负载可能打破完全一致，判据不能依赖单次输出。
>   - temperature=0 ≠ 完全确定性：非确定性还来自服务端批处理与数值精度，同输入仍可能有微差——生产评测要容忍这种量级的抖动。
>   - 生产形态是"参数跟角色走"而不是全局魔法数：OpenCode 把 temperature/topP 做进 agent 定义而非全局配置，内建 build/plan/general/explore 等 7 个 agent 各自配参——抽取型子 agent 用温度 0，总结型 agent 稍放开。
>   - 调参纪律：先按任务类型定档，再在固定评测集上做单变量微调，所有结论以评测分为准。
> - 追问与陷阱：
>   - 追问：temperature 和 top_p 该调哪个？常见错误："两个都调小更稳"——同时调两个随机性旋钮无法归因，默认值起步、有抖动证据再动其中一个。
>   - 追问：温度 0 就能完全复现吗？常见错误："等于确定性"——seed 是 best-effort、服务端有负载扰动，回归判据要按"微差可容忍"设计。
>   - 追问：创作任务温度越高越有创意吗？常见错误："调到 1.5 更发散"——过高会退化为乱码与跑题，创意场景通常 0.7-0.9 封顶并配评测。
> - 加分项：能说出"为什么 temperature=0 不确定"的底层原因（服务端并行 batching 与浮点非结合性），以及结构化输出 + 温度 0 是抽取/判定链路的标准组合；再补 OpenCode 的 per-agent 配参实证（`agent/agent.ts:35-56`）。
> - 延伸阅读：[tuning-handbook §6.1 temperature / top_p / seed](../tuning-handbook/Agent调优手册.md)｜[06-opencode 架构拆解 §8.1：参数做进 agent 定义](../06-opencode/架构拆解.md)

> **Q003. system prompt 与 user prompt 的区别？提示词为什么要分层？**（难度：初 ｜ 频次：中）
> - 考察点：消息角色的权限语义与"分层裁决"思想——能不能从产品与安全视角理解提示词结构，而不是只当文本拼接。
> - 参考回答：
>   - system/developer 消息是厂商与产品的控制通道，定义身份、能力与红线；user 是终端用户输入。层级存在的意义是冲突裁决：当两者矛盾时，规范产品会显式写明谁优先。
>   - 一条 agent 请求的提示词其实有四层：①产品系统提示词（厂商固化、每轮常驻）→②项目指令文件（AGENTS.md/CLAUDE.md，会话开始注入）→③运行时注入块（环境块、system-reminder，按需拼装）→④用户消息。
>   - 分层理由一（权限与裁决）：Codex 提示词明文规定"直接系统/开发者/用户指令优先于 AGENTS.md 指令"，且 AGENTS.md 作用域限定为所在目录整棵子树、深层优先于浅层——把"用户可分层提供指令"本身写进协议。
>   - 分层理由二（缓存经济学）：系统提示词、工具定义常驻且稳定，可进缓存前缀吃折扣价；用户消息每轮变化只能放后缀——分层直接决定账单。
>   - 分层理由三（调优定位）：全局风格写进角色指令层；"检索命中了但不会用"改用户输入模板与依据规则；单节点不稳改该节点提示词——先找准配置位置再动笔，而不是整段重写。
>   - SDK 形状差异是实操考点：OpenAI 把 system 塞进 messages 数组，Anthropic 的 system 是独立参数不进 messages——迁移时最常见的两个踩坑点之一（另一个是 Anthropic 的 content 是块数组）。
> - 追问与陷阱：
>   - 追问：用户说话够强硬能覆盖 system 规则吗？常见错误："可以，模型会听话"——产品的正确防御是层级裁决设计与权限收窄，而不是指望模型自觉排序。
>   - 追问：为什么不把所有规则都塞进 system？常见错误："越全越稳"——常驻内容按每轮请求付账（主干 3-6k token 是当前主流），塞太多既贵又稀释注意力。
>   - 追问：分层和 RAG 是什么关系？常见错误：混为一谈——分层管"谁的话算数"，RAG 管"带什么知识进来"，两者最终都落进提示词但解决不同问题。
> - 加分项：能画出四层结构并指出"工具定义也是提示词的一部分"（名称 + JSON Schema + 描述随请求发送，上下文份额常超系统提示词正文）；以及 system-reminder 这类"注入通道本身也是提示词定义的"精巧设计。
> - 延伸阅读：[prompt-handbook §1.2 一条 agent 请求的解剖：提示词有四层](../prompt-handbook/提示词搭建文档.md)｜[prompt-handbook §5.2 层级与作用域：谁的话算数](../prompt-handbook/提示词搭建文档.md)｜[tuning-handbook §2.1 system prompt 结构](../tuning-handbook/Agent调优手册.md)

> **Q004. 什么是大模型幻觉（hallucination）？RAG 为什么能缓解但不根除？**（难度：初 ｜ 频次：高）
> - 考察点：幻觉的成因机制与 RAG 的能力边界——能否把"知识没命中"与"答得不忠实"两类失败分开治理。
> - 参考回答：
>   - 幻觉（hallucination）指模型生成流畅、自信但无依据或与事实不符的内容。成因有三：训练目标是下一 token 预测（流畅优先于真实）、知识冻结在训练截止日、模型没有可靠的"我不知道"边界。
>   - RAG（检索增强生成，Retrieval-Augmented Generation）的缓解原理：推理前把可能用得上的知识检索出来塞进上下文，把"凭记忆答"变成"看资料答"，并支持逐句溯源引用。
>   - 相比微调与长上下文直塞，RAG 的独特优势是六个维度全绿：私有知识、时效（增量索引即生效）、逐句可引、权限在检索层裁剪、知识更新改索引即生效、成本低（每次只带相关片段）。
>   - 为什么不根除——两个失败面：检索不到时模型照样编（召回失败，F1），检索到了也可能答得不忠实、扩展片段外内容（忠实度失败，F2）；"知识库里存了答案"和"能答对"之间隔着解析、切分、嵌入、检索、重排、权限、生成约束七八个环节，任何一环出错最终回答都会错。
>   - 工程分诊口诀：召回率（recall）与忠实度（faithfulness）是两个指标，别混着治——答案不忠于召回片段就治生成约束（仅依据资料作答+拒答出口），片段根本没召回就治检索（切分/参数/改写）。
>   - 生产缓解组合拳：仅依据资料回答 + 显式拒答出口（"无法确认/建议转人工"，拒答正确也算通过）、引用约束、judge 场景 evidence-before-score（先摘录证据再打分）。
> - 追问与陷阱：
>   - 追问：RAG 检索命中了为什么还幻觉？常见错误："命中=答对"——命中且回答错时先对照答案与片段：扩展了片段外内容是忠实度问题，归到检索头上调参就是在错层使劲。
>   - 追问：微调能把知识训进去从而消除幻觉吗？常见错误："训进权重就不编了"——微调注入知识易过拟合、无法溯源、更新要重训，反而是幻觉治理的退步。
>   - 追问：幻觉怎么量化？常见错误："肉眼看看"——用 RAGAS faithfulness 等指标加坏例集做回归，分清召回率与忠实度两条线。
> - 加分项：能指出幻觉的概率本质——模型对指令与数据没有语法边界，输出是统计最优而非事实校验后的结果；并给出"拒答也是正确"的评测设计（把"无法确认"写进判据）。
> - 延伸阅读：[rag-handbook §1.1 RAG 是什么：与微调/长上下文对比表](../rag-handbook/RAG搭建文档.md)｜[tuning-handbook §3.1 召回率与忠实度分诊](../tuning-handbook/Agent调优手册.md)

> **Q005. 上下文窗口很大，为什么不能把所有资料全塞进去？**（难度：初 ｜ 频次：低）
> - 考察点：对"窗口大小 ≠ 有效容量"的理解——注意力、成本、权限三重约束下"先筛后读"的必然性。
> - 参考回答：
>   - 第一重约束是注意力：context rot（上下文腐烂）——token 越多，每个 token 分到的注意力越薄，模型对"曾经精确记得"的内容开始失准；有效注意力不随窗口线性扩展。
>   - 第二重是位置偏差：lost in the middle（中间遗忘）——关键内容的检索精度对它在窗口中的位置呈 U 形，开头结尾好、中间塌陷；靠"塞得更多"换覆盖率是负收益。
>   - 第三重是成本：窗口大不等于便宜——Gemini 3.1-pro 输入 >200k 后单价从 $2 翻倍到 $4/百万 token（输出 $12→$18），长上下文是翻倍计价；agent 每轮全量重发历史，成本随轮次近二次增长。
>   - 第四重是质量：无关内容是噪声，拉低精度、助长幻觉；长上下文改变的是检索粒度（可以检更大的块），而不是消灭"先筛后读"。
>   - 最硬的理由是权限：长上下文要求先把全部文档塞进 prompt，检索层按身份裁剪（ACL）就没法做了——企业多租户场景这一条就能否决"全塞"方案。
>   - 正解是分层治理：RAG/检索先筛、剪枝（旧工具结果→占位符）→摘要（compact）→新窗口的压缩三层模型、子代理隔离大输出。
> - 追问与陷阱：
>   - 追问：都有 1M 窗口了还需要 RAG 吗？常见错误："窗口大杀死 RAG"——业界主流结论是互补而非替代：1M 窗口改变检索粒度，不消灭筛选与权限裁剪。
>   - 追问：塞满窗口和精挑 10 篇哪个好？常见错误："塞满覆盖率最高"——context rot 与位置偏差下中间部分基本白塞，账单还翻倍。
>   - 追问：什么时候可以长上下文直塞？常见错误：绝对化"永远要 RAG"——文档少且固定、无权限分层、一次性任务时直塞是合理选择，但要接受每轮线性成本。
> - 加分项：能引用工作区证据链——ZCode 三层预算（microcompact 阈值 0.9、auto compact 预留 21k 输出 + 13k buffer、reactive 兜底）与"日志为真源、压缩只改投影"不变量，说明 2026 年头部 agent 全在窗口内做精细经济学。
> - 延伸阅读：[context-handbook §1.1 上下文经济学：注意力是预算](../context-handbook/Context与记忆系统手册.md)｜[tuning-handbook §6.4 上下文窗口与截断策略](../tuning-handbook/Agent调优手册.md)

> **Q006. 大模型 API 的流式输出（streaming）是怎么实现的？SSE 是什么？**（难度：初 ｜ 频次：中）
> - 考察点：从生成机制到传输协议的完整链路——SSE 帧格式、服务端实现要点与常见坑，是否真写过流式服务。
> - 参考回答：
>   - 生成机制决定传输形态：模型自回归逐 token 生成，服务端边生成边推；流式不改变结果与总时长，只改变交付时序——收益是首字延迟（TTFT，time to first token）与感知体验。
>   - SDK 形态：stream=True 返回增量事件迭代器，每个 chunk 携带 delta（增量片段），客户端自己把 delta 拼成全文；服务端不记对话，每次请求仍带全量历史。
>   - SSE（Server-Sent Events，服务器推送事件）是单向 HTTP 长连接，帧格式是硬约定：每帧以 `data: ` 开头、以空行结尾，Content-Type 为 text/event-stream；业界惯例用 `data: [DONE]` 作为自定义结束标记。
>   - 服务端实现（FastAPI + StreamingResponse）：用异步生成器惰性 yield——token 到一批推一批，天然背压；必须用 AsyncOpenAI 等异步客户端，同步客户端会阻塞整个事件循环（服务端第一大坑）。
>   - 生命周期管理：客户端断开时生成器会被取消，内部要做清理（取消即取消上游流）；生产建议换 sse-starlette 的 EventSourceResponse，获得心跳（ping）与标准事件字段。
>   - 与 WebSocket 的取舍：LLM 回复是单向下行，SSE 单向长连接实现简单、天然兼容 HTTP 基建（网关/重试/代理），双向交互需求才需要 WS——"SSE 不够新"不是换 WS 的理由。
>   - 学一次用两处：MCP 的 Streamable HTTP 传输用的也是同族机制，SSE 是 LLM 基础设施层通用技能。
> - 追问与陷阱：
>   - 追问：流式能让生成更快/更省吗？常见错误："流式加速生成"——token 总数与速率不变，账单不变，改善的只是首字延迟与用户感知。
>   - 追问：为什么不用 WebSocket？常见错误："WS 更先进"——单向场景 SSE 更简单可靠，WS 的双向能力在这里是多余复杂度。
>   - 追问：流式中途出错怎么办？常见错误："没设计错误帧"——要在事件流里定义错误事件与前端收尾语义，否则用户看到半截话；重连还需考虑幂等。
> - 加分项：能给出最小 SSE 代码骨架（`yield f"data: {delta}\n\n"`）并解释空行结尾的协议意义；再提一句 Anthropic SDK 的 text_stream 已把事件聚合为纯文本增量——不同 SDK 的流式抽象层级不同。
> - 延伸阅读：[python-handbook §7.2 FastAPI + SSE 流式：LLM 服务的工业标准](../python-handbook/Python大模型应用开发手册.md)｜[python-handbook §3.2 openai SDK：stream=True 增量迭代器](../python-handbook/Python大模型应用开发手册.md)

> **Q007. few-shot 示例怎么选、怎么排序？加多少个合适？**（难度：中 ｜ 频次：高）
> - 考察点：few-shot（少样本示例）的选择/排序/数量决策，以及示例与缓存、评测的交互——最常用杠杆上的实操深度。
> - 参考回答：
>   - 要不要加：输出格式、判断标准、语气这类"不容易用规则说清楚"的东西，1-3 个高质量示例通常胜过继续堆规则——"示例胜过规则"是 Anthropic 官方技法的第二条。
>   - 选哪些：一个标准样例 + 一个边界样例 + 一个缺失信息样例——让模型既会正常处理，也知道高风险输入怎么兜底；只给标准样例的典型后果是模型不会拒答。
>   - 放哪里：关键示例放开头或结尾——lost in the middle 位置偏差决定了中间位置利用率最低；Claude Code 的生产提示词把最关键约束在开头和结尾各写一遍，就是这个原理的应用。
>   - 加多少：长上下文模型可以放大示例数（many-shot，many-shot learning，多示例提示），增益与示例数近似对数关系——但 token 成本与"过度模仿样例"的风险同步上升，不是越多越好。
>   - 缓存交互常被忽略：按相似度动态取的示例会打断缓存前缀——正确做法是稳定示例放前缀、动态部分放后缀，示例块放进系统提示词稳定区还能吃缓存折扣。
>   - 写正例不写反例：Claude Code 的 7 个语气示例全是正例，没有一个"不要这样"——给"该长什么样"比给"不该长什么样"有效；对反直觉规则补一句 why，遵循度更高。
>   - 示例也是提示词的一部分：换示例=改提示词，必须过同一评测集回归，而不是拍脑袋换。
> - 追问与陷阱：
>   - 追问：示例越多效果越好吗？常见错误："堆 20 个总比 3 个强"——占上下文、推高每轮成本、引发过度模仿，增益对数递减。
>   - 追问：示例和规则矛盾时听谁的？常见错误："规则优先"——示例往往是最强的隐式引导，出现矛盾要修示例而不是只改规则文本。
>   - 追问：检索式动态 few-shot 怎么落地？常见错误：只讲"按相似度取 top-k"不讲缓存代价——动态内容必须放前缀之后，否则命中率全灭。
> - 加分项：能同时引用两篇实证锚点——lost in the middle（Liu et al. 2023，arXiv:2307.03172）与 many-shot（Agarwal et al. 2024，arXiv:2404.11018），并落到"示例块放系统提示词稳定区吃缓存"的工程合流点。

> **Q008. 思维链（CoT）与 ReAct 的区别？什么时候加 CoT 反而有害？**（难度：中 ｜ 频次：高）
> - 考察点：两大范式的机理与边界，特别是 2026 年的实证分水岭——"推理模型不需要外部 CoT 触发词"。
> - 参考回答：
>   - CoT（Chain-of-Thought，思维链）让模型先推理再作答：零样本触发词"让我们一步一步思考"在快思考模型的推理类任务上有可复现提升（Kojima et al. 2022 的原始实证）。
>   - ReAct 是 Reason + Act 交替——"边想边调工具"的范式（Yao et al. 2022），是 agent 主循环的来源；工作区六家 agent 的主循环几乎全是 ReAct 变体，这是它工程地位的直接证据。
>   - 何时有害：对推理模型（reasoning model，自带内部推理预算的模型）堆外部 CoT 触发词，边际收益消失甚至为负——OpenAI 提示词指南明确建议不要对推理模型堆 "step by step" 类提示，Anthropic 对 extended thinking 的建议同向。
>   - 档位化证据：DeepSeek 现役两档模型均提供 thinking / non-thinking 双模式开关——"要不要 CoT"已经从提示词层下沉到了模型档位层，触发词调优空间被模型档位吃掉大半。
>   - 成本账：推理 token 计入输出计费（OpenAI 口径），而输出比输入贵 4-10×——长思维链直接放大账单里最贵的档位，这是"CoT 有害"的经济学面。
>   - 最确定的正面用例是 judge（判分）场景：evidence-before-score（先摘录证据再打分）等价于 CoT-before-score，能显著压幻觉判分——这是触发词在 2026 年最稳的正面地位。
>   - 实证纪律：触发词有没有用不要抄结论，在自己的评测集上跑 A/B（单变量、温度 0）；真正稳定提升的从来不是"加一句思考"，而是补齐依据、边界与输出约束。
> - 追问与陷阱：
>   - 追问：给推理模型加"一步步思考"会怎样？常见错误："总有帮助"——可能与内部推理机制冲突并徒增输出 token，官方建议是少手工 CoT、把约束写清楚让模型自己规划。
>   - 追问：CoT 输出的推理过程可信吗？常见错误："推理链=真实因果"——可能是事后合理化，关键决策要靠工具校验与评测而不是读推理链。
>   - 追问：ReAct 自主循环和固定工作流怎么选？常见错误："都用 ReAct 更灵活"——路径固定的任务用显式工作流更便宜更稳，转交条件明确时用确定性分支，模型只处理开放路由。
> - 加分项：能指出 ReAct 与 SDK 工具调用两段式（模型返回 tool_calls、执行在应用侧）的对应关系，并用 20 行自研循环复现六家 agent 的内核形状——这是把论文概念落到源码层的信号。

> **Q009. 让模型稳定输出 JSON 有哪些方案？可靠性怎么排？**（难度：中 ｜ 频次：高）
> - 考察点：结构化输出（structured output）的方案谱系与优先级排序——格式漂移（F4）的根治思路。
> - 参考回答：
>   - 方案①（最可靠）：API 级结构化输出——JSON Schema 约束解码，各家 API 均支持；约束在解码层，模型物理上很难输出不合法结构，比提示词约束可靠一个量级，是首选。
>   - SDK 落地形态：OpenAI 用 `parse` + pydantic 模型自动转 Schema、拿到即合法实例；Gemini 的 response_schema 直接收 pydantic 类型（连 list[模型] 都行）；Anthropic 用工具强约束（forced tool choice）实现同类效果。
>   - 方案②：schema 校验 + 定向重试——校验失败把错误信息回喂重试（一次为限），重试两次仍失败进人工/兜底分支；重试不是无限的，要有熔断。
>   - 方案③（下策但有水位）：固定字段模板 + 禁解释（"仅输出 JSON，字段如下"），配合 few-shot 与缺失值规则（"无法判断时 intent 输出其他、need_human 输出 true"）也能到生产水位——没有 schema 支持时的退路。
>   - 方案④（互补而非替代）：确定性逻辑出提示词——时间戳、编号、金额计算、格式校验永远不要让模型"生成"，让工具/代码节点返回；模型只做该模型做的事。
>   - 常见失败模式要能报菜名：输出被 markdown 代码围栏包裹、JSON 中途被 max_tokens 截断、字段名漂移、夹带解释文字——前两者靠解码层与长度预算解决，后两者靠 schema 与 few-shot。
>   - 标准组合：判定/抽取场景 temperature=0 + 结构化输出 + 显式缺失值规则；schema 设计本身是工程——字段越少越稳、枚举优于自由文本。
> - 追问与陷阱：
>   - 追问：有了约束解码还要校验吗？常见错误："API 保证合法就不用校验"——合法 ≠ 正确（值错了 schema 也会过），业务断言与缺失值检查必须保留。
>   - 追问：提示词里写"请输出 JSON"行不行？常见错误："加一句就稳了"——提示词约束是统计性的，格式漂移是高频失败类型，根治在解码层。
>   - 追问：解析失败怎么兜底？常见错误："无限重试"——回喂错误重试一次为限，仍失败走降级分支并打点，静默重试循环是账单与延迟杀手。
> - 加分项：能对比四家 SDK 的结构化输出抽象差异（OpenAI parse / Gemini response_schema / Anthropic forced tool choice / litellm 部分透传），并指出"输出更短"是结构化输出的隐藏收益（输出 token 比输入贵 4-10×）。

> **Q010. prompt caching（提示缓存）的原理与定价？怎么设计稳定前缀？**（难度：中 ｜ 频次：高）
> - 考察点：提示缓存的机制、四家定价差异与稳定前缀工程——agent 成本工程的第一杠杆，最能拉开候选人档次。
> - 参考回答：
>   - 原理：对请求前缀做精确匹配缓存，命中部分按缓存读价计费并省去重复预计算，同时大降首字延迟——Anthropic 缓存作用域为同一组织，OpenAI 为前缀 + key 维度。
>   - 定价（2026-09-28 实抓）：Anthropic 缓存写 1.25×（5 分钟 TTL）/ 2×（1 小时 TTL）、读 0.1×（Opus 5.5 读价为输入的 5%，Sonnet/Haiku 为 10%）；OpenAI 自动缓存读为 10% 价（gpt-5.x 系）；DeepSeek 最激进——缓存命中输入 $0.006 vs 未命中 $0.30（约 2%）；缓存读普遍只占原价 2-25%。
>   - 触发方式差异：Anthropic 是显式的——在消息/工具上加 cache_control 断点（最多 4 个，位置向后生效）；OpenAI 是自动的——提示 ≥1024 token 即尝试前缀缓存，无需配置。
>   - 延迟收益：OpenAI 实测缓存命中延迟最高降约 80%；Anthropic 官方示例约 2× 提速量级。
>   - 稳定前缀设计的标准序：工具定义 → 系统提示词 → few-shot 稳定区 →（动态内容止步于此）；时间戳、随机 ID、每轮变化的检索结果一旦混进前缀，从该字节起缓存全灭——最常见的元凶就是拼接了当前时间或流水号。
>   - agent 场景的复利结构：每轮全量重发（历史 + 系统提示词 + 工具定义），输入 token 随轮次滚动增长，命中率对账单的影响是非线性的——所以命中率是第一成本指标。
>   - 命中率要进可观测：usage 里的 cache_read_input_tokens（Anthropic）/ prompt_tokens_details.cached_tokens（OpenAI）要进 trace 与成本报表；命中率趋零 = 有东西在前缀里漂，要做成告警。
>   - 平台细节两则：OpenAI 的 prompt_cache_key 可按租户/会话分组路由，但同前缀流量约 15 req/min 会溢出到其他缓存机器（高并发时打散到多个 key 反而可能提高总命中率）；Anthropic 的 1 小时 TTL 适合低频长会话（写费翻倍换跨轮存活）。
>   - 工作区实证：ZCode 把缓存做成显式契约——system prompt 每段带 cacheHint:"stable"，cache-control 在 provider 可见投影之后统一设置；OpenClaw 把"prompt 前缀复用"称为成本/延迟生命线。
> - 追问与陷阱：
>   - 追问：缓存写比原价还贵（1.25×），值得吗？常见错误："写费是亏的"——写费是一次性投资，后续每轮读都是 0.1×，多轮会话两轮即回本。
>   - 追问：对话里有时间戳缓存还有效吗？常见错误："缓存会自动跳过变化部分"——前缀精确匹配没有任何模糊性，常变内容必须挤到提示词尾部。
>   - 追问：语义缓存（semantic cache）能不能上？常见错误："省 60-85% 何乐不为"——"语义相近 ≠ 答案相同"的正确性风险需要相似度阈值 + 失效策略，只能作第二层，且先吃满前缀缓存。
> - 加分项：能推导"缓存命中价与未命中价差一个数量级，所以命中率是最值得盯的成本指标"，并给出截断保缓存的设计约束——从后往前剪（保护最近消息），不破坏最前面的稳定前缀。
> - 延伸阅读：[tuning-handbook §2.4 提示缓存：成本与延迟的第一杠杆](../tuning-handbook/Agent调优手册.md)｜[tuning-handbook §7.2 缓存命中率：第一杠杆](../tuning-handbook/Agent调优手册.md)｜[context-handbook §2.6 缓存锚点](../context-handbook/Context与记忆系统手册.md)

> **Q011. 中文场景的 token 计量与成本估算有什么坑？**（难度：中 ｜ 频次：中）
> - 考察点：CJK（中日韩字符）场景特有的计量失真与三处漏账——做过中文生产系统的人才会踩过的坑。
> - 参考回答：
>   - 核心坑：中文的 token 压缩率与英文不同且因 tokenizer 而异——工程粗估口径是英文约 4 字符/token、中文约 1.6 字符/token，一个汉字通常 1-2 个 token；用英文口径估中文预算必然失真。
>   - 真实事故模式（工作区源码实证）：OpenCode 的压缩预算用"字符数/4"估算，对中文显著低估——预算内实际已逼近超窗；且 provider 没回报 usage 时按 0 处理，成本被系统性低估。
>   - 反面对照：OpenClaw 显式把 CJK 计入压缩估算；工作区最小实现按语种分除数（中文 1.6、英文 4 字符/token）——单一除数是 CJK 场景的已验证反例。
>   - 正解：CJK 场景必须用 tokenizer 实算（官方 count_tokens 接口/tiktoken），"字符/4"只配做粗预算；本地估算只做预算预警，对账以 provider 回报的 usage 为准，偏差超阈值告警。
>   - 成本估算要按四档单价：成本 = Σ(普通输入×价 + 缓存读×价 + 输出×价 + 缓存写×价)——中文会话常被漏算的是缓存档与输出档，以及"历史全量重发"的复利结构。
>   - 中文特有的放大器：同一段中文系统提示词每轮全量重发，中文 token 密度高意味着常驻成本比英文直觉更高——稳定前缀 + 缓存命中在中文场景更关键，而不是更不重要。
>   - 行业口径变化（加分观点）：第三方报道（虎嗅 2026-05）显示行业开始按"每次任务验收通过的实际成本"而非 token 单价评估应用——成本估算的终点是单位任务成本，不是单价乘字符。
> - 追问与陷阱：
>   - 追问：一个汉字就是一个 token 吗？常见错误："等价"——高频汉字常 1 token、生僻字与繁体可能切出更多，中文 token 数必须按 tokenizer 实算。
>   - 追问：为什么我的成本估算总偏低？常见错误："价格表看错了"——通常是三处漏账：缓存读档没单列、输出档没估、"每轮全量重发历史"的滚雪球没建模。
>   - 追问：中文 prompt 换成英文写更省吗？常见错误："省 token 就是省钱"——英文通常更省 token，但可能牺牲任务遵循度与本地化质量；该省的是缓存与输出结构，不是语言本身。
> - 加分项：能引用 OpenCode `packages/core/src/util/token.ts:4`（字符/4）与 `session/session.ts:341-345`（usage 缺失按 0 处理）两个源码级证据，说明"估算失真"不是理论风险而是已发生的事故模式。

> **Q012. 推理模型（reasoning model）与快思考模型怎么分工？价差多大？**（难度：中 ｜ 频次：中）
> - 考察点：三档模型分工表、真实价差量级与路由纪律——会不会按任务配模型而不是无脑旗舰。
> - 参考回答：
>   - 三档分工（2026-09-28 实抓阵容）：推理/旗舰档（Anthropic Opus 5.5、OpenAI gpt-5.2-pro、Gemini 3.1-pro、DeepSeek v4-pro thinking）做规划、策略判断、复杂推理、判卷（judge）、难题兜底；快思考/均衡档（Sonnet 5、gpt-5.1/5、gemini-3.8-flash）做主力生成与常规 agent 主循环；轻量档（Haiku 4.5、gpt-5-mini/nano、flash-lite）做意图分类、字段抽取、查询改写、标题这类短任务。
>   - 价差量级：7-35×。具体对：Haiku 4.5 $1/$5 vs Opus 5.5 $4/$20（4×）；gpt-5-nano $0.05/$0.40 vs gpt-5.2 $1.75/$14（35×）；Sonnet 5 $2/$10 vs Fable 5.1 $10/$50（5×）——路由错误的代价是真金白银。
>   - 推理模型的隐性成本：推理 token 计入输出计费（OpenAI 口径），输出又是输入的 4-10×——长思考链放大的是账单里最贵的档位，评估推理模型必须看"含思考的总输出 token"。
>   - 反向浪费同样致命：用推理/旗舰模型做分类、抽取、改写是算力浪费；用轻量模型做多步规划则错误率被放大——分工表就是路由表，两张方向都要防。
>   - 级联（cascade）与降级：先小后大——小模型置信度不足或失败再升级旗舰；每级之间要有明确的升级判据（置信度阈值、判据输出），不是"感觉不行"。
>   - 路由纪律：路由器自己也要过评测集——路由错了等于把错误率做进架构；每档模型的 pass 率与成本要并排监控。
>   - 配套工程：模型信息当配置管，不当代码管——OpenCode 把模型清单（含 cost/limit/status 字段）外置到 models.dev 并 TTL 缓存，换模型从"发版"变"改配置"。
> - 追问与陷阱：
>   - 追问：直接全用最强模型不行吗？常见错误："质量优先无脑上旗舰"——7-35× 价差下账单不可持续，且大量任务轻量档足够；正确姿势是路由 + 评测 + 成本并排监控。
>   - 追问：能不能用提示词限制推理模型的思考长度来省钱？常见错误："压思考预算免费"——预算过低直接牺牲正确性，该做的是把任务路由到合适档位，而不是阉割旗舰。
>   - 追问：thinking/non-thinking 开关怎么用？常见错误："全局固定一档"——按任务难度切档：难任务开 thinking、简单任务直出，DeepSeek 双模式开关就是这个设计的落地。
> - 加分项：能补延迟维度的取舍——Anthropic Opus 5.5 Fast 档 2× 价格换至多 2.5× 提速（当日实抓），交互链路的兜底手段；以及"成本-质量-延迟三角的正确用法是显式选择放弃哪个"。

> **Q013. 微调（fine-tuning）、提示工程、RAG 分别适合什么场景？怎么选？**（难度：中 ｜ 频次：低）
> - 考察点：三条技术路线的生态位与决策顺序——能不能按问题类型选层，而不是"上来就微调"。
> - 参考回答：
>   - 三者改的东西不同：提示工程改"指令"，RAG 改"依据"（推理前检索进上下文），微调改"权重"（把模式训进模型）——选型的第一问是问题出在哪一层。
>   - RAG 的六维优势（对比微调与长上下文直塞）：私有知识、时效（增量索引改了即生效）、逐句溯源可引、权限在检索层裁剪、知识更新不重训、成本低（每次只带相关片段）——企业知识场景的默认答案。
>   - 微调的适用面窄得多：风格/格式固化、领域语言对齐、任务窄且稳定、有大量高质量标注数据的场景——不适合知识注入（易过拟合、无法溯源、更新要重训、成本高）。
>   - 提示工程是第一手段且最便宜（迭代分钟级），但要认清边界：知识没命中时单纯加长 prompt 治不了根因——先分诊是"没听懂任务"还是"没拿到依据"。
>   - 决策顺序惯例：先提示工程 → 不足补 RAG（知识/时效/溯源问题）→ 有稳定标注数据且问题是格式/风格/窄任务时才考虑微调；few-shot + 提示缓存通常是微调的廉价替代。
>   - 判断口诀：定行为 → 提示词；教流程 → Skill；连系统 → MCP；带知识 → RAG；跨会话 → 记忆——后四者最终都落进提示词，管理的是"何时、以多大代价放什么进上下文"。
>   - 生产常态是组合而非互斥：RAG 供知识 + 提示工程定行为与格式 + 必要时微调固化风格或小模型分类器（成本套利）。
> - 追问与陷阱：
>   - 追问：知识更新频繁选哪个？常见错误："微调一劳永逸"——重训周期跟不上增量更新，RAG 改索引即生效。
>   - 追问：微调能替代 RAG 省检索成本吗？常见错误："训进去就不用检索了"——丢掉溯源与权限裁剪两大能力，知识时效变差，幻觉更难治理。
>   - 追问：什么时候微调真的值得？常见错误：说不出判据——大量标注可得、任务窄且稳定、小模型微调能替代大模型提示（如轻量档做分类）时，成本套利成立。
> - 加分项：能引用 MIT NANDA 报告"95% 企业 GenAI 项目无可入账价值"——选型的第一问不是技术路线而是有没有验收标准；路线之争在评测集面前才有意义。
> - 延伸阅读：[rag-handbook §1.1 三条路线六维对比表](../rag-handbook/RAG搭建文档.md)｜[prompt-handbook §1.3 与 Skill/MCP/RAG/记忆的边界](../prompt-handbook/提示词搭建文档.md)｜[eval-handbook §1.3 评测是落地的第一问](../eval-handbook/Agent评测与质量工程手册.md)

> **Q014. 多模态输入（图片）是怎么计价的？**（难度：中 ｜ 频次：低）
> - 考察点：多模态计价机制的定性理解——图片如何折算 token、价格由什么决定、成本杠杆在哪。
> - 参考回答：
>   - 机制：图片在输入侧被转换成 token（视觉编码后与文本同窗），与文本一起按输入 token 计费；模型回复的文本仍按输出 token 计——图片本身只产生输入侧成本，不产生"输出图片"的费用。
>   - 折算规则没有全行业标准：有的按分辨率/尺寸映射为固定 token 数，有的按 tile（瓦片切片）数量累加——同一张图在不同平台的折算可能差数倍，报价前必须查当日官方定价页，不能凭"一张图 X 元"的印象账。
>   - 量级感：一张普通分辨率图片折算的 token 通常远多于同版面文字，多图与高分辨率请求是 token 大户——多模态应用成本失控的头号来源。
>   - 输入侧机制同样适用：批处理 -50%（四家当日实抓一致）、提示缓存对含图的稳定前缀按平台规则生效——离线多模态批任务（打标、审核）应走 batch，在线高频同图请求应进缓存前缀。
>   - 工程杠杆按性价比排：按需降分辨率（理解类任务多数不需要原始分辨率）→ 控制图片数量（裁剪/筛选后再传）→ 同一张图进稳定前缀吃缓存 → 离线负载走批处理。
>   - 与架构的交互：多模态 RAG 里检索回来的图片同样占输入预算——要给图片设预算上限与降级策略（超预算降分辨率或转文本描述）。
> - 追问与陷阱：
>   - 追问：图片为什么比文字贵？常见错误："一张图就几十个 token"——视觉 token 数与分辨率挂钩，通常远超一行文字，且各平台折算规则不同。
>   - 追问：发高清图和压缩图效果差很多吗？常见错误："分辨率越高越好"——对多数理解类任务质量差异有限而成本差异巨大，先在评测集上验证降分辨率的质量损失再定档。
>   - 追问：视频输入怎么算？常见错误："按视频时长计费"——主流做法是抽帧折算成多图计费，预算按"帧数 × 每帧折算 token"估。
> - 加分项：能把多模态计价接回四档模型——图片属于"普通输入"或"缓存读"档（进稳定前缀后），因此缓存命中率工程对多模态 agent 同样是第一杠杆。
> - 延伸阅读：[tuning-handbook §6.6 四家价格速查（计价口径基准）](../tuning-handbook/Agent调优手册.md)｜[python-handbook §3.4 google-genai SDK：多模态客户端形态](../python-handbook/Python大模型应用开发手册.md)

> **Q015. 调用大模型 API 的超时、重试与幂等怎么设计？**（难度：中 ｜ 频次：低）
> - 考察点：错误分型、重试纪律与幂等设计——LLM 调用是"会失败的外部依赖"，考生产可靠性基本功。
> - 参考回答：
>   - 错误分型决定策略：可重试错误是超时、429 限流、5xx；不可重试是 4xx 业务错误（参数错、鉴权失败、内容策略拒绝）——对 4xx 重试只会放大失败并烧钱。
>   - 重试三件套：次数上限 + 指数退避（带抖动，429 按 Retry-After 头等待）+ 幂等键；聚合网关（如 litellm）内建限流重试与负载均衡可复用，但应用层仍要有兜底——SDK 只管 HTTP 层。
>   - per-task 超时：每个任务独立 deadline，超时判失败并归因；反模式是全局唯一超时——一条卡死拖垮整链。
>   - 幂等是重试的前提：写操作（建单、发消息、扣款）重试必须带幂等键，否则"重试"就变成"重复副作用"——运维红线是"重试要设置次数、间隔和幂等约束"。
>   - 预算熔断：整轮 token/费用设上限，触顶即停并出部分报告；工作区先例是 ZCode 的连续失败 3 次熔断与 rapid-refill 断路器（防"压缩-回填-再压缩"的烧钱循环）——无预算上限的长循环是"账单爆炸"事故的直接来源。
>   - 降级链要显式：检索失败 → 通用回答；工具超时 → 缓存/默认值；模型超时 → 小模型；全部失败 → 转人工；每级降级要有自己的判据与日志——"悄悄降级"是最难排查的静默失败。
>   - 流式链路的特殊性：超时要分两段看（TTFT 首字超时与总时长超时）；客户端断开要取消上游流并清理，避免半死连接继续烧 token。
> - 追问与陷阱：
>   - 追问：重试会不会造成重复扣款/重复建单？常见错误："重试是 SDK 的事"——SDK 只重试 HTTP 层，业务幂等键必须应用层设计，两端都要管。
>   - 追问：超时设多长合适？常见错误："越长越稳"——过长占住资源并放大尾延迟；应按 P95 延迟预算反推（如交互 P95 ≤ 8s 拆成 TTFT、生成速率、工具往返三笔账再分配）。
>   - 追问：429 立刻重试行吗？常见错误："马上重试抢额度"——必须按 Retry-After 指数退避，立刻重试等于加剧限流并可能被封。
> - 加分项：能把"投机执行"讲清楚——无依赖只读调用可预取并行，有副作用的调用禁止投机必须串行 + 幂等；以及延迟预算分解法（先测各分量再选杠杆，平均错方是最常见的浪费）。
> - 延伸阅读：[tuning-handbook §4.5 重试与超时预算](../tuning-handbook/Agent调优手册.md)｜[tuning-handbook §4.4 路由与降级](../tuning-handbook/Agent调优手册.md)｜[python-handbook §3.5 litellm：聚合层的重试与负载均衡](../python-handbook/Python大模型应用开发手册.md)

> **Q016. embedding（嵌入）调用和生成式调用有什么区别？**（难度：中 ｜ 频次：低）
> - 考察点：嵌入模型与生成式模型在输出形态、计费、工程纪律上的系统差异——RAG 工程的基础认知。
> - 参考回答：
>   - 本质区别：embedding 模型把文本映射为定长向量（语义相似度空间中的一个坐标），不生成内容；生成式模型输出 token 序列。前者算"相似度"，后者产"内容"。
>   - 计费与参数差异：embedding 按输入 token 计价、无输出档、无采样参数（temperature 对它没有意义）、无对话语义（不需要 messages 历史）——调用形态是"一批文本进、一批向量出"。
>   - 工程不变量一：向量统一归一化后"内积 == 余弦相似度"（sentence-transformers 的 normalize_embeddings=True）；本地方案（bge 系列）与 API 方案都可行，中文选型看 C-MTEB 榜单、英文看 MTEB。
>   - 工程不变量二：换嵌入模型 = 换向量空间，新旧向量不可混存——升级必须全库重建索引并过回归集，排行榜分数只决定候选，自己的测试集决定上线。
>   - 能力盲区：嵌入对精确词（错误码、型号、人名）是弱项——生产标配是稠密向量 + BM25 稀疏双索引，RRF（倒数排名融合）合并后交叉编码器重排取 top-N，这是性价比最高的一步。
>   - 失败模式不同：生成式怕幻觉，嵌入怕"检索退化"（大规模下召回下滑）与语义偏移（分数高但实际不相关）——质量指标是 Recall@k，不是忠实度。
>   - 与记忆的边界：embedding 是"检索"不是"记忆"——它没有写入、遗忘、冲突消解的语义，跨会话记忆要靠记忆系统管理，向量库只是其中一条召回通道。
> - 追问与陷阱：
>   - 追问：embedding 会有幻觉吗？常见错误："向量模型不会错"——它不编造内容但会语义偏移，相似度高分不等于真的相关，必须用 Recall@k 评检索质量。
>   - 追问：换 embedding 模型必须重建索引吗？常见错误："维度一样就能混用"——不同模型的向量空间不可比，混存等于检索报废；灰度期要用双索引过渡。
>   - 追问：embedding 调用需要重试与缓存吗？常见错误："嵌入很便宜不用管"——确定性调用适合结果缓存（同一文本同一向量），但批量重建索引时要控并发与限流。
> - 加分项：能给出两阶段检索的标准参数直觉——每路召回 recall_k≈50、RRF 融合、交叉编码器重排取 top-5；并指出 reranker 只重排前 K，成本远低于全量嵌入。
> - 延伸阅读：[python-handbook §5.1 嵌入：sentence-transformers](../python-handbook/Python大模型应用开发手册.md)｜[rag-handbook §2.4 嵌入与索引规范](../rag-handbook/RAG搭建文档.md)

> **Q017. 提示词注入（prompt injection）为什么"上检测器当边界"是反模式？正确防御是什么？**（难度：高 ｜ 频次：高）
> - 考察点：注入防御的架构观——能否说清"检测器只是遥测不是边界"，并给出分层防御与 lethal trifecta 判据。
> - 参考回答：
>   - 先说根因：经典安全靠"代码/数据"边界（SQL 参数化、输出编码）重建防线，LLM 应用里指令与数据没有语法边界——两者同为 token，模型用统计方式区分，注入无法像 SQL 注入那样用"转义"根除。
>   - 反模式的两个死因：①攻击可对抗性改写（base64、隐喻、多语言、分隔符变换）绕过分类器；②误杀率（把正常业务文本当注入）直接杀死产品可用性——检测器在论文与评测中恰好是表现最差的一层。
>   - 生产系统的立场（OpenClaw memory-architecture.md 原话）："内容级扫描挡不住投毒，所以在写入处强制 provenance、用结构化门槛代替事后检测"——检测器的正确角色是遥测信号：报警 → 降级运行（如暂收回网络权限）→ 人工复核，而不是"检测通过 = 放行"。
>   - 正确防御是四层结构：①指令隔离（数据包上下"围栏"、关键安全指令就近重述——压缩时也要逐字保留）；②数据来源标记（spotlighting，Microsoft 方案——provenance 必须是结构化字段而不是文本内自称）；③双 LLM 模式（Simon Willison）与 CaMeL（Google DeepMind：特权 LLM 只处理查询与工具调用、永不看不可信内容；隔离 LLM 只消化不可信内容、永不持有工具——结构性阻断"注入→动作"）；④最小权限 + 出口控制——唯一不依赖模型行为的层。
>   - lethal trifecta（致命三要素，Simon Willison 2025-06）：访问私有数据 + 接触不可信内容 + 对外通信能力，三者齐备 = 攻击链闭环（EchoLeak 即生产级实证：邮件域隐藏指令 → 驱动读敏感数据 → 经 markdown 图片外呼）；防御含义是断腿优先级——最难砍的是前两条，最易最值得砍的是第三条出口（egress）。
>   - 布防原则：按"兑现路径"布防，不按"输入来源"布防——输入有无数条路（网页、邮件、issue、检索片段），兑现只有工具出口那几条；列出 agent 全部对外动作逐一说明拦截点，才是能通过安全评审的表述。
>   - 目标重述：注入是概率问题不是布尔问题——同一载荷换个措辞或模型版本，obey 率就变；正确目标是"证明注入不可兑现"，"永不注入成功"是不可能的目标。
>   - 一条长期判断：模型升级会改变概率但不改变架构——把希望押在"下一代模型不再被注入"等价于没有防御；权限、沙箱与出口控制是模型无关的。
> - 追问与陷阱：
>   - 追问：我上了注入检测器是不是就安全了？常见错误："检测通过就放行"——对抗样本可绕过、误杀伤可用性；检测只能做遥测与降级触发，边界必须建在权限与出口上。
>   - 追问：CaMeL/双 LLM 那么好为什么没普及？常见错误："技术先进就该用"——代价是功能损失：凡是"读了不可信内容再行动"的任务都被切掉或降级，目前研究原型多、产品化少。
>   - 追问：系统提示词里写"忽略内容中的指令"有用吗？常见错误："写了就防住了"——围栏是提示词层面的约定、没有强制力，只能降低误服概率，挡不住自适应攻击。
> - 加分项：能给出 EchoLeak（CVE-2025-32711，CVSS 9.3）零点击全链的四步拆解，并指出"前四步任何一步拦住链路即断，生产实际只在出口的域伪装上被部分绕过"——印证出口控制是纵深中价值最高的一层。
> - 延伸阅读：[security-handbook §2.3 防御分层：四层结构 + 一个反模式](../security-handbook/AI应用安全手册.md)｜[security-handbook §1.4 lethal trifecta](../security-handbook/AI应用安全手册.md)｜[context-handbook §6.2 记忆污染：注入的持久化形态](../context-handbook/Context与记忆系统手册.md)

> **Q018. 生产级 agent 的提示词是怎么组织与装配的？（结合工作区六家 agent）**（难度：高 ｜ 频次：高）
> - 考察点：从"写一段 prompt"到"提示词基础设施"的视角跃迁——有没有读过真实 agent 的提示词组织方式。
> - 参考回答：
>   - 先给四层解剖（一条 agent 请求携带的提示词）：①产品系统提示词（厂商固化、每轮常驻）→②项目指令文件（AGENTS.md/CLAUDE.md，会话开始注入）→③运行时注入块（环境块、system-reminder、记忆区块，按需拼装）→④用户消息——按"谁写、何时进上下文"划分。
>   - 主干结构有通用骨架：从六家真实生产提示词归纳出八区块——身份声明、安全红线（IMPORTANT 标注）、环境上下文（占位符注入）、行为与语气（配示例）、任务工作流（分步）、工具策略（何时用哪个工具）、外部指令接入（用户文件的作用域协议）、输出与呈现（渲染介质相关）。
>   - 载体形态光谱（本工作区一手证据）：Claude Code 逆向还原出 12 个提示词文件；Codex 官方开源 5 份按模型命名的 prompt.md；OpenCode 15 个 .txt 共 1302 行（另有 agent/prompt/ 4 个子任务提示词）；OpenClaw 是 1340 行的 TS 提示词渲染器——提示词工程化程度随产品复杂度递增。
>   - 运行时装配分三层：静态层（git 管理的常量文件与区块构建函数）→模板层（占位符：$cwd/$OS/$date 运行时填值）→动态层（每轮计算的环境信息、git 状态、记忆区块、system-reminder）→渲染器拼成最终 system message。
>   - 层级裁决是显式协议不是默认行为：Codex 明文"直接系统/开发者/用户指令优先于 AGENTS.md"，AGENTS.md 作用域 = 所在目录整棵子树、深层优先；system-reminder 被约定"不是用户输入"——注入通道本身也是提示词定义的。
>   - 缓存边界是第一等工程约束：OpenClaw 用 SYSTEM_PROMPT_CACHE_BOUNDARY 与 RELOCATABLE_BOUNDARY 两个常量把提示词切成"稳定前缀 + 可移动后段"，常变区块（时间、git 状态）必须放边界之后，否则每轮击穿缓存；ZCode 则给每段标 cacheHint:"stable"。
>   - 别忘了工具定义：每件工具的名称、JSON Schema 与描述都随请求发送，上下文份额常超系统提示词正文——工具策略区块与"工具按需装配"（Codex 的 MCP 按输入动态拉起）都是为这个服务的。
>   - 量级基准：Claude Code 主干 workflow 提示词约 13.6KB（约 3.4k token）、Codex gpt-5.2 主干约 22KB（约 5.5k token）——主干 3-6k token 是当前主流，靠区块结构与按需加载而不是长度堆料。
>   - 提示词即代码：OpenClaw 有类型定义与单元测试，改区块走 PR 评审；主干与子任务分离（OpenCode 的 compaction/explore/summary/title 独立提示词）——压缩、起标题不占主干预算。
> - 追问与陷阱：
>   - 追问：system prompt 越长越专业吗？常见错误："大厂都是几千行"——主干 3-6k token 是主流，结构化与按需加载才是关键，泄露库里的"牢笼式"重复禁令多是踩坑补丁，照抄会把别家的债接过来。
>   - 追问：用户写的 AGENTS.md 会不会架空产品规则？常见错误："用户文件优先"——规范产品显式写裁决顺序与作用域（子树限定、深层优先），而不是靠模型自觉。
>   - 追问：提示词要不要进版本管理？常见错误："商业机密不进 git"——六家生产提示词全部是 git 管理的文件或代码，演进走 PR + 评测回归；不进版本管理的提示词无法回归。
> - 加分项：能现场画出装配时序（静态层 → 模板层填值 → 动态层追加 → cache-control 在 provider 可见投影之后统一设置），并指出"早设 cache-control 会被后续改动作废"这类只有读过源码才知道的细节。
> - 延伸阅读：[prompt-handbook §4 企业真实提示词收集与 §5 使用机制](../prompt-handbook/提示词搭建文档.md)｜[01-claude-code 架构拆解：逆向 12 文件的提示词组织](../01-claude-code/架构拆解.md)｜[06-opencode 架构拆解：15 文件提示词家族](../06-opencode/架构拆解.md)

> **Q019. 什么是 context rot 与 lost-in-the-middle？对长上下文应用设计意味着什么？**（难度：高 ｜ 频次：低）
> - 考察点：两个长上下文核心实证的名字、机理与五条设计推论——是否读过奠基文献并落到工程。
> - 参考回答：
>   - context rot（上下文腐烂）：token 越多，每个 token 分到的注意力越薄，模型对"曾经精确记得"的内容开始失准——原始观察来自 Chroma 的 context rot 研究，Anthropic 2025-09《Effective context engineering for AI agents》把它变成上下文工程的学科基石。
>   - lost in the middle（中间遗忘）：Liu et al. 2023（arXiv:2307.03172）用多文档问答实验证明：检索精度对关键文档在窗口中的位置呈 U 形——开头和结尾好、中间塌陷；同一偏差也出现在 LLM-as-judge 的 pairwise 评审里。
>   - 两者合起来推翻一个直觉：窗口大小 ≠ 有效容量——"注意力是预算，不是画布"；上下文工程的优化目标是"使期望结果最大化的最小高信号 token 集"，不是塞最多信息。
>   - 设计推论一（位置工程）：重要内容放两头——Claude Code 的生产提示词把防御性安全红线在开头和结尾各写一遍，few-shot 关键示例放开头或结尾而不是中间。
>   - 设计推论二（检索与注入排序）：RAG 召回的片段要按相关性排序而非随机堆放，最相关的放首尾；长文档场景"引用前先定位"（先指出在哪一段再作答）。
>   - 设计推论三（长会话治理）：剪枝（旧工具结果→占位符）→ 摘要（compact）→ 新窗口的三层模型，且剪枝排在摘要前面（工具结果信噪比衰减最快）；不变量是"日志为真源，压缩只改投影"。
>   - 设计推论四（评测侧）：位置偏差会污染评测——LLM-as-judge 的 pairwise 评审要用交换仲裁（两个顺序各评一次）对冲；长上下文能力要用长文档评测集验证，不能看参数表的窗口数字。
>   - 设计推论五（成本侧）：长上下文计价翻倍（Gemini 3.1-pro 输入 >200k 从 $2 到 $4/百万 token），"能塞下"与"塞得起且答得好"是三个不同的问题。
> - 追问与陷阱：
>   - 追问：既然有 1M 窗口为什么还谈注意力不够？常见错误："窗口=有效容量"——context rot 下中间内容利用率低，且长上下文计价翻倍，塞满是三输（质量、成本、延迟）。
>   - 追问：把关键信息重复写几遍能救吗？常见错误："多写几遍总行"——首尾位置工程有意义，但无脑重复挤占注意力预算；排序、检索与剪枝是正解。
>   - 追问：压缩摘要会不会丢关键约束？常见错误："摘要无损"——摘要有损，生产实现要配保真约束（ZCode 的摘要提示词两次强调安全相关指令必须逐字保留，9 段结构固定）。
> - 加分项：能引用六家 agent 的"上下文工程密度军备竞赛"证据链——从 anon-kode 时代的全量累积 + 手动 /compact，到 2026 年 ZCode 三层预算 + 熔断、OpenClaw 压缩质量审计、OpenCode 被评为密度最高——说明学科在三年内成形。
> - 延伸阅读：[context-handbook §1.1 上下文经济学：注意力是预算](../context-handbook/Context与记忆系统手册.md)｜[tuning-handbook §2.2 位置偏差在 few-shot 上的应用](../tuning-handbook/Agent调优手册.md)

> **Q020. 为什么 Claude Code/OpenCode 等顶级 agent 要"按模型分 prompt"？**（难度：高 ｜ 频次：低）
> - 考察点：per-model（按模型）提示词家族的工程动机——是否理解"提示词是模型能力的函数"。
> - 参考回答：
>   - 先给事实（本工作区一手证据）：Codex 仓库按模型放 5 份 prompt.md——gpt_5_1（24,535 字节）、gpt_5_2（21,950 字节）与三个 codex 变体（约 6.7-7.7KB）；OpenCode 的 session/prompt/ 下 15 个文件按模型/用途分家（gemini.txt、gpt.txt、anthropic.txt、kimi.txt、default.txt 等）；Claude Code 逆向还原出 12 个提示词文件——没有一家"一套 prompt 打天下"。
>   - 原因一：模型能力不同，指令密度应不同——gpt_5_1→gpt_5_2 主干从 24.5KB 减到 21.9KB：新代模型听得懂更短的指令，提示词随模型能力演进变短；而 codex 变体只要 7.7KB——同一产品内差距就是 3 倍。
>   - 原因二：模型有特有行为需要专属条款——OpenCode 的 anthropic.txt 有独有区块 "# Professional objectivity"；各家模型训练分布不同，同一句话的遵循度、语气、工具选择倾向都不同。
>   - 原因三：上下文经济参数因模型而异——tokenizer、窗口大小、缓存最小长度（Anthropic 的 Opus/Sonnet 为 1024 token、Haiku 4.5 为 4096）、推理预算都不同，提示词的长度与结构要跟着配。
>   - 原因四：成本——常驻提示词是每轮重发的成本项，为便宜的小模型配短 prompt 是成本工程的一部分；大模型配长 prompt 的"能力溢价"要有理由。
>   - 不分家的代价：一套通用 prompt 在部分模型上行为漂移（格式、语气、工具选择），且享受不到新模型的指令遵循红利——等于永远按"最弱公共分母"设计。
>   - 工程配套：模型信息当配置管——OpenCode 把模型清单（含 cost/limit/status(deprecated) 字段）外置到 models.dev 并 TTL 缓存，换模型从"发版"变"改配置"；其 agent 定义支持 per-agent 指定模型与温度（7 个内建 agent 各自配参）。
>   - 维护姿势：骨架共享 + 差异文件——八区块骨架跨模型复用，变的是各区块详略与专属条款（OpenCode 的 plan-reminder-anthropic.txt 就是按模型的差异补丁），配评测回归防止各家族漂移——不是每模型从零重写。
> - 追问与陷阱：
>   - 追问：按模型分 prompt 会不会维护爆炸？常见错误："一份改 N 份太乱"——骨架共享 + 差异补丁文件 + 评测回归是标准解法；真正的爆炸来自无骨架的 N 份独立拷贝。
>   - 追问：小模型直接抄大模型的 prompt 行吗？常见错误："同一份全用"——小模型通常需要更低的指令密度、更多示例、更显式的步骤，抄长 prompt 往往更差。
>   - 追问：新模型上线怎么迁 prompt？常见错误："直接切流量"——先跑同评测集对比新旧模型行为差异，再决定继承、瘦身或新增条款；把 prompt 演进做成 PR + 回归而不是线上试错。
> - 加分项：能指出"按模型分家"与"按模型路由"是同一件事的两面——路由层（§6.5）决定请求去哪档，提示词家族决定那档里说什么；两者都模型化后，换模型才真正从发版变成改配置。
